6장 이벤트 소싱과 저장소

V2 세션은 "메모리 속 메시지 배열"이 아닙니다. 모든 상태 변화는 SQLite에 이벤트로 기록되고, 화면과 모델이 보는 메시지 표는 그 이벤트를 투영(projection)한 결과입니다. 이 장은 V2의 모든 내구성(durability)을 떠받치는 Bus와 저장소를 다룹니다.

6.1 왜 이벤트 소싱인가

코딩 에이전트에는 세 가지 까다로운 요구가 있습니다.

  1. 죽어도 이어서 해야 합니다. 서버가 업그레이드되거나 크래시해도 진행 중이던 턴을 재개해야 합니다.
  2. 여러 화면이 같은 세션을 봅니다. TUI, 데스크톱, 웹이 동시에 붙고, 늦게 붙은 클라이언트도 정확히 따라잡아야 합니다.
  3. 되돌릴 수 있어야 합니다. 특정 메시지 이전으로 되돌리거나(revert) 갈라서(fork) 다른 길을 시도합니다.

"무슨 일이 일어났는가"를 순서 있는 사실의 목록으로 남기면 세 요구가 모두 같은 원리로 풀립니다. 재개는 로그를 다시 읽는 것이고, 동기화는 특정 시퀀스 이후를 재생하는 것이며, 되돌리기는 경계 이후를 투영에서 지우는 것입니다.

AGENTS.md의 원칙 영속 이벤트는 최소로 유지합니다. 환원 불가능한 새 사실만 기록하고, 순서 있는 집합체 이력을 접어서(fold) 얻을 수 있는 상태는 반복하지 않습니다. 풍부한 정보는 투영과 읽기 모델에 둡니다.

텍스트·추론 델타는 100ms마다 묶여 실시간으로만 흐르고 재생되지 않습니다. *.Started는 파트의 시작과 식별 정보(메시지 ID, 순번)만 기록하고, *.Ended가 전체 텍스트를 담습니다. 소스 주석 그대로 "Text.Ended is the replayable full-value boundary"입니다. 토큰 하나하나를 영속화하지 않으면서도 결과는 잃지 않는 절충입니다.

6.3 Bus: 한 트랜잭션 안의 이벤트와 투영

packages/core/src/bus.ts(909줄)는 이벤트 소싱과 실시간 pub/sub를 겸합니다. 핵심은 publish가 영속 이벤트를 기록하는 방식입니다.

sequenceDiagram participant Caller as 호출자 participant Bus participant DB as SQLite (BEGIN IMMEDIATE) participant Proj as 투영기들 participant Sub as 실시간 구독자 Caller->>Bus: publish(InboxEnqueued, data, commit?) Bus->>DB: 트랜잭션 시작 Bus->>DB: 집합체 마지막 seq 읽기, seq = latest+1 Bus->>Proj: 해당 타입의 투영기 모두 실행 Proj->>DB: session_inbox 행 삽입 등 Bus->>DB: commit(seq) 훅 (클레임 등) Bus->>DB: event_sequence 갱신, event 삽입 DB-->>Bus: COMMIT Bus->>Sub: 실시간 라우팅, 로그 추종자 깨우기

그림 6-1 영속 이벤트 발행 — 이벤트와 상태 변화가 하나의 원자 단위

투영기가 죽으면(예: 이미 존재하는 ID로 LifecycleConflict) 트랜잭션 전체가 취소됩니다. 이벤트는 기록됐는데 상태는 안 바뀌는 어긋남이 원천적으로 생기지 않습니다. 멱등성과 충돌 감지도 이 원자성 위에서 구현됩니다.

subscribe                              // 휘발성 실시간 Stream

replay / remove / claim

6.4 log와 Synced 표지: 빈틈없는 따라잡기

log()는 follow:false면 로그 끝에서 완료하고, follow:true면 재생 후 실시간으로 전환합니다. 두 모드 모두 재생 워터마크에서 Synced 표지를 한 번 보냅니다.

재생과 실시간 사이의 틈을 어떻게 메울까요? "과거를 읽고 나서 구독"하면 그 사이 커밋된 이벤트를 놓칩니다. Bus는 먼저 구독하고 나서 과거를 읽습니다. 소스 주석 그대로, 재생 중 커밋된 이벤트는 "읽기에 나타나거나, 표지 이후 깨움으로 도착"합니다. 중복은 seq로 걸러지고 누락은 없습니다.

저장된 페이로드는 읽을 때 업그레이드됩니다(SessionLegacy.event). 옛 모양으로 쓰인 이벤트도 한 곳에서 새 스키마로 변환되므로, 이벤트 스키마를 진화시켜도 과거 로그가 깨지지 않습니다.

6.5 Database 서비스

  • SQLite 단일 파일을 Effect SqlClient 위에서 도는 사내 Drizzle 포크로 다룹니다. 드라이버는 Bun, Node, workerd(Durable Objects) 세 가지입니다.
  • PRAGMA: journal_mode=WAL, synchronous=NORMAL, busy_timeout=5000, cache_size=-64000, foreign_keys=ON.
  • 파일과 -wal/-shm은 POSIX에서 0600입니다.
  • 마이그레이션은 경로별 세마포어 아래서 돕니다. 빈 DB는 schema.gen.ts로 한 번에 부트스트랩하고 모든 마이그레이션을 완료 처리합니다(마이그레이션 59개, 최신 20261030054400_job).
  • "OpenCode는 접두사 없는 테이블 이름공간을 소유합니다. DB를 공유하는 임베더는 밑줄 접두사 테이블을 쓸 수 있습니다."
  • v1-migration.bun.ts(1,234줄)가 V1 데이터를 가져옵니다.

왜 하나의 SQLite 파일일까요? V1은 세션·메시지·파트를 각각 JSON 파일로 저장했습니다(2장 참고). 파일이 수만 개가 되면 목록 조회가 느려지고, 여러 파일에 걸친 변경을 원자적으로 할 수 없습니다. WAL 모드 SQLite는 단일 파일로 동시 읽기와 원자적 다중 테이블 쓰기를 모두 주며, 4장의 "고정 포트로 단일 서버 보장"과 결합해 쓰기 경쟁도 피합니다.
