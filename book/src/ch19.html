그림 19-1 추천 읽기 경로

버전 고정 GitHub의 dev 브랜치 링크는 계속 바뀝니다. 2.3.0 구현을 분석하려면 반드시 v2.3.0 태그(또는 이 책이 참조한 로컬 저장소)를 기준으로 삼으십시오.

19.2 소스를 읽는 요령

  • AGENTS.md를 먼저: 루트와 각 패키지의 AGENTS.md는 기여자용 규칙이지만, "왜 이렇게 하지 말라"는 금지 조항 하나하나가 과거의 실패를 담고 있어 설계 의도를 읽기에 가장 좋은 문서입니다.
  • 명세는 의도, 코드는 현재: 이 책에서 찾은 불일치만 해도 재시도 횟수, 출력 잘라내기 방식, 훅 실행 시점, 도구 이름 등록 방식 등이 있습니다.
  • 주석의 "why"를 수집: V2 코드는 "무엇을"보다 "왜"를 주석으로 남기는 규칙을 따릅니다(AGENTS.md: "명백하지 않은 제약만 주석으로"). // Write-ahead claim: ... 같은 주석이 설계 문서 역할을 합니다.
  • 이벤트를 따라가기: 어떤 기능이든 "어떤 영속 이벤트를 발행하고 어떤 투영기가 받는가"를 추적하면 데이터 흐름이 드러납니다.
  • 시뮬레이션으로 실행: OPENCODE_SIMULATE와 packages/simulation으로 실제 프로바이더 없이 결정적으로 돌려 볼 수 있습니다.

19.5 비공식 감사 문서를 비판적으로 읽기

"Deep Architectural Audit"는 2.x 내부를 가장 폭넓게 분석한 단일 문서이지만, ChatGPT 답변이 경고한 대로 현행 구현 설명(1·2부)과 작성자의 비판·재설계 제안(3·4부)이 섞여 있습니다.

부내용이 책과의 대조
1부모노레포 토폴로지, 2층 Effect 레이어 그래프, 세션 수명주기(접수·inbox·스텝·투영), 지침 델타, 압축 수치, 도구 실행대부분 이 책의 3~10장과 일치(예: keep 15k, SHRINK_STEPS, 출력 2,000줄/50 KiB). 단 v2.0.26 기준이라 백그라운드 서브에이전트 기본값 등 2.3.0 변경은 없음

외부 분석을 다루는 원칙 ① 버전을 확인합니다(이 문서는 2.0.26). ② "현재 구현"이라는 주장은 소스로 검증합니다. ③ 비판은 근거(파일·줄)를 따라가 직접 판단합니다. ④ 제안은 제안으로만 읽습니다. 이 책도 예외가 아닙니다. 이 책의 모든 설명은 2.3.0 소스를 기준으로 했지만, 여러분이 읽는 시점의 코드와 다를 수 있습니다.

19.6 맺으며

OpenCode V2를 관통하는 설계 원칙을 다섯 줄로 정리하며 책을 마칩니다.

  1. 사실을 먼저 기록하라. 입력도, 도구 호출도, 실행 의도도 부작용 전에 디스크에 남깁니다(이벤트 소싱, 클레임).
  2. 경계에서만 바꿔라. 입력 승격, 설정 리로드, Location 이동, 지침 변경은 모두 "스텝 경계"에서 일어납니다.
  3. 캐시를 존중하라. 바뀌지 않는 것은 앞에, 바뀌는 것은 뒤에, 변경은 덧붙여서.
  4. 재생 가능하게 만들어라. 카탈로그는 변환의 재생, 세션은 이벤트의 재생, 클라이언트는 로그의 재생입니다.
  5. 거부는 거부답게. 사용자의 "아니오"와 중단은 모델이 우회할 수 있는 오류로 바꾸지 않습니다.

이 원칙들은 OpenCode에만 해당하지 않습니다. 장기 실행되는 모든 에이전트 시스템을 설계할 때 같은 질문 — "이것이 중간에 끊기면 무엇이 깨지는가?" — 을 던져 보십시오.
