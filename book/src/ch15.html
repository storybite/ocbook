15장 플러그인과 훅 — 엔진을 넓히고 끼어들기

플러그인은 코드를 써서 OpenCode를 넓히는 수단입니다. 도구·에이전트·명령 같은 목록을 바꾸고, 터미널과 데스크톱 화면을 늘리고, 작업 흐름 중간에 끼어듭니다. 이 장은 먼저 플러그인의 구조와 로딩 순서, 최소 예제를 보고(15.1~15.3절), 이어서 플러그인의 핵심 도구인 훅을 다룹니다. OpenCode가 일하는 과정은 정해진 순서로 흘러갑니다. 사용자 입력을 받고, 모델에 요청을 보내고, 도구를 실행하고, 일이 끝나면 쉽니다. 훅(hook)은 이 흐름의 정해진 지점마다 뚫어 둔 "끼어들기 구멍"입니다. 플러그인은 그 구멍에 함수를 걸어 두고, OpenCode가 그 지점을 지날 때마다 그 함수가 불려 "지금 하려는 일"을 들여다보고 고칠 수 있습니다. 15.4절부터는 훅이 무엇이고 어떻게 동작하는지 쉬운 예로 시작해서, 훅이 흐름의 어디에 걸려 있는지, OpenCode 자신이 훅으로 무엇을 만들었는지를 차례로 보고, 마지막에 직접 훅을 써서 OpenCode를 내 팀에 맞게 바꾸는 방법을 정리합니다.

15.2 로딩 순서와 수명

목록을 다시 만드는 원리

OpenCode에는 처음부터 들어 있는 명령도 있고, 설정 파일이나 플러그인으로 추가한 명령도 있습니다. 이 명령들을 모아야 사용자가 쓸 수 있는 하나의 목록이 됩니다.

이때 OpenCode는 목록을 만드는 방법을 순서대로 기억합니다. 기본 기능, 설정을 읽는 부분, 외부 플러그인이 각자 “이 명령을 더해 주세요”나 “이 명령을 빼 주세요”라는 지시서를 맡기는 셈입니다. 코드에서는 이런 지시서를 변환(transform)이라고 부릅니다.

설명을 위해 “기본 명령 넣기”, “테스트 명령 더하기”, “번역 명령 더하기”라는 지시서가 이 순서대로 등록됐다고 가정하겠습니다. 마지막 지시서는 번역 플러그인이 맡겼습니다. OpenCode가 빈 목록에 세 지시서를 차례로 적용하면 기본 명령에 테스트 명령과 번역 명령이 더해집니다.

이제 번역 플러그인을 끄면 어떻게 될까요? 그 플러그인이 맡긴 “번역 명령 더하기” 지시서가 빠집니다. OpenCode는 빈 목록에서 시작해 남은 두 지시서를 다시 적용합니다. 그러면 기본 명령과 테스트 명령만 있는 목록이 만들어집니다. 플러그인이 했던 일을 거꾸로 취소하는 코드를 따로 만들 필요가 없습니다.

“재생 가능한 변환”은 남아 있는 지시서를 처음부터 다시 실행할 수 있다는 뜻입니다. 지시서가 추가되거나 빠졌을 때, 또는 새로 고침(reload())을 할 때 목록을 다시 만듭니다. 완성된 목록이 이전과 달라졌을 때만 “목록이 바뀌었다”는 이벤트를 보냅니다.

설정 파일도 이 과정에 참여합니다. 내부 플러그인이 설정을 읽고, 그 내용을 목록에 반영할 지시서를 등록합니다. 따라서 설정으로 더한 기능과 외부 플러그인으로 더한 기능을 같은 방식으로 모을 수 있습니다.

명령뿐 아니라 에이전트, 스킬, MCP 서버, 프로바이더, 모델, 도구 등도 같은 원리로 목록을 관리합니다. 이런 목록은 작업 위치(Location)별로 관리되며, 플러그인이 맡긴 지시서는 그 플러그인이 켜져 있는 동안만 유지됩니다.

왜 설정 자체를 고치는 방식 대신 이 방식을 택했을까요? 플러그인이 설정을 고치고, 그 설정을 쓰는 서비스들을 다시 불러오는 방식도 검토했습니다. 하지만 설정을 건드릴 때마다 다시 불러와야 할 서비스가 많아집니다. 채택한 방식에서는 설정과 플러그인이 각각 목록을 만드는 지시서를 맡깁니다. 플러그인을 끄거나 설정을 새로 읽을 때도 남은 지시서를 다시 적용하면 됩니다. 여러 변경을 “목록 다시 만들기”라는 같은 절차로 처리하려는 설계입니다.

15.3 플러그인 컨텍스트와 최소 예제

ctx는 app, location, options와 도메인들 — agent, aisdk, command, credential, event, integration, mcp, model, permission, plugin, provider, reference, rpc, session, shell, skill, storage, tool, vcs, websearch, worktree — 그리고 experimental.{terminal.read, generate, artifact}를 제공합니다. 각 도메인은 생성된 @opencode/client/effect/api 인터페이스를 확장하므로 플러그인·원격 클라이언트·임베디드 호스트가 같은 API 어휘를 씁니다.

.opencode/plugins/guard/index.tsimport { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "guard",
  setup: async (ctx) => {
    // 1) 리뷰어 서브에이전트 추가
    await ctx.agent.transform((agents) =>
      agents.update("reviewer", (a) => { a.mode = "subagent"; a.description = "보안 리뷰" }))
    // 2) 위험한 셸 차단
    await ctx.tool.hook("execute.before", (e) => {
      const command = String((e.input as { command?: unknown })?.command ?? "")
      if (e.tool === "shell" && /rm -rf \//.test(command))
        throw new Error("루트 삭제는 허용되지 않습니다")
    })
    // 3) 재시도 3회 이상이면 포기
    await ctx.session.hook("retry", (e) => { if (e.attempt >= 3) e.decision = { retry: false } })
    return () => { /* 정리 */ }
  },
})

README의 Promise 형식과 packages/plugin/src/promise/tool.ts의 ToolHooks 타입(tool, sessionID, agent, messageID, id, input: unknown)에 맞춘 설명용 코드입니다. before 훅에서 던진 오류는 어댑터가 Tool.Error로 바꿔 호출을 거부합니다.

  • 플러그인은 호스트의 effect 인스턴스를 공유하므로 effect를 peer dependency로 선언하고 번들하지 않습니다.
  • 실제 예: packages/plugins/figma는 ctx.mcp.transform으로 원격 서버를, ctx.skill.transform으로 번들 스킬을 추가하되 기존 ID는 덮지 않습니다.
  • V1 플러그인 코드는 V2에서 실행되지 않습니다. /docs/build/plugins/migrate-v1 가이드를 따라야 합니다.

변환과 훅

위 예제에는 확장 방식 두 가지가 섞여 있습니다. ctx.agent.transform처럼 목록을 고치는 변환은 "무엇이 있는가"를 바꿉니다(15.2절). ctx.tool.hook·ctx.session.hook처럼 작업 흐름에 끼어드는 훅은 "지금 일어나는 일"을 바꿉니다. 훅은 session, tool, permission, shell, aisdk 다섯 도메인에 모두 스물한 개가 있습니다. 등록 순서대로 하나씩 실행되고, 모두 같은 이벤트 객체를 고칩니다. 실패해서 호출을 거부할 수 있는 것은 tool.execute.before뿐입니다. 다음 절부터 훅을 자세히 봅니다.

15.4 훅이란 무엇인가

비유로 먼저: 공항의 세 가지 장치

공항을 떠올려 보십시오. 승객이 비행기를 타기까지 공항이 승객에게 영향을 주는 방법은 세 가지가 있습니다.

공항OpenCode성격
운항 시간표: 어떤 비행기가 몇 시에 있는지변환(transform): 어떤 에이전트·도구·모델이 있는지"무엇이 있는가"를 정함. 승객 한 명 한 명과는 무관
보안 검색대: 승객이 지나갈 때마다 가방을 열어 보고, 위험물은 빼거나 통과를 막음훅(hook): 요청·도구 호출이 지나갈 때마다 내용을 보고 고치거나 막음"지금 지나가는 이 일"을 바꿈. 통과하는 순간에, 그 자리에서
출발 안내판: 이미 떠난 비행기를 보여 줌이벤트 구독: 이미 일어난 일을 알려 줌보기만 할 뿐 바꿀 수 없음

훅은 보안 검색대입니다. 모든 승객이 반드시 지나가야 하는 길목에 서 있고, 지나가는 승객(이벤트)의 가방을 열어 내용물을 바꿀 수 있습니다. 그래서 가장 강력하지만, 검색대가 느리면 모든 승객이 늦어지고 검색대가 고장 나면 탑승 자체가 멈춥니다. 훅도 똑같습니다. 이 장의 주의 사항은 대부분 이 성질에서 나옵니다.

플러그인이 엔진에 영향을 주는 세 수단 — 고르는 기준

여기서 목록은 OpenCode가 사용할 수 있는 에이전트·도구·MCP 서버·모델을 종류별로 모아 둔 명단입니다.

수단API언제 실행되나바꿀 수 있는 것예
변환ctx.agent.transform(...) 등목록이 다시 계산될 때에이전트·도구·MCP·모델 목록"리뷰어" 서브에이전트를 추가
훅ctx.session.hook(...) 등그 일이 일어나는 바로 그 순간그 일 하나의 입력·결과·결정위험한 셸 명령 하나를 거부
이벤트 구독ctx.event.subscribe(...)일이 끝나 기록된 뒤없음(보기만)실행이 실패하면 메신저로 알림

한 줄로 줄이면 이렇습니다. 무엇을 갖출지는 변환으로, 지금 이 일을 어떻게 할지는 훅으로, 일어난 일을 알기만 하면 이벤트로.

훅 하나는 이렇게 생겼다

가장 단순한 훅을 봅시다. 모델이 셸 명령을 실행하려 할 때마다 명령을 콘솔에 찍는 훅입니다.

export default Plugin.define({
  id: "logger",
  setup: async (ctx) => {
    //            도메인    이름               이 지점을 지날 때마다 불릴 함수
    await ctx.tool.hook("execute.before", (event) => {
      if (event.tool === "shell") console.log("셸 실행:", event.input)
    })
  },
})

읽는 법은 세 부분입니다.

  1. 어디에 걸까: ctx.tool.hook("execute.before", …)는 "도구(tool) 도메인의 실행 직전(execute.before) 지점"이라는 뜻입니다. 이 둘을 합쳐 tool.execute.before 훅이라고 부릅니다.
  2. 무엇을 받나: 함수가 받는 event가 "지금 지나가는 일"입니다. 이 훅이라면 도구 이름(tool), 입력(input), 세션 ID 등이 들어 있습니다.
  3. 어떻게 바꾸나: 돌려주는 값은 없습니다. 바꾸고 싶으면 event의 필드를 직접 고칩니다. 예를 들어 event.input = {...}로 입력을 바꾸면 도구는 바뀐 입력으로 실행됩니다.
이 장에서 쓰는 말
  • 훅 지점: OpenCode가 훅을 부르는 자리. 이름은 도메인.이름(예: session.context).
  • 도메인: 훅을 묶는 분야. session(세션·모델 요청), tool(도구 실행), permission(권한 판정), shell(셸 프로세스), aisdk(AI SDK 모델 생성) 다섯 가지.
  • 이벤트 객체: 훅 함수가 받는 event. 입력과 출력을 함께 담은 "고칠 수 있는 서류"입니다. 이 장의 "이벤트"는 6장의 저장소 이벤트와 다른 말이니 혼동하지 마십시오.
  • 등록: hook(...)을 불러 함수를 훅 지점에 걸어 두는 것.
  • 발동: OpenCode가 그 지점을 지나며 걸린 함수들을 부르는 것(소스의 trigger).
V1의 훅과 무엇이 달라졌나

V1(1.x) 플러그인은 함수 하나가 "훅 객체"를 돌려주는 형태였습니다. "chat.message", "chat.params", "chat.headers", "tool.execute.before", "permission.ask", "experimental.chat.system.transform" 같은 키에 (input, output) 함수를 매다는 방식입니다. V2는 이것을 두 갈래로 정리했습니다.

  • 목록을 바꾸는 일은 변환으로 옮겼습니다. V1의 config, tool, tool.definition 같은 키가 하던 일입니다. 변환은 다시 계산할 수 있으므로 플러그인을 내리면 흔적 없이 되돌아갑니다(15.2절).
  • 일에 끼어드는 것은 도메인별 훅으로 묶었습니다. 이름은 도메인.이름 하나의 체계이고, 입력과 출력은 이벤트 객체 하나에 함께 들어 있습니다. V1의 chat.* 계열은 V2의 session.context(요청 내용)와 session.model.request(주소·헤더)로 나뉘었습니다.

V1 플러그인 코드는 V2에서 그대로 돌지 않습니다. Promise 어댑터는 setup이 V1식 훅 객체를 돌려줘도 오류를 내지는 않지만, 그 객체를 훅으로 쓰지 않고 무시합니다(plugin/src/promise/adapter.ts: "only a function is a cleanup"). V1과 V2 모두 설정 파일에 셸 명령을 적는 방식의 훅은 없습니다. OpenCode의 훅은 전부 플러그인 코드입니다.

15.5 동작 원리: 한 줄로 서서, 같은 서류를 고친다

모든 훅은 Location(5장)마다 하나씩 있는 PluginHooks 서비스에 모입니다. 구현은 100줄 남짓이고, 핵심인 "발동"은 몇 줄입니다.

core/src/plugin/hooks.tsconst trigger = Effect.fnUntraced(function* (domain, name, event) {
  for (const entry of callbacks.get(key(domain, name)) ?? []) {      // ① 등록된 순서대로
    if (entry.options?.providerID !== undefined &&
        entry.options.providerID !== eventProviderID(event)) continue // ② 다른 프로바이더용이면 건너뜀
    yield* entry.callback(event)                                      // ③ 같은 event를 넘김
  }
  return event                                                        // ④ 마지막 모습을 돌려줌
})

이 코드를 풀어 말하면 다섯 가지 규칙이 됩니다.

  1. 한 줄로 섭니다. 같은 훅 지점에 함수가 여럿 걸려 있으면 등록된 순서대로 하나씩 부릅니다. 동시에 부르지 않습니다. 등록 순서는 플러그인 로딩 순서(15.2절)를 따릅니다. 내장 플러그인이 먼저, 외부 플러그인이 다음, 설정 리더와 정책 플러그인이 맨 뒤입니다.
  2. 같은 메모장 한 장을 차례로 고칩니다. 모든 함수가 받는 같은 이벤트 객체 하나를 메모장이라고 생각하면 됩니다. 플러그인 A가 권한을 ‘허용’에서 ‘질문’으로 바꾸면, B는 ‘질문’으로 바뀐 상태를 받아 이어서 고칩니다. OpenCode는 모든 플러그인을 거친 뒤 메모장에 남은 값을 사용합니다.
  3. 마지막 사람이 최종 결정권을 가집니다. 그래서 "정책 플러그인이 맨 마지막에 실행된다"는 말은 곧 "정책이 마지막 결정을 한다"는 뜻입니다.
  4. 프로바이더를 골라 걸 수 있습니다. 이벤트에 model이 있는 훅은 { providerID: "anthropic" } 같은 옵션으로 그 프로바이더의 요청에만 걸 수 있습니다(②).
  5. 플러그인과 함께 사라집니다. 등록할 때 플러그인의 수명(Scope)에 정리 함수가 함께 걸립니다. 플러그인을 끄거나 고쳐서 다시 로드하면 그 플러그인의 훅도 자동으로 빠집니다.

예: 세 플러그인이 같은 권한 훅에 걸려 있다면

모델이 git push를 실행하려 해서 권한 판정이 일어났고, 설정 규칙상 판정은 "허용(allow)"이라고 합시다. permission.evaluate 훅에 세 함수가 이 순서로 걸려 있습니다.

훅이 실패하면 — 가장 중요한 규칙

실패해도 되는 훅은 tool.execute.before 하나뿐입니다. 이 훅에서 오류를 던지면 그 도구 호출 하나만 거부되고, 모델은 오류 메시지를 도구 결과로 받습니다. 즉 "이 명령은 안 됩니다, 이유는…"이라는 답을 받고 다른 방법을 찾습니다.

나머지 훅에는 실패할 통로가 없습니다. Promise API에서 이런 훅이 예외를 던지면 예상하지 못한 결함(defect)으로 처리되어 그 실행 전체가 실패합니다. 사용자 입장에서는 하던 일이 갑자기 오류로 끝납니다. 플러그인 README도 "다른 세션 훅처럼 실패하면 실행이 실패한다"고 경고합니다.

그러니 원격 서버를 부르는 것처럼 실패할 수 있는 작업은 훅 안에서 직접 try/catch로 감싸십시오. 내장 플러그인도 대부분 훅 끝에 오류 처리를 붙여, 실패하면 로그만 남기고 넘어갑니다.

성능을 위한 장치도 하나 있습니다. session.http.request/response 훅은 등록된 함수가 있을 때만 요청을 웹 표준 Request/Response 객체로 바꿉니다(hooks.has로 확인). 아무도 이 훅을 쓰지 않으면 변환 비용도 들지 않습니다.

15.7 요청 훅: 모델이 보는 것을 바꾸기

모델이 보는 세상은 결국 요청 하나입니다(9장). 요청 훅은 그 요청이 조립된 직후, 보내기 직전에 불려 모델이 볼 내용을 고칠 기회를 줍니다. 요청에는 네 종류가 있고, 종류마다 훅 이름이 다릅니다.

요청 종류언제훅

압축(compaction)대화를 요약할 때(9.6절)session.compaction
부수 생성(generate)플러그인이 ctx.session.generate로 따로 물을 때session.generate

네 훅 모두 한 함수(SessionModelRequest.prepare)의 같은 자리에서 불리고, 받는 이벤트도 거의 같습니다.

예: 매 요청에 팀 규칙 한 줄 상기시키기

  event.messages.splice(at, 0, reminder as any)
})

메시지 모양은 설명을 위해 단순화했습니다. 내장 플러그인은 Message.user(text)(@opencode/ai/effect)로 만듭니다(plugin/plan.ts, plugin/goal.ts).

이렇게 넣은 문장은 그 요청에만 들어가고 저장되지 않습니다. 화면에도, 세션 기록에도 보이지 않습니다. 다음 스텝에서 훅이 다시 불려 다시 넣는 방식입니다. 늘 같은 내용이라면 굳이 훅을 쓰지 말고 AGENTS.md(13.2절)에 적는 편이 쉽습니다. 훅은 "상황에 따라 다른 내용"을 넣을 때 쓸모가 있습니다. 예를 들어 지금 브랜치 이름이나 진행 중인 목표 같은 것입니다.

왜 "끝 근처에" 넣어야 하나 — 캐시 이야기

9.1절에서 보았듯 프로바이더는 요청의 앞부분이 지난번과 똑같으면 그만큼을 캐시에서 싸고 빠르게 처리합니다. 앞에서 한 글자라도 다르면 그 뒤는 전부 새로 계산합니다. 책 한 권을 복사할 때, 1쪽에서 한 글자가 바뀌면 1쪽부터 다시 복사해야 하는 것과 같습니다.

넣는 자리넣는 내용결과
system 맨 앞현재 시각(매번 다름)❌ 매 스텝 캐시 전부 무효. 긴 세션에서 비용이 몇 배로
system 앞쪽모델 이름(바뀌지 않음)✅ 매번 같으므로 괜찮음(identity 플러그인)
마지막 사용자 메시지 앞상황에 따라 바뀌는 알림✅ 앞부분은 그대로라 캐시 유지(Plan·goal 플러그인)

규칙은 하나입니다. 매번 같은 값이면 앞에 넣어도 되고, 바뀌는 값이면 뒤에 넣습니다. Plan 플러그인 소스의 주석도 같은 말을 합니다. "appending near the tail so the cached prefix stays warm."

도구 메뉴 고치기

tools로 할 수 있는 일은 세 가지입니다.

  • 설명 고치기: event.tools.read.description = "offset과 limit으로 필요한 줄 범위만 읽으십시오." — 파일 전체 대신 read의 offset(시작 줄)과 limit(읽을 줄 수)을 지정해 필요한 코드 주변만 읽도록 유도해, 불필요한 텍스트가 모델의 컨텍스트를 차지하는 일을 줄이려는 예입니다. 내장 셸 도구는 이 훅으로 실제로 쓰일 셸 이름을 설명에 넣고, 서브에이전트 도구는 지금 부를 수 있는 서브에이전트 목록을 설명 끝에 붙입니다(tool/plugin/shell.ts, tool/plugin/subagent.ts).
  • 숨기기: delete event.tools.write — 이번 요청에서 모델이 그 도구를 보지 못합니다.
  • 이름 바꾸기: 정의를 다른 키로 옮기면 모델은 새 이름을 봅니다. OpenCode는 훅에 넘긴 정의 객체가 원래 어느 도구였는지 기억해 두므로, 모델이 새 이름으로 부르면 원래 도구가 실행됩니다.

반대로 새 도구를 만들어 넣는 것은 안 됩니다. 어느 도구에서도 오지 않은 정의는 실행할 대상이 없으므로 버려집니다. 도구 추가는 훅이 아니라 변환(ctx.tool.transform)의 일입니다. "메뉴판 글씨는 고칠 수 있어도, 주방에 없는 요리를 메뉴에 올릴 수는 없다"고 생각하면 됩니다.

모델 호출을 아예 건너뛰기: result

compaction과 title 훅에는 result 필드가 있습니다. 여기에 값을 넣으면 OpenCode는 모델을 부르지 않고 그 값을 결과로 씁니다.

// 제목을 모델 대신 규칙으로: "[브랜치] 작업 세션"
await ctx.session.hook("title", (event) => {
  event.result = `[${currentBranch}] 작업 세션`
})

currentBranch는 setup에서 미리 구해 두었다고 가정한 설명용 변수입니다.

제목이나 요약을 자체 규칙·자체 요약기로 만들고 싶을 때, 모델 호출 한 번을 통째로 아낄 수 있습니다.

참고: 요약은 모델에 맡기고, 남길 것만 지시하기

압축 요청은 주 요청과 같은 대화를 보내 그 캐시를 다시 쓰려고 합니다. system에 문장을 더하면 그 뒤의 대화 부분은 캐시를 다시 쓰지 못한다는 점도 기억해 두십시오.

15.8 전송 훅: 어디로, 어떻게 보낼지 바꾸기

무엇을 보낼지 정해진 다음에는 "어느 모델로, 어느 주소로, 어떤 헤더를 붙여" 보낼지가 남습니다. 이 단계의 훅은 대부분 프로바이더 플러그인을 위한 것이지만, 회사 환경에 맞출 때는 일반 사용자에게도 쓸모가 있습니다. 편지에 비유하면 15.7절이 "편지 내용"을 고치는 일이고, 이 절은 "봉투와 배송 방법"을 고치는 일입니다.

훅쉽게 말하면언제 쓰나
session.experimental.model.resolve이번 요청만 다른 모델로"라우터 모델". 요청 종류(kind)를 보고 주 요청은 큰 모델로, 제목은 작은 모델로
session.model.request받는 주소(baseURL)와 봉투에 붙일 표(headers)사내 게이트웨이·프록시 경유, 추적·비용 집계용 헤더
session.http.request / response실제 HTTP 요청·응답을 통째로본문 검사·마스킹, 오류 응답 바꾸기
session.experimental.ws.*WebSocket 연결과 프레임 하나하나WebSocket 전송(9.8절) 디버깅·변형
session.retry"다시 보낼까?"의 결정재시도 횟수 제한, 대기 시간 조정
aisdk.sdk / aisdk.language모델과 통신할 SDK 객체 자체OpenCode에 내장되지 않은 AI SDK 패키지 붙이기(16장)

각 훅의 세부 규칙은 이렇습니다.

  • model.resolve는 같은 프로바이더 안에서만 모델을 바꿀 수 있습니다. 다른 프로바이더의 모델을 지정하면 ModelUnavailableError가 납니다. 자격 증명과 훅이 원래 선택한 프로바이더의 것으로 유지되기 때문입니다. 세션에 저장된 모델 선택은 바뀌지 않고, 이번 요청만 바뀝니다. GitHub Copilot의 "Auto" 모델이 이 훅으로 만들어졌습니다.
  • model.request의 headers에는 7.7절의 affinity 헤더(x-session-affinity 등)가 이미 들어 있습니다. 덮어쓰면 캐시 라우팅이 흐트러질 수 있으니 추가만 하는 것이 안전합니다.
  • http.request에서 요청 객체를 그대로 두면 OpenCode는 원래 본문을 다시 읽지 않고 그대로 보냅니다. 스크린샷이 든 큰 요청을 메모리에 두 벌 들고 있지 않기 위한 배려입니다. 본문을 고칠 때만 새 Request를 만들어 넣으십시오. OpenCode 프로바이더 플러그인은 응답 훅으로, 콘솔 연결 상태 때문에 생긴 오류 응답을 원인을 설명하는 인증 오류로 바꿔 돌려줍니다.
  • ws.send/receive로 프레임을 바꾸면 바뀐 프레임이 그대로 오갑니다. 프로토콜의 의미가 달라지게 고치는 것은 전적으로 플러그인 책임입니다.
  • retry 훅은 "재시도할 수 있다"고 판정된 오류에서만 불립니다(8.5절). event.decision = { retry: false }로 포기시키거나 delay(밀리초)를 바꿀 수 있습니다. 지연 값이 음수나 무한대면 원래 값을 씁니다. 반대로 재시도 대상이 아닌 오류를 재시도하게 만들 수는 없습니다. 훅이 불리지 않기 때문입니다.
// 사내 게이트웨이 경유 + 팀 헤더 (anthropic 요청에만)
await ctx.session.hook("model.request", (e) => {
  e.baseURL = "https://llm-gateway.internal/anthropic"
  e.headers["x-team"] = "platform"
}, { providerID: "anthropic" })

주소와 헤더 이름은 설명용입니다. 주소가 고정이라면 훅보다 providers.<id> 설정(17.9절)이 간단합니다. 훅은 요청마다 다르게 정해야 할 때 씁니다.

참고: 프롬프트와 응답 들여다보기(디버깅)

session.http.request/response 훅을 쓰면 모델이 실제로 받은 요청 본문(시스템 프롬프트·대화·도구 정의)과 모델의 응답을 그대로 볼 수 있습니다. WebSocket 전송(9.8절)을 쓰는 모델이면 session.experimental.ws.*의 send/receive로 프레임을 봅니다. 응답 본문은 스트림이라 훅에서 원본을 읽어 버리면 OpenCode가 받을 내용이 사라집니다. 그래서 내장 프로바이더 플러그인도 event.response.clone().text()처럼 복사본만 읽습니다(plugin/provider/snowflake-cortex.ts).

import { appendFile } from "node:fs/promises"

const LOG = "/tmp/opencode-http.log"
const log = (text: string) => void appendFile(LOG, text + "\n").catch(() => {})

await ctx.session.hook("http.request", (e) => {
  // 요청 객체는 바꾸지 않고 복사본만 읽는다
  void e.request.clone().text().then((body) => log(`>>> ${e.kind} ${e.request.url}\n${body}`))
})

await ctx.session.hook("http.response", (e) => {
  // 기다리지 않는다. 기다리면 응답이 끝날 때까지 스트리밍이 멈춘다
  void e.response.clone().text().then((body) => log(`<<< ${e.response.status}\n${body}`))
})

훅이 끝나야 OpenCode가 응답을 받으므로, 복사본을 끝까지 읽을 때까지 훅이 기다리면 모델 응답이 다 올 때까지 화면에 아무것도 나오지 않습니다. 그래서 기록은 기다리지 않고 따로 흘려보냅니다. 헤더에는 API 키가 들어 있으므로 기록하지 않았습니다.

15.9 생명주기 훅: 입력, 포크, 유휴

session.prompt — 입력이 저장되기 전에

사용자 입력은 inbox(7.3절)에 저장되기 전에 이 훅을 지납니다(session/prompt.ts). 텍스트, 첨부 파일, 언급한 에이전트와 스킬, 전달 방식(steer/queue, 7.4절)을 모두 바꿀 수 있습니다.

// "#123"처럼 이슈 번호를 쓰면 이슈 링크를 덧붙인다
await ctx.session.hook("prompt", (e) => {
  const m = e.prompt.text?.match(/#(\d+)/)
  if (m) e.prompt.text += `\n\n(참고: https://tracker.example.com/issues/${m[1]})`
})

session.fork — 포크된 세션에 알리기

7.7절에서 보았듯 /fork는 대화만 복사하고, 파일과 백그라운드 작업은 원본과 공유하거나 원본에 남겨 둡니다. 모델은 이 사실을 모르면 원본의 서브에이전트 결과를 기다리거나 원본이 고치던 파일을 덮어쓸 수 있습니다.

내장 fork-notice 플러그인은 이 훅에서 포크된 세션에 <fork-notice> 안내문을 넣어 둡니다(plugin/fork-notice.ts). 내용을 요약하면 넷입니다.

  • 포크 이전에 시작한 작업은 원본의 것이니 기다리거나 다시 하지 말 것
  • 파일·브랜치·외부 서비스는 원본과 공유되니, 원본이 하던 것을 바꾸기 전에 현재 상태를 확인하고 새 브랜치나 워크트리로 갈라질 것
  • 새 작업은 평소대로 할 것
  • 어느 쪽이 해야 할지 애매하면 물어볼 것

이 안내문은 resume: false로 넣습니다. 그래서 포크만 했을 때 모델이 저절로 돌기 시작하지는 않고, 사용자가 다음 메시지를 보낼 때 함께 읽힙니다.

session.experimental.idle — 멈추려는 세션을 붙잡기

8.7절의 루프에서 모델이 도구 호출 없이 답을 끝내고 기다리는 입력도 없으면, 세션은 "할 일 끝"으로 보고 유휴 상태로 갑니다. 이 훅은 바로 그 직전에 불립니다(session/runner/llm.ts). 퇴근하려는 직원을 문 앞에서 붙잡고 "이것 하나만 더"라고 말할 기회입니다.

훅이 ctx.session.synthetic(...)으로 입력을 넣으면, 세션은 유휴로 가지 않고 같은 실행 안에서 다음 턴을 시작합니다. 같은 실행이므로 실행 클레임(7.6절)도 유지됩니다. 그래서 이 루프가 도는 중에 서버가 재시작되면 재시작 복구가 이어서 돌립니다.

// 테스트가 통과할 때까지 최대 5번 더 시킨다
const rounds = new Map<string, number>()
await ctx.session.hook("experimental.idle", async (e) => {
  // 자기 서브에이전트가 아직 돌고 있으면 기다린다 (끝나면 훅이 다시 불림)
  if (e.background.some((w) => w.kind === "subagent" && w.sessionID === e.sessionID)) return
  const n = rounds.get(e.sessionID) ?? 0
  if (n >= 5) return                          // ← 상한이 없으면 영원히 돈다
  try {
    if (await testsPass()) return             // 목표 달성: 쉬게 둔다
    rounds.set(e.sessionID, n + 1)
    await ctx.session.synthetic({ sessionID: e.sessionID, text: "테스트가 아직 실패합니다. 원인을 찾아 고치십시오." })
  } catch (err) {
    console.error(err)                        // ← 예외를 던지면 실행 전체가 실패한다
  }
})

testsPass()는 설명용 함수입니다. 구조는 플러그인 README의 idle 예제를 따랐습니다.

이 예제는 모델이 "다 했다"며 멈추려 할 때 테스트로 정말 끝났는지 확인하고, 아직 실패하면 다시 일을 시킵니다. 같은 작업을 처음부터 다시 하는 것은 아닙니다. 모델은 그때까지의 대화를 그대로 이어 받아 실패 원인만 고칩니다. 예를 들어 "로그인 실패 시 에러 메시지를 한국어로 바꿔 줘"라고 요청했다면 다음처럼 움직입니다.

  1. 모델이 edit로 메시지를 고치고 "수정했습니다"라고 답한 뒤 도구 호출 없이 끝냅니다. 기다리는 입력도 없으므로 유휴 직전에 훅이 불립니다.
  2. testsPass()가 실패합니다. 기존 테스트가 옛 영어 메시지를 기대하고 있었기 때문입니다. 훅은 rounds를 1로 올리고 "테스트가 아직 실패합니다…"를 합성 입력으로 넣습니다.
  3. 세션은 유휴로 가지 않고 다음 턴을 시작합니다. 모델은 이 메시지를 읽고 실패 원인을 찾아 테스트의 기대 문자열을 고칩니다. 턴이 끝나면 훅이 다시 불립니다.
  4. 테스트가 통과하면 훅은 그냥 return하고 세션은 유휴로 갑니다. 다섯 번을 다시 시켜도 계속 실패하면 거기서 멈추고 사용자에게 넘깁니다.

중간에 모델이 서브에이전트에게 실패 분석을 맡겼다면 첫 줄 검사에 걸려 훅은 그냥 돌아갑니다. 서브에이전트가 끝나면 그 알림이 세션을 깨우고, 훅이 다시 불려 판정을 이어 갑니다.

  • 불리지 않는 경우: 사용자가 중단했을 때, 실행이 실패했을 때, 그리고 수동 압축처럼 모델을 부르지 않은 실행 뒤
  • background: 아직 돌고 있는 백그라운드 셸·서브에이전트·이미지 생성의 목록(7.7절의 SessionBackground.outstanding)
  • 기다리는 법: 세션 자신의 셸이나 서브에이전트가 끝나면 그 알림이 세션을 깨우고 훅도 다시 불립니다. 그러니 기다릴 일이 있으면 그냥 return하면 됩니다. 반면 자식 세션이 남긴 셸은 자식을 깨우므로, 목록에 보여도 참고용일 뿐입니다.
  • 상한은 직접: 매번 입력을 넣는 훅은 끝나지 않습니다. 반복 횟수 상한은 플러그인이 정해야 합니다.

이 훅을 직접 쓰기 전에 내장 /goal 명령으로 충분한지 먼저 확인하십시오. /goal이 바로 이 훅으로 만든 "목표 달성까지 계속" 기능이고, 위 예제보다 훨씬 꼼꼼한 상한과 판정을 갖추고 있습니다(15.12절의 🛠 상자).

idle 훅에서 서브에이전트를 꼭 띄우기

위의 합성 입력은 모델에게 일을 "부탁"할 뿐입니다. 서브에이전트를 띄울지도 모델이 정합니다. 멈출 때마다 리뷰어에게 변경을 검토시키는 것처럼 반드시 띄워야 한다면 방법이 달라집니다. 외부 플러그인에는 서브에이전트를 직접 만드는 API가 없습니다. 실제로 서브에이전트를 띄우는 SubagentJob 서비스는 subagent 도구와 명령 플러그인 같은 내장 플러그인에만 주어집니다(plugin/internal.ts). 대신 길이 하나 열려 있습니다. subagent: true인 슬래시 명령(13.6절)을 훅 안에서 ctx.session.command로 실행하는 것입니다. 명령 플러그인이 자식 세션을 만들고 그것을 백그라운드 작업으로 등록하므로, 모델이 subagent 도구를 부른 것과 같은 서브에이전트가 됩니다(config/plugin/command.ts).

.opencode/commands/review-bg.md---
description: 변경 검토
agent: reviewer
subagent: true
---
커밋되지 않은 변경을 검토하고, 고쳐야 할 문제만 짧게 보고하십시오.
// 세션이 멈추려 할 때마다 리뷰어를 띄운다 (세션당 최대 3번)
const reviews = new Map<string, number>()
await ctx.session.hook("experimental.idle", async (e) => {
  try {
    // 이 훅은 서브에이전트 세션이 멈출 때도 불린다. 최상위 세션에서만 띄운다
    if ((await ctx.session.get({ sessionID: e.sessionID })).parentID) return
    // 이미 띄운 리뷰어가 돌고 있으면 기다린다 (끝나면 훅이 다시 불림)

    const n = reviews.get(e.sessionID) ?? 0

이벤트 필드와 command 입력(sessionID, name, text)은 packages/plugin/src/promise/session.ts와 생성된 클라이언트의 타입을 따랐습니다. 소스로 맞춘 설명용 코드이며 실행해 확인하지는 않았습니다.

흐름은 이렇습니다. 모델이 일을 마치고 멈추려 하면 훅이 리뷰어를 띄우고 그냥 돌아갑니다. 부모 세션에는 넣은 입력이 없으므로 유휴로 갑니다. 리뷰어는 백그라운드에서 돌다가 끝나면 부모 inbox에 <subagent> 보고를 넣습니다(12.5절). 그 보고가 부모를 깨우고, 모델은 지적된 문제를 고친 뒤 다시 멈추려 합니다. 그러면 훅이 다시 불리고 두 번째 리뷰어가 뜹니다. 세 번째 리뷰 뒤에는 상한에 걸려 멈춥니다.

  • 최상위 세션 확인이 필요한 이유: idle 훅은 세션을 가리지 않습니다. 리뷰어 세션이 끝날 때도 불리므로, 이 확인이 없으면 리뷰어가 또 리뷰어를 띄웁니다. 명령으로 띄우는 서브에이전트에는 subagent 도구의 깊이 제한(experimental.subagent_depth)과 권한 확인이 적용되지 않으니 막는 일은 플러그인 몫입니다. 내장 goal 플러그인도 같은 이유로 부모를 거슬러 올라가 확인합니다(plugin/goal.ts).
  • 왜 ctx.session.create로 직접 만들지 않나: create({ parentID })와 prompt로 만든 자식 세션도 끝나면 부모에게 보고하고, 서버가 재시작되면 이어서 돕니다. 하지만 백그라운드 작업으로 등록되지 않습니다. 그래서 위 예제의 e.background 검사에 잡히지 않고, 작업 목록에도 나오지 않습니다. 돌고 있는지 확인하는 일까지 플러그인이 직접 떠안게 됩니다.
  • 왜 idle 훅인가: tool.execute.after에서도 명령을 실행할 수 있습니다. 하지만 그 훅은 도구 호출마다 불리므로 서브에이전트가 쏟아집니다. 한 차례 일이 끝난 뒤 맡길 검토나 검증이라면 멈추기 직전이 맞는 자리입니다.

tool.execute.before — 문 앞에서 막거나 고치기

await ctx.tool.hook("execute.before", (e) => {
  const command = String((e.input as { command?: unknown })?.command ?? "")

던진 오류 메시지는 모델에게 도구 결과로 전달됩니다. 그래서 "안 됩니다"만 쓰지 말고 대신 무엇을 하라까지 쓰는 것이 좋습니다. 모델은 그 문장을 읽고 스테이징 DB로 다시 시도합니다.

내장 tool.input.repair 플러그인이 이 훅의 좋은 예입니다. 모델이 다른 하네스에서 배운 습관대로 bash라는 도구를 부르면, event.tool을 shell로 바꿔 실행되게 하고 입력도 스키마에 맞게 고칩니다. 그리고 tool.execute.after에서 "bash라는 도구는 없어서 shell로 실행했으니 다음엔 직접 부르라"는 문장을 결과에 덧붙입니다. before와 after가 호출 ID로 짝을 이루는 패턴입니다.

tool.execute.after — 결과를 다듬어 모델을 가르치기

이미 실행된 것을 되돌릴 수는 없지만, 모델이 받는 결과 문장은 바꿀 수 있습니다. 내장 Plan 플러그인은 Plan 에이전트가 계획 디렉터리 밖을 편집하다 권한에 막히면, 일반 권한 오류 대신 "Plan 디렉터리 밖의 파일은 수정할 수 없다"는 구체적인 메시지로 바꿉니다(plugin/plan.ts). 오류 메시지가 구체적일수록 모델은 같은 실수를 덜 반복합니다.

permission.evaluate — 판정을 바꾸기

// git push는 규칙상 허용이어도 항상 사람에게 묻는다
await ctx.permission.hook("evaluate", (e) => {
  if (e.action === "shell" && e.resources.some((r) => r.startsWith("git push")) && e.effect === "allow")
    e.effect = "ask"
})

셸 도구의 action은 shell, resources는 파싱된 명령 텍스트입니다(11.3절).

이 훅이 불리는 순서를 정확히 알아야 합니다.

  1. 설정 규칙(에이전트·세션 권한)에 deny가 하나라도 걸리면 바로 거부합니다. 훅은 불리지 않습니다.
  2. 그렇지 않으면 저장된 "항상 허용" 규칙까지 반영해 allow 또는 ask로 판정하고, 그 값을 훅에 넘깁니다.
  3. 훅들이 순서대로 고칩니다. 관리형 정책(11.6절)의 tool.use 거부는 정책 플러그인이 맨 마지막에 적용합니다.
  4. 훅이 남긴 값이 ask인데 지켜보는 사람이 없는 무인 실행이면 "승인이 필요한데 승인할 사람이 없다"는 사유로 거부됩니다.

shell.create.before — 실행 환경 다듬기

// 모든 셸을 비대화형으로: 페이저나 확인 프롬프트에서 멈추지 않게
await ctx.shell.hook("create.before", (e) => {
  e.env.CI = "1"
  e.env.GIT_PAGER = "cat"
})

이 훅은 셸 서비스가 만드는 모든 프로세스에 걸립니다. 모델의 셸 도구뿐 아니라 사용자가 직접 입력한 ! 명령도 포함됩니다. 환경 변수를 지우면 데몬 경로에서도 지워진 채로 유지됩니다. 실패할 통로가 없으므로 막는 용도로는 쓸 수 없습니다.

명령 자체를 고치는 예도 있습니다. Windows에서 셸 출력의 한글이 깨지는 경우입니다. OpenCode는 셸 출력을 UTF-8로 읽는데(shell.ts의 output), PowerShell은 콘솔 코드 페이지(한국어 Windows는 CP949)로 내보내기 때문입니다. 게다가 PowerShell은 -NoProfile로 실행되므로(shell/select.ts의 args) $PROFILE에 넣은 인코딩 설정도 적용되지 않습니다. 그래서 이 훅에서 명령 앞에 인코딩 설정을 붙입니다.

// Windows PowerShell에서 한글이 깨지지 않게: 출력 인코딩을 UTF-8(BOM 없음)로 맞춘다
await ctx.shell.hook("create.before", (e) => {
  if (!/(^|[\\/])(pwsh|powershell)(\.exe)?$/i.test(e.shell)) return
  e.command =
    "[Console]::OutputEncoding = [Text.UTF8Encoding]::new($false); " +
    "$OutputEncoding = [Console]::OutputEncoding; " +
    e.command
  e.env.PYTHONUTF8 = "1" // 파이썬은 콘솔 설정과 별개로 UTF-8 모드를 켜야 한다
})

e.shell에는 pwsh.exe까지 붙은 전체 경로가 오므로 파일 이름으로 PowerShell인지 가립니다. [Console]::OutputEncoding은 PowerShell이 내보내는 출력과 외부 프로그램의 출력을 읽는 인코딩을, $OutputEncoding은 외부 프로그램에 파이프로 넘기는 인코딩을 정합니다. 권한 판정은 이 훅보다 먼저 끝나므로(그림 15-4), 앞에 붙인 문장 때문에 권한 규칙 매칭이 달라지지 않습니다.

막으려면 어디서 막아야 하나

"위험한 명령을 막고 싶다"는 요구에는 세 가지 길이 있고, 위에서부터 고르면 됩니다.

  1. 권한 규칙(11.1절): 첫 선택입니다. 선언적이고, 사용자가 화면에서 보고 승인할 수 있으며, 플러그인이 필요 없습니다.
  2. tool.execute.before에서 던지기: 규칙의 와일드카드로 표현하기 어려운 조건일 때 씁니다. 예를 들어 입력의 여러 필드를 조합해 판단해야 하는 경우입니다. 거부 사유가 모델에게 그대로 전달됩니다.
  3. permission.evaluate: 판정을 "사람에게 묻기(ask)"로 바꾸고 싶을 때 씁니다.

shell.create.before는 막는 용도가 아니라 실행 환경을 다듬는 용도입니다.

15.11 OpenCode는 자기 기능을 훅으로 만든다

훅은 외부 플러그인을 위한 부가 장치가 아닙니다. OpenCode의 상당 부분이 같은 훅 API를 쓰는 내장 플러그인으로 만들어져 있습니다. 이것이 설계의 시험대 역할을 합니다. 내장 기능을 훅만으로 만들 수 있다면, 같은 일을 외부 플러그인도 할 수 있다는 뜻이기 때문입니다.

이렇게 씁니다 — 끝날 때까지 맡기기: /goal

폭주를 막는 상한이 여럿 있습니다(plugin/goal.ts).

  • 최대 50라운드에서 멈춥니다.
  • 같은 사유가 반복되거나 도구를 쓰지 않은 라운드가 3번 이어지면 "진척 없음"으로 멈춥니다.
  • 백그라운드 작업을 30분 넘게 기다리면 멈춥니다.
  • 사용자가 중단하거나, 실행이 실패하거나, 서버가 재시작되면 멈춥니다.

예. /goal npm test가 모두 통과하고 lint 경고가 0이 되게 해처럼 확인할 수 있는 완료 조건을 주십시오. "코드를 좋게 만들어"처럼 끝이 없는 목표는 심사가 계속 continue를 내다가 진척 없음이나 50라운드 한도에서 멈추고, 그동안 토큰만 씁니다.

도는 중에 방향을 바꾸고 싶으면 그냥 메시지를 보내면 됩니다. steer로 끼어들어 다음 경계에서 반영됩니다(7.4절). 목표 자체를 멈추려면 /goal pause를 쓰십시오.

이렇게 씁니다 — 훅 플러그인 만들기

1단계: 자리 만들기. 프로젝트에 .opencode/plugins/team-hooks/ 디렉터리를 만들고 그 안에 index.ts를 둡니다. .opencode/plugins/ 바로 아래의 디렉터리와 .ts·.js 파일은 자동으로 로드되고, 고치면 핫 리로드됩니다(plugin/source-directory.ts). 설정의 plugins 항목으로 로컬 경로를 지정할 때는 파일이 아니라 디렉터리여야 합니다(15.2절).

2단계: 필요한 훅만 골라 넣기. 이 장의 예제들을 모으면 이런 모양입니다.

.opencode/plugins/team-hooks/index.tsimport { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "team-hooks",
  setup: async (ctx) => {
    // ① 운영 DB를 건드리는 셸 명령은 거부한다 (모델에게 사유와 대안이 전달된다)
    await ctx.tool.hook("execute.before", (e) => {
      const command = String((e.input as { command?: unknown })?.command ?? "")
      if (e.tool === "shell" && /psql\s.*prod/.test(command))
        throw new Error("운영 DB 접속은 금지입니다. 스테이징(-h staging-db)을 쓰십시오.")
    })

    // ② git push는 규칙상 허용이어도 사람에게 묻는다
    await ctx.permission.hook("evaluate", (e) => {
      if (e.action === "shell" && e.resources.some((r) => r.startsWith("git push")) && e.effect === "allow")
        e.effect = "ask"
    })

    // ③ 모든 셸 프로세스를 비대화형으로
    await ctx.shell.hook("create.before", (e) => {
      e.env.CI = "1"
      e.env.GIT_PAGER = "cat"
    })

    // ④ 재시도할 수 있는 오류라도 3번째부터는 포기한다
    await ctx.session.hook("retry", (e) => {
      if (e.attempt >= 3) e.decision = { retry: false }
    })
  },
})

이벤트 필드는 packages/plugin/src/effect/{tool,permission,shell,session}.ts의 타입을 따랐습니다. 명령 패턴은 설명용입니다.

3단계: 확인하기. 플러그인이 로드되지 않았거나 setup에서 실패했다면 /plugins의 Server 구역에서 오류를 볼 수 있습니다(15.2절의 🛠 상자). 훅이 실제로 불렸는지는 훅 안에 로그를 남겨 확인하는 것이 가장 빠릅니다. 위 ①이라면 모델에게 "psql로 prod에 접속해 봐"라고 시켜 거부 메시지가 돌아오는지 보면 됩니다.

훅을 쓸 때 빠지기 쉬운 함정
  • 예외 하나로 하던 일이 끝납니다. tool.execute.before 외의 훅에서 던진 예외는 실행 전체를 실패시킵니다(15.5절). 네트워크 호출이 들어가는 훅은 반드시 try/catch로 감싸십시오.
  • context 훅에서 앞쪽을 바꾸면 비용이 오릅니다. 시각, 랜덤 값, 매번 달라지는 문장을 system 앞쪽에 넣으면 매 스텝 캐시가 깨집니다(15.7절).
  • 훅은 생각보다 자주 불립니다. context 훅은 매 스텝, 도구 훅은 도구 호출마다 불립니다. 무거운 작업을 넣으면 모든 응답이 그만큼 느려집니다. 미리 계산할 수 있는 것은 setup에서 해 두십시오.
  • idle 루프에는 상한을 두십시오. 조건 없이 입력을 넣으면 끝나지 않습니다. 내장 goal 플러그인도 라운드·정체·대기 시간 세 가지 상한을 둡니다.
  • idle 훅은 서브에이전트 세션에서도 불립니다. 최상위 세션에서만 동작하게 하려면 parentID를 확인하십시오. 특히 훅에서 서브에이전트를 띄운다면 이 확인이 없을 때 서브에이전트가 끝없이 중첩됩니다(15.9절).
  • context에서 고친 내용은 남지 않습니다. 화면과 기록에는 원래 내용이 보입니다. 기록에 남겨야 하면 prompt 훅이나 ctx.session.synthetic을 쓰십시오.
  • 새 도구는 훅으로 못 만듭니다. context 훅의 tools에 새 항목을 넣으면 버려집니다. ctx.tool.transform을 쓰십시오.
  • experimental.이 붙은 훅(model.resolve, ws.*, idle)은 이름과 모양이 바뀔 수 있다고 명시되어 있습니다. 버전을 올릴 때 확인하십시오.
