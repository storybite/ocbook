9장 컨텍스트 엔지니어링 — 프롬프트 조립, 지침, 압축

모델이 보는 것은 결국 한 번의 요청입니다. 이 장은 그 요청이 어떻게 만들어지는지, 그리고 대화가 길어질 때 무엇을 남기고 무엇을 요약하는지를 다룹니다. 모든 설계를 관통하는 키워드는 프롬프트 캐시입니다.

9.1 왜 캐시가 설계를 지배하는가

LLM 프로바이더는 요청의 앞부분(접두, prefix)이 이전 요청과 바이트 단위로 같으면 그 부분을 캐시에서 읽어 비용과 지연을 크게 줄여 줍니다. 에이전트는 스텝마다 거의 같은 대화를 반복 전송하므로 캐시 적중 여부가 비용을 몇 배씩 좌우합니다. 그래서 V2는 다음 원칙을 지킵니다.

  • 자주 바뀌지 않는 것을 앞에, 자주 바뀌는 것을 뒤에 둡니다.
  • 시스템 프롬프트는 한 "에포크" 동안 바이트 단위로 고정합니다.
  • 바뀐 내용은 앞부분을 고치지 않고 대화 중간에 "변경 알림"으로 덧붙입니다.
  • 도구 정의 순서와 JSON Schema도 안정적으로 유지합니다(이름순 정렬, 정수 범위 제거 등).

이렇게 씁니다 — 캐시를 깨지 않는 습관

캐시는 "앞부분이 똑같을 때만" 재사용됩니다. 그래서 세션 중간에 무엇을 바꾸느냐에 따라 비용이 크게 달라집니다. 대화가 10만 토큰쯤 쌓인 세션이라면, 캐시가 깨지는 순간 그 10만 토큰을 다시 정가로 읽게 됩니다.

세션 중간의 변경캐시에 미치는 영향
모델 바꾸기(/models)새로 시작. 프로바이더 캐시는 모델별이라 앞부분을 처음부터 다시 읽음
같은 모델의 추론 단계만 바꾸기(/variants, ctrl+t)Anthropic·OpenAI Responses 경로는 메시지 안의 표지로 바꿔 캐시 유지. 다른 경로는 요청 상단이 바뀌어 깨질 수 있음
build ↔ plan(shift+tab)캐시 유지. 둘은 같은 기본 프롬프트와 같은 도구 목록을 쓰고, 바뀌는 것은 끝쪽에 붙는 진입·이탈 알림 한 줄뿐. 단, 두 에이전트에 다른 모델을 골라 두었다면 '모델 바꾸기'와 같음
그 밖의 에이전트로 바꾸기(/agents)시스템 프롬프트·도구 목록·모델이 다르면 앞부분이 달라져 깨질 가능성이 큼
폴더 이동(/cd)·지침 변경기준선은 그대로, 변화만 델타로 덧붙임 → 대체로 유지(9.5절)

그래서 이렇게 씁니다.

  1. 모델은 세션을 시작할 때 정합니다. 긴 세션 도중에 "더 센 모델로 한 번만"이 필요하면, 세션을 바꾸지 말고 같은 모델의 추론 단계(ctrl+t)를 올려 보십시오.
  2. 모델을 꼭 바꿔야 한다면 먼저 줄입니다. /compact로 이력을 체크포인트 요약으로 줄인 뒤 바꾸면 다시 읽을 양이 작습니다. 또는 /new로 새 세션을 시작하고 필요한 맥락만 전달합니다.
  3. plan과 build는 같은 모델로 둡니다. 둘을 오가도 캐시가 깨지지 않는 것은 요청 앞부분을 이루는 세 가지가 같기 때문입니다.
    • 시스템 프롬프트: build와 plan 모두 자기 프롬프트를 정하지 않아 같은 기본 프롬프트를 씁니다.
    • 도구 목록: plan은 편집을 막지만 편집 도구를 목록에서 빼지는 않습니다. 도구 목록은 "그 도구에 마지막으로 걸리는 규칙이 전부(*)를 막는가"만 보고 도구를 뺍니다. plan의 마지막 edit 규칙은 "계획 폴더는 허용"이라서 edit·write·patch가 목록에 남고, 실행하는 순간 권한 검사에서 막힙니다(11.4절). 이 점이 특히 중요합니다. 기본 프롬프트는 도구 이름 목록으로 만들어지므로, 도구가 하나라도 빠지면 프롬프트까지 달라집니다.
    • 모델: 둘 다 모델을 지정하지 않아 세션에서 고른 모델을 그대로 씁니다. 그런데 앱은 에이전트마다 마지막 모델을 따로 기억합니다(12.2절). plan에 빠른 모델을 골라 두면 이 조건이 깨져서 전환할 때마다 모델 바꾸기와 같은 비용이 듭니다.
    그러니 모델만 맞춰 두면, 계획을 다듬다가 구현하고 다시 계획으로 돌아가도 캐시 걱정이 없습니다.

9.2 baseTranscript: 요청 조립

  • system[0]: 에이전트가 누구이고 어떻게 일하는지 정하는 프롬프트입니다. 에이전트에 system이 있으면 그것을 씁니다(예: explore의 읽기 전용 탐색 프롬프트). 없으면 SessionSystemPrompt.make(toolNames)가 기본 프롬프트 runner/prompt/system.txt를 만듭니다. 이때 toolNames는 ${OPENCODE_TOOL_GUIDANCE} 자리에 실제로 쓸 수 있는 도구(shell·write·edit 등)의 사용법만 골라 넣는 데 씁니다. 에이전트 프롬프트는 기본 프롬프트에 덧붙지 않고 그 자리를 대체합니다.
  • system[1]: Instructions.join(initial)로 만든 지침 에포크의 베이스라인입니다. 전역·프로젝트 AGENTS.md, instructions 파일, 스킬 목록, MCP 지침 등을 합친 내용이며 세션 첫 턴에 고정됩니다. 세션 도중 지침이 바뀌면 system[1]은 그대로 두고 대화 중간에 시스템 메시지로 알립니다. system[1]은 압축 뒤 새 에포크가 시작될 때만 다시 만듭니다.

prepare 단계(모든 요청 공통)

조립이 끝난 요청은 모델에 보내기 직전에 아래 네 단계를 거치며 다듬어집니다. 주 대화든 압축 요약이든 제목 생성이든 같은 길을 지납니다.

  1. 도구 목록 다듬기: 플러그인 훅이 모델에게 보낼 도구 목록을 고칠 수 있습니다. 훅에는 원본이 아니라 깊은 복사본(deep copy)을 넘기므로, 훅이 무엇을 고쳐도 여러 스텝·세션이 함께 쓰는 원본 정의는 그대로 남습니다. 훅이 할 수 있는 일은 이미 있는 도구의 이름·설명을 바꾸거나 도구를 빼는 것까지입니다. 목록에 없던 도구를 훅이 새로 끼워 넣으면 그 정의는 버립니다. 실제로 어떤 경우에 고치는지는 절 끝의 상자 '도구 목록은 왜 고칠까요?'에서 예로 봅니다.
  2. 답변 길이 상한 정하기: 모델이 이번 답변에 쓸 수 있는 출력 토큰 수를 정합니다. 기본은 모델의 출력 한도이지만, 컨텍스트 창에 남은 자리가 그보다 좁으면 남은 자리에 맞춰 줄입니다. 예를 들어 창이 200k인데 입력이 이미 190k를 차지했다면, 모델의 출력 한도가 32k라도 남은 10k 안쪽으로 줄여 요청합니다. 그래야 창이 넘치지 않습니다. 이 계산은 주 대화와 압축 요청에서만 하고, 제목·generate 요청은 프로바이더 기본값을 씁니다. 계산식은 아래 코드에 있습니다.
  3. 플러그인 훅에 차례로 맡기기: 먼저 요청 종류에 맞는 훅 하나가 요청을 고칩니다. 종류에 따라 session.context(주 대화), compaction(압축 요약), generate, title(제목 생성) 가운데 하나입니다. 다음으로 session.model.request 훅이 요청을 보낼 주소(baseURL)와 헤더를 바꿀 수 있습니다. 필요하면 더 아래에서 http.request/response 훅으로 실제 HTTP 요청·응답을, experimental.ws.* 훅으로 WebSocket 전송을 들여다볼 수도 있습니다.
  4. 마지막 정리: 훅이 참고할 수 있던 저장용 메타데이터를 지워 모델 쪽으로는 보내지 않습니다. 모델이 읽지 못하는 미디어(예: 텍스트 전용 모델에 보낸 이미지)는 빼 버리지 않고 "ERROR: Cannot read …"라는 글로 바꿉니다. 그러면 요청이 실패하지 않고, 모델도 그 자리에 읽지 못한 파일이 있었다는 것을 알고 사용자에게 알릴 수 있습니다. 이미지가 쌓여 총량이 너무 커지면 가장 오래된 이미지부터 지웁니다(아래 표의 25 MiB / 15 MiB).

그림 9-2 주 대화 요청 하나가 prepare 단계를 지나는 순서

그림은 주 대화 요청을 예로 들었습니다. 위 목록은 훅(3번)과 정리(4번)를 나눠 적었지만, 실제 코드는 요청 종류별 훅을 부른 직후에 정리를 하고 그다음에 session.model.request 훅을 부릅니다. 훅 지점에 등록된 처리기는 등록 순서대로 불리고, 뒤 처리기는 앞 처리기가 고친 초안을 이어받습니다. 등록된 처리기가 없으면 초안은 그대로 나갑니다.

'context 함수'가 아니라 '훅 지점'인 까닭 — "안녕?" 요청 하나로 보기

여기서 말하는 코어는 서버 안에서 실제 일을 하는 엔진 본체, 곧 packages/core 패키지입니다(3.3절). 세션 실행, 모델 요청 조립, 도구·권한, 플러그인 관리, 저장이 모두 여기에 있고, 모델 요청을 만드는 코드는 session/model-request.ts입니다. 내장 플러그인도 같은 패키지(packages/core/src/plugin/)에 들어 있지만, 엔진에 직접 붙지 않고 사용자 플러그인과 똑같이 훅 지점에 훅(처리기)을 거는 방식으로 붙습니다.

사용자가 "안녕?"이라고만 보내도 이 길을 그대로 지납니다.

  1. 코어가 "안녕?"을 담은 요청 초안을 만듭니다. 초안에는 시스템 프롬프트, 대화, 도구 목록이 들어 있습니다.
  2. 모델에 보내기 직전에 코어는 trigger("session", "context", 초안) 한 줄만 실행합니다. "이 초안을 고칠 처리기가 걸려 있으면 순서대로 나오라"는 뜻입니다.
  3. 걸려 있는 처리기들이 등록된 순서대로 같은 초안을 받아 고칩니다. 예를 들어 내장 IdentityPlugin은 모델 이름·프로바이더 ID·모델 ID를 담은 '# Your Model' 블록을 시스템 프롬프트에 넣습니다. 그 뒤에 사용자 플러그인이 있다면 "답은 한국어로" 같은 문장을 덧붙일 수도 있습니다(설명을 위해 가정한 예입니다).
  4. 처리기가 모두 끝나면 trigger가 다 고쳐진 초안을 코어에 돌려줍니다. 3번 예라면 '# Your Model' 블록(사용자 플러그인이 있다면 "답은 한국어로" 문장까지)이 들어간 초안입니다. 코어는 이 초안을 앞에서 본 '마지막 정리'를 거쳐 모델에 보냅니다. 걸린 처리기가 하나도 없으면 아무도 고치지 않았으므로 1번에서 만든 초안이 그대로 나갑니다.

})

trigger(domain, name, event)의 세 인자는 차례로 훅이 속한 영역(aisdk·session·permission·shell·tool 중 하나), 그 영역 안에서 쓰는 훅 지점의 이름, 처리기들에게 차례로 넘길 객체입니다. 코드는 domain과 name을 이어 "session.context" 같은 훅 지점 이름을 만들고, 그 이름으로 처리기 목록을 찾습니다. 책이 훅 지점을 도메인.이름 형식으로 부르는 것도 이 때문입니다. 그래서 위 코드는 이렇게 읽으면 됩니다. trigger("session", "context", 초안)은 session.context 훅 지점에 걸린 훅(처리기)들을 등록 순서대로 하나씩 실행합니다. 처리기들은 모두 같은 초안 객체를 받아 직접 고치고, trigger는 다 고쳐진 그 객체를 돌려줍니다.

이 지점을 'context 함수'라고 부르지 않는 이유는 2번에 있습니다. 코어 안에는 초안을 고치는 정해진 함수가 없습니다. 위 코드처럼 코어는 걸려 있는 처리기를 차례로 부를 뿐이고, 실제로 고치는 함수는 모두 플러그인이 바깥에서 걸어 둔 것입니다. 몇 개가 걸려 있는지도 그때그때 달라서 0개일 수도 여러 개일 수도 있습니다. 덕분에 기능을 더할 때 코어 코드를 고칠 필요 없이 함수만 하나 더 걸면 됩니다. 이렇게 걸어 두는 함수, 곧 처리기 하나하나를 훅(hook)이라고 부르고, 훅을 걸 수 있도록 코어가 정해 둔 자리를 훅 지점이라고 부릅니다(15.4절). session.context는 처리기가 아니라 처리기들이 걸리는 위치, 곧 훅 지점의 이름입니다. 정리하면 코어가 정해 둔 훅 지점에 플러그인이 훅(처리기)들을 겁니다. 여기서 '훅을 건다'는 말은 실행이 아니라 hook(...)으로 등록한다는 뜻이고, 실제 실행은 코어가 그 지점에 이르러 trigger로 부르는 발동입니다. 흔히 'session.context 훅'이라고 줄여 부르지만, 정확히는 'session.context 지점에 걸린 훅들'입니다. 또 이 훅들은 6장의 Bus 이벤트에 반응해 도는 것이 아니라, 코어가 요청을 준비하다 이 지점에 이르면 직접 부릅니다. 훅이 변환·이벤트 구독과 어떻게 다른지는 15.4절에서 다룹니다.

9.5 InstructionState: 지침은 값의 델타

이 절의 요점은 세션 도중 AGENTS.md 같은 지침이 바뀌어도 시스템 프롬프트를 다시 쓰지 않고, 바뀐 부분만 대화 중간에 시스템 메시지로 알린다는 것입니다. 첫 턴의 지침은 기준값(베이스라인)이 되어 system[1]에 들어갑니다. 그 뒤에는 스텝마다 지침의 해시를 비교해, 달라졌을 때만 변경분(델타)을 그 시점의 대화에 끼워 넣습니다. 이렇게 하면 프롬프트 앞부분이 그대로 남아 캐시가 깨지지 않습니다. 압축으로 어차피 앞부분을 다시 써야 할 때 그동안의 변경을 새 기준값으로 합칩니다.

그림 9-4 지침 변경의 전달

  • 둘 중 짧은 쪽으로 알립니다. 세션 도중 AGENTS.md가 바뀌면 그 사실을 대화 중간에 시스템 메시지로 모델에게 알립니다. 알리는 방법은 두 가지입니다. 새 내용을 통째로 다시 싣거나(전체 교체), 어떤 줄이 빠지고 더해졌는지만 보여 주는 diff를 보내는 것입니다. OpenCode는 둘 중 더 짧은 쪽을 고릅니다. 긴 파일에서 한두 줄만 고쳤다면 diff를, 거의 전부 바꿨다면 전체 내용을 보내 토큰을 아낍니다.
  • 보낸 글은 완성본 그대로 보관합니다. 모델에게 보낸 변경 안내문은 다 만든 글 그대로 이벤트에 저장합니다("얼린다"). 나중에 다시 만들려면 그때의 지침 파일이 있어야 하는데, 그 파일은 이미 바뀌었거나 사라졌을 수 있기 때문입니다.
  • 읽지 못한 파일은 처음에만 문제가 됩니다. 첫 턴에 기준값을 만들 때 읽지 못한 소스가 있으면 기준값을 만들지 않고 멈춥니다. 기준값이 생긴 뒤에는 읽지 못한 소스를 건너뛰고 마지막으로 저장한 값을 그대로 씁니다.
  • 되돌리면 지침 기록도 되돌립니다. 되돌리기(revert)로 지침 변경 메시지나 기준값의 시작점이 지워지면, 저장된 지침 상태를 지워(rewind) 남은 이력에 맞게 다시 만들게 합니다.
왜 시스템 프롬프트를 고치지 않고 "중간 메시지"로 알릴까요? AGENTS.md 한 줄을 고칠 때마다 system[1]을 다시 만들면 그 뒤의 대화 전체가 캐시에서 빠집니다. 변경을 시간순 위치에 시스템 메시지로 끼우면 앞부분은 그대로라 캐시가 유지되고, 모델은 "언제 규칙이 바뀌었는지"까지 알게 됩니다. 압축으로 어차피 앞부분을 다시 써야 하는 시점에 새 에포크로 합쳐 정리합니다.

9.6 압축(Compaction): 언제, 무엇을 남기나

발동 조건

session/compaction.tsconst calculateCeiling = (limit, buffer) => {
  const window = inputWindow(limit)
  if (window <= 0) return Number.POSITIVE_INFINITY
  const tokens = typeof buffer === "string" ? Math.round((window * Number.parseFloat(buffer)) / 100) : buffer
  if (tokens !== undefined && tokens < window) return window - tokens
  return window - Math.max(Math.floor(window * RESERVE_SHARE), window >= 2 * RESERVE_MIN ? RESERVE_MIN : 0)
}
session/compaction.ts — 유효 입력 창const inputWindow = (limit) =>
  limit.input && limit.context ? Math.min(limit.input, limit.context) : limit.input || limit.context

예를 들어 컨텍스트 창이 200k이고 input 한도가 따로 없는 모델이라면, 창의 15%인 30k가 최소 여유분 16k보다 크므로 30k를 비워 둡니다. 그래서 천장은 170k입니다. 컨텍스트 창이 200k라도 input 한도가 100k라면 실제로 쓸 수 있는 창은 100k입니다. 이때 15%인 15k는 16k보다 작으므로 16k를 비워 두고, 천장은 84k가 됩니다. 설정에서 compaction.buffer를 정해도 이 실제 입력 창을 기준으로 계산합니다.

압축할지는 두 값을 더해서 정합니다. 하나는 실제 토큰 수로, 마지막 모델 응답 때 프로바이더가 알려 준 사용량(입력, 캐시 읽기·쓰기, 출력, 추론)입니다. 다른 하나는 예상 토큰 수로, 그 응답 뒤에 새로 붙어 프로바이더가 아직 세지 않은 도구 결과나 메시지의 양입니다. 이 값은 실제로 센 것이 아니라 글자 4개를 토큰 1개로 치는 추측값입니다(util/token.ts). 소스에는 왜 4인지 적혀 있지 않은데, 영어 글에서 토큰 하나가 대략 4글자라는 경험칙을 따른 것으로 보입니다. 두 값의 합이 천장에 닿거나 넘으면 자동으로 압축합니다.

예: 200k 창 모델의 천장은 170k입니다. 직전 응답에서 프로바이더가 160k를 썼다고 알려 왔습니다. 그 뒤 모델이 파일을 읽어 48,000자짜리 결과를 받으면 글자 4개를 토큰 1개로 쳐서 48,000 ÷ 4 = 약 12k로 추측합니다. 실제 토큰 수는 이와 다를 수 있습니다. 160k + 12k = 172k로 천장 170k를 넘으므로, 다음 요청을 보내기 전에 먼저 압축합니다.

  • 요약 요청은 평소 요청을 그대로 보내고 끝에 요약 지시만 붙입니다. 그래서 요약 자체가 프롬프트 캐시를 재사용합니다. 바로 위에서 요약에서 뺀다고 한 AGENTS.md와 환경 정보도 이 요청에는 그대로 들어 있습니다. 모델은 이것들을 입력으로 보기는 하지만, 요약 지시에 따라 요약(출력)에는 옮겨 적지 않습니다. 이것들을 일부러 빼고 보내면 요청 앞부분이 평소와 달라져 캐시를 다시 쓸 수 없습니다.
  • 응답에 템플릿 헤딩이 하나도 없으면 한 번 재촉(NUDGE)하고, 재응답에도 하나도 없으면 실패합니다. 검사는 "헤딩 중 하나라도 있는가"뿐이라 요약의 완전성까지 보장하지는 않습니다(템플릿도 해당 없는 절은 생략 가능하다고 안내).
  • 원본 전체 이력은 DB에 영속 보존됩니다. 압축은 "활성 이력"만 다시 만듭니다.

네이티브 압축과 선계산

  • model.compaction.type === "native"면 프로바이더 자체 압축을 씁니다. "trigger" 방식은 체크포인트를 받아 최근 사용자 메시지를 앞에 붙이고, "endpoint" 방식은 프로바이더가 대체 창을 돌려줍니다. 결과는 암호화된 항목이라 같은 모델에서만 재생됩니다.
  • 선계산(precompute, 기본 꺼짐): 천장에 가까워지면 백그라운드로 요약해 두되 적용하지 않고 보관합니다. 실제로 필요할 때까지 캐시를 깨지 않기 위함입니다.
  • 모든 압축 호출 비용은 실패·중단이어도 즉시 UsageRecorded{source:"compaction"}로 청구됩니다.
왜 "최근 원문 + 요약"일까요? 요약만 남기면 모델은 방금 하던 일의 세부(정확한 오류 메시지, 마지막 diff)를 잃습니다. 원문만 남기면 창이 넘칩니다. 최근 15k 토큰은 "지금 손에 쥔 작업", 요약은 "여기까지 온 맥락"을 담당합니다. 사람이 인수인계할 때 "지금까지 요약 + 방금 하던 화면"을 넘기는 것과 같습니다.
이렇게 씁니다 — 언제 /compact, 언제 /new인가

자동 압축은 천장을 넘으면 알아서 일어나지만, 직접 시점을 고르면 더 잘 다룰 수 있습니다. /compact(ctrl+x c)는 지금까지의 대화를 위 그림처럼 구조화 요약 + 최근 약 15k 토큰 원문으로 바꿉니다. 요약에는 목표, 요구 사항, 결정, 작업 상태, 다음 할 일, 관련 파일, 중요한 맥락이 정해진 틀로 들어갑니다.

전혀 다른 일을 시작한다/new이전 맥락은 오히려 방해. 요약 비용도 들지 않음

예 — 큰 기능을 단계별로 만들기. 1단계 "DB 스키마 추가"가 끝나 테스트까지 통과했습니다. 여기서 /compact를 하면 요약에 "스키마 추가 완료, 마이그레이션 파일은 db/migrations/0012.sql" 같은 내용이 남고, 2단계 "API 구현"을 가벼운 맥락으로 시작할 수 있습니다. 에이전트가 일하는 중에 눌러도 됩니다. 압축은 inbox에 제어 항목으로 들어가 다음 스텝 경계에서 실행됩니다.

알아 둘 것
  • 모델 호출이 일어납니다. 요약을 만드는 데 비용이 들고(틀을 벗어나면 한 번 더 재시도), 사용량에 "compaction"으로 기록됩니다. compaction 에이전트에 모델을 정해 두면 그 모델이, 아니면 세션 모델이 요약합니다.
  • TUI에서 고른 모델이 세션 모델로 확정됩니다. /compact는 압축 전에 현재 선택한 모델로 세션 모델을 바꿉니다.
  • 되돌리기가 확정됩니다. /undo로 숨겨 둔 메시지가 있으면, 압축하는 순간 그 메시지들이 영구 삭제되어 /redo를 할 수 없게 됩니다(11.9절).
  • 자동 압축을 꺼 두어도 /compact는 동작합니다. 아직 대화가 없으면 "Nothing to compact yet"이 뜹니다.

9.7 제목·사용량·통계

  • 제목(title.ts): 최대 100자, 컨텍스트 8,000자, 첫 메시지 2,000자. 작은 모델(또는 최소 추론 변형)을 먼저 시도하고 실패하면 주 모델로. Renamed는 "그사이 다른 이벤트가 없었을 때만" 커밋되어 사용자의 수동 이름 변경이 항상 이깁니다.
  • 사용량(usage.ts): 프로바이더가 보고한 비용을 우선합니다("보고된 0도 권위 있음"). 없으면 카탈로그 가격으로 계산하며 컨텍스트 티어를 고려하고, 추론 토큰은 출력 단가로 청구합니다.
  • 통계(stats.ts): 모델별 스텝·토큰·비용, 도구별 호출·성공·소요 시간. 기본 창 31일. CLI opencode stats가 사용합니다.
"작은 모델"은 어떻게 고르나

모델 크기를 재서 스스로 판단하는 것이 아니라 정해진 순서를 따릅니다(session/context.ts의 selectTitle).

  1. 직접 지정: title 에이전트에 모델이 지정되어 있으면 그 모델을 씁니다. 변형을 적지 않았으면 그 모델의 최소 추론 변형을 고릅니다.

9.8 세션별 WebSocket 전송

상태 유지 WebSocket을 지원하는 프로바이더(Responses 계열 연속 체크포인트)에서만 씁니다. 세션당 채널 하나, 세마포어로 보호합니다.

WebSocket은 HTTP보다 무엇이 나은가? WebSocket 채널은 앞 스텝의 응답 ID와 그때 보낸 요청·받은 출력을 체크포인트로 들고 있다가, 다음 스텝에서는 previous_response_id와 새로 늘어난 입력만 보냅니다(증분 전송). 앞 요청과 출력이 새 요청 입력의 앞부분과 그대로 겹치고, 모델·시스템 지시·도구 목록 같은 나머지 요청 설정도 앞 스텝과 같을 때만 이렇게 하고, 아니면 요청 전체를 보냅니다. 프로바이더가 이어 받기를 거절해도(previous_response_not_found 등) 전체 요청으로 다시 보냅니다. HTTP 경로에는 이 체크포인트가 없어 스텝마다 대화 전체를 다시 보냅니다. 대신 WebSocket은 프로바이더가 지원해야 쓸 수 있고, 연결 교체·유휴 종료 같은 관리가 따릅니다. 그래서 OpenCode는 HTTP를 언제든 돌아갈 수 있는 기본값으로 두고, WebSocket은 되면 쓰는 최적화로 다룹니다.
상수값이유
ROTATE_AFTER_MS55분장기 연결 교체
CONNECT_TIMEOUT15초
IDLE_TIMEOUT30분"추론 모델은 몇 분간 아무것도 스트리밍하지 않을 수 있다"
MAX_STREAM_FAILURES5연속 실패 시 그 세션은 HTTP로 고정

연결 실패는 즉시 HTTP 폴백으로 고정되고, 1009(프레임 과대) 종료도 HTTP로 떨어집니다. 이동·리로드·삭제 시 채널을 닫습니다.

프로바이더마다 다른 점. 여기서 말하는 WebSocket은 OpenCode가 따로 만든 전송 방식이 아니라 프로바이더 API가 제공하는 기능입니다. 그래서 쓸 수 있는지와 세부 설정이 프로바이더마다 다릅니다. packages/ai는 Responses 계열 공통 채널 OpenResponsesChannel을 하나 두고, 프로바이더마다 이 채널을 쓸지, 연결을 얼마 만에 새로 열지(rotateAfterMs)를 정합니다. 프로바이더가 이 값을 정하면 그 값이 우선하고, 위 표의 ROTATE_AFTER_MS(55분)는 기본값으로만 쓰입니다.
