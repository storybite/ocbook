17장 설정 총람

이 장은 OpenCode V2.3.0의 모든 설정을 한곳에 모은 참조 장입니다. 서버/코어 설정(opencode.json), 터미널 설정(cli.json), 서비스 설정, 기능 플래그, 환경 변수, 키바인드까지 소스(packages/schema/src/config*.ts, packages/tui/src/config, packages/core/src/flag.ts)에서 직접 확인한 목록입니다.

그림 17-1 설정 로드 순서 — 오른쪽일수록 일반 설정의 우선순위가 높음

출처가 달라도 같은 길을 지난다

그림 17-1의 아홉 출처는 모양이 제각각입니다. 디스크의 파일도 있고, 환경 변수 문자열도 있고, MDM plist와 원격 서버의 응답도 있습니다. 하지만 OpenCode 안에서는 모두 "JSON 텍스트 하나"로 취급되고, 같은 세 단계를 거쳐 문서(Document)가 됩니다(core/src/config.ts).

flowchart LR F["opencode.json 파일"] --> T C["OPENCODE_CONFIG_CONTENT 값"] --> T M["MDM plist
(JSON으로 변환)"] --> T W["well-known 원격 설정"] --> T T["JSON 텍스트"] --> S["① 변수 치환
{env:…}, {file:…}"] S --> P["② 파싱·정규화
JSONC 읽기, V1 키 변환"] P --> V["③ 스키마 검증
Info"] V --> D["문서 하나
→ 설정 목록에 순서대로"]

그림 17-2 모든 설정 출처가 지나는 공통 경로

  1. 변수 치환(ConfigVariable.substitute): 텍스트 안의 {env:이름}과 {file:경로}를 실제 값으로 바꿉니다. 아래 "변수 치환"에서 자세히 봅니다.
  2. 파싱과 정규화(parseInfo): 주석과 끝 쉼표를 허용하는 JSONC로 읽고, V1 형식의 키를 V2 키로 옮깁니다(17.14절).
  3. 스키마 검증: 결과를 설정 스키마(Info)로 확인합니다. 잘못된 값은 경고를 남기고 버립니다.

그래서 OPENCODE_CONFIG_CONTENT는 "파일 대신 환경 변수에 담은 opencode.json"입니다. 파일에 쓸 수 있는 키는 모두 쓸 수 있고, V1 형식 키도 똑같이 받아들여집니다. 코드에서도 다른 점은 텍스트를 파일에서 읽느냐 환경 변수에서 읽느냐뿐입니다.

순서가 곧 우선순위

설정을 쓰는 쪽은 값이 어느 출처에서 왔는지 묻지 않습니다. 그림 17-1 순서대로 쌓인 목록에서 위치만 봅니다.

  • 일반 값은 그 키를 가진 마지막 문서를 씁니다(Config.latest는 findLast). 그래서 오른쪽일수록 강합니다. 키에 따라 이름별로 합치거나 이어 붙이는 방식은 아래 표와 같습니다.
  • 정책은 목록을 뒤집어 읽어 먼저 로드된 문서가 이깁니다(11.6절). 그래서 관리형 정책이 맨 앞에 따로 놓입니다.

같은 OPENCODE_CONFIG_CONTENT라도 일반 값으로는 관리형 settings 다음으로 강하지만, policies로는 가장 약합니다. 출처의 종류가 아니라 목록 속 자리 하나가 두 가지 우선순위를 모두 정합니다.

이렇게 씁니다 — 파일을 만들지 않고 설정 바꾸기: OPENCODE_CONFIG_CONTENT

CI나 일회성 실행에서 저장소의 설정 파일을 건드리지 않고 몇 가지만 바꾸고 싶을 때 씁니다.

bashOPENCODE_CONFIG_CONTENT='{"model":"corp-gateway/big","snapshots":false}' opencode run "변경 사항을 요약해 줘"

이 값은 프로젝트 설정보다 뒤에 놓이므로 model과 snapshots는 이 값이 이깁니다. 다만 permissions처럼 이어 붙는 키는 앞의 규칙에 덧붙을 뿐이고, policies는 앞선 문서의 정책을 뒤집지 못합니다. 무엇을 막는 용도로 쓰려면 이 점을 기억하십시오.

병합 방식키
마지막 파일이 값 전체를 이김shell, model, default_agent, snapshots, tool_output, websearch, warming, timezone, experimental
이름별 병합agents, commands, providers(및 providers.*.models), mcp.servers. mcp.timeout은 필드별. formatter는 boolean이면 앞을 초기화, 객체면 이름별. compaction, media.image, worktree는 필드별
누적(이어 붙임)permissions(마지막 매치 승리), instructions, skills, plugins, watcher.ignore, references
왜 키마다 병합 방식이 다를까요? model처럼 하나만 의미 있는 값은 덮어쓰기가 자연스럽습니다. agents처럼 이름 있는 항목 모음은 전역에서 정의한 에이전트를 프로젝트가 지우지 않도록 이름별로 합칩니다. permissions처럼 순서가 의미를 갖는 목록은 이어 붙여야 "전역 기본 + 프로젝트 예외"가 됩니다. 각 키의 의미론에 맞춰 병합을 고른 것입니다.

변수 치환

  • {env:VAR}: 환경 변수 값(없으면 빈 문자열). JSON으로 해석하기 전에 텍스트에서 바꾸므로 어느 키, 어느 자리에나 쓸 수 있습니다. 치환 결과가 JSON을 깨뜨릴 때만(예: 역슬래시가 든 Windows 경로) 이스케이프해서 다시 바꿉니다. 호출하는 쪽이 별도 변수 묶음을 넘길 수도 있는데, well-known은 이것으로 로그인 키를 프로세스 환경에 퍼뜨리지 않고 치환에만 씁니다(16.7절).
  • {file:path}: 파일 내용(trim, JSON 이스케이프). ~/ 확장, 상대 경로는 설정 파일 기준. //로 시작하는 줄에서는 건너뜀.
  • 적용 대상: 설정 파일, OPENCODE_CONFIG_CONTENT, MDM plist, well-known 문서.

17.4 permissions

필드타입설명
action와일드카드 문자열도구·동작 이름
resource와일드카드 문자열경로, 명령 텍스트, URL 등
effectallow|deny|ask

action 이름: read, edit, glob, grep, shell, webfetch, websearch, question, skill, subagent, todowrite, experimental_image_generate, external_directory, execute(Code Mode), opencode_list_mcp_resources, opencode_read_mcp_resource, opencode_watch_mcp_event, MCP 도구 <server>_<tool>, 그리고 *.

OpenCode 관리 도구도 같은 규칙(네임스페이스_도구명)으로 이름이 붙고, 그 이름으로 막거나 허용할 수 있습니다(tool/plugin/opencode.ts, schedule.ts, artifact.ts).

action도구
opencode_models사용 가능한 모델 검색
opencode_session_rename, opencode_session_move세션 이름 바꾸기, 세션 디렉터리 옮기기
opencode_worktree_create, opencode_worktree_list워크트리 만들기, 목록
opencode_worktree_remove워크트리 삭제. 이 도구만 edit으로 검사하므로 edit 규칙의 영향도 받음
opencode_schedule_create, _list, _pause, _resume, _delete예약 작업(schedules 플래그, 17.13)
opencode_artifact_create, _read, _update, _delete아티팩트(artifacts 플래그, 17.13)

이 도구들은 모두 Code Mode 카탈로그로 노출되므로, execute를 막으면 직접 도구로 바뀌어 보입니다(10.6절). 도구 하나를 완전히 숨기려면 {"action": "opencode_schedule_create", "resource": "*", "effect": "deny"}처럼 resource를 *로 막습니다.

write·patch는 별도 action이 아닙니다 도구 이름은 write, patch여도 파일 변경 권한은 모두 edit으로 검사합니다(file-write.ts, tool/plugin/patch.ts). 설정에 write deny만 넣으면 쓰기가 막히지 않습니다. V1 설정의 write/patch/apply_patch는 로드 시 edit으로 정규화됩니다(17.14절).
예: 보수적인 프로젝트 권한"permissions": [
  { "action": "external_directory", "resource": "*", "effect": "ask" },
  { "action": "shell", "resource": "*", "effect": "ask" },
  { "action": "shell", "resource": "git status *", "effect": "allow" },
  { "action": "shell", "resource": "git push *", "effect": "deny" },
  { "action": "edit", "resource": "migrations/*", "effect": "ask" }
]

17.18 환경 변수

환경 변수는 설정에 들어오는 길이 두 가지입니다.

  • 설정 문서가 되는 것: OPENCODE_CONFIG_CONTENT(opencode.json 전체), OPENCODE_CLI_CONFIG_CONTENT(cli.json 전체), 그리고 값 자리의 {env:…}. 그림 17-2의 공통 경로를 지나므로 파일과 완전히 호환되고, 우선순위는 목록 속 자리가 정합니다(17.2절).
  • 기능이 직접 읽는 것: 나머지 OPENCODE_* 변수 대부분. 설정 문서가 되지 않고, 각 모듈이 process.env를 그 자리에서 읽습니다. 그래서 대응하는 설정 키가 있어도 어느 쪽이 이기는지가 변수마다 다릅니다.

OpenCode가 자식 프로세스에 설정하는 변수

PTY·셸: OPENCODE_TERMINAL=1. shell 도구: AGENT=1, OPENCODE=1, AI_AGENT=opencode, OPENCODE_SESSION_ID. 워크트리 시작 명령: OPENCODE_WORKTREE_BASE(원본 디렉터리), OPENCODE_WORKTREE_PATH(새 워크트리, core/src/worktree.ts). 빌드 상수(OPENCODE_CHANNEL, OPENCODE_VERSION, OPENCODE_LOCAL 등)는 사용자 설정이 아닙니다.
