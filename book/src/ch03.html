3장 모노레포와 계층 아키텍처

OpenCode V2 저장소에는 서른 개가 넘는 패키지가 있습니다. 이 장에서는 패키지 목록을 외우는 대신 "어떤 방향으로만 의존할 수 있는가"라는 규칙 하나로 전체 구조를 읽는 법을 설명합니다.

3.1 계층으로 본 전체 그림

OpenCode V2는 크게 다섯 층으로 나뉩니다. 맨 위의 사용자 인터페이스(터미널 TUI, 데스크톱, 웹)는 모두 HTTP 클라이언트일 뿐이고, 실제 일은 서버 안의 Core가 합니다. Core는 LLM 호출을 packages/ai에 맡기고, 파일·셸·SQLite·Git 같은 실행/저장 자원을 직접 다룹니다.

그림 3-1 OpenCode V2의 논리 계층

터미널에서 무언가를 입력해도 TUI가 직접 LLM을 부르거나 파일을 고치지 않습니다. TUI는 서버의 session.prompt API를 호출할 뿐이고, 서버가 Core의 세션 엔진을 깨워 모델과 도구를 조정합니다. 결과는 SSE 이벤트 스트림으로 다시 TUI에 흘러갑니다.

왜 이렇게 나눴을까요? 코딩 에이전트는 수십 분씩 일하는 장기 작업입니다. UI가 엔진을 품고 있으면 터미널 창을 닫는 순간 작업이 사라집니다. 엔진을 서버로 떼어 내면 (1) 창을 닫아도 작업이 계속되고, (2) TUI·데스크톱·웹이 같은 세션을 동시에 볼 수 있으며, (3) 원격 서버에 붙는 것도 같은 코드로 됩니다. UI는 "보여 주는 일"만, Core는 "일하는 일"만 합니다.

3.2 의존 방향의 법칙

루트 AGENTS.md는 의존 방향을 다음처럼 못 박습니다.

AGENTS.md의 규칙 런타임 의존은 Schema → Core·Protocol → Server 방향으로만 흐릅니다. 클라이언트 런타임 코드는 Schema와 Protocol에는 의존할 수 있지만 Core나 Server에는 절대 의존하지 않습니다. sdk만이 Client·Core·Server를 조합합니다.

그림 3-2 주요 패키지 의존 그래프 (화살표는 "의존한다")

이 규칙이 주는 효과는 분명합니다.

  • Schema는 브라우저에서도 돕니다. 런타임이 없는 순수 계약이라 웹 앱과 데스크톱 렌더러가 그대로 가져다 씁니다.
  • 클라이언트는 가볍습니다. Core를 끌어오지 않으므로 SQLite·셸·PTY 같은 무거운 의존 없이 서버에 붙을 수 있습니다.
  • API는 하나의 진실에서 생성됩니다. Protocol의 HttpApi 정의에서 OpenAPI 문서와 Promise·Effect 두 종류의 클라이언트를 코드 생성합니다. 생성 파일은 손으로 고치지 않습니다.
현실과의 간극 packages/tui/package.json은 @opencode/core를 의존성으로 선언하고 있어 규칙과 어긋납니다. 규칙은 지향점이고, 코드베이스가 아직 그 방향으로 정리되는 중임을 보여 주는 예입니다.

Rust PTY 데몬process-daemon서버 프로세스가 바뀌어도 터미널 세션을 넘겨받기(handoff) 위함
왜 Effect인가? 에이전트 하네스의 어려움은 "성공 경로"가 아니라 "중간에 끊길 때"에 있습니다. 사용자가 Esc를 누르고, 서버가 업그레이드되고, 프로바이더가 429를 돌려주고, 서브에이전트 세 개가 동시에 돕니다. Effect는 모든 작업을 취소 가능한 파이버로 만들고, Scope로 자원 정리를 보장하며, 오류를 타입으로 드러냅니다. 초기 1.x는 이것을 Promise와 전역 상태로 처리했고, 1.x 후반부터 Effect로 옮겨 가기 시작했습니다(마지막 1.x인 1.19.5도 이미 파이버를 씁니다). 2.x는 처음부터 Effect를 바탕으로 다시 쓰면서 한 걸음 더 나아갔습니다. 파이버가 죽어도 작업이 사라지지 않도록, 실행 상태를 파이버를 띄우기 전에 SQLite에 먼저 기록합니다(7.6절).
