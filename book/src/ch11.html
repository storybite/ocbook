11장 권한·셸·파일 편집·스냅숏

에이전트에게 손발을 주었다면 다음 질문은 "어디까지 허락할 것인가"와 "잘못했을 때 어떻게 되돌릴 것인가"입니다. 이 장은 V2의 안전장치를 다룹니다.

11.1 권한 규칙 모델

packages/schema/src/permission.ts · core/src/permission.tsEffect  = "allow" | "deny" | "ask"
Rule    = { action: string, resource: string, effect }
Ruleset = Rule[]
Reply   = "once" | "always" | "reject"

export function evaluate(action, resource, ...rulesets) {
  return rulesets.flat().findLast((rule) =>
      Wildcard.match(action, rule.action) && Wildcard.match(resource, rule.resource)
  ) ?? { action, resource: "*", effect: "ask" }
}

마지막으로 매치된 규칙이 이기고, 아무것도 매치되지 않으면 ask입니다. 와일드카드는 *→.*, ?→.이며 역슬래시는 /로 정규화되고, 끝의 " *"는 선택적이라 git *는 git에도 매치됩니다. Windows에서는 대소문자를 무시합니다.

왜 "마지막 매치 승리"일까요? V1은 도구별 맵(permission: {bash: {"git push *": "ask"}})이라 우선순위가 숨어 있었습니다. 순서 있는 배열 + 마지막 매치 승리는 CSS나 방화벽 규칙처럼 "일반 규칙 먼저, 예외는 뒤에"로 쓰면 되므로 읽는 사람이 결과를 바로 예측할 수 있습니다. 설정 파일이 여러 개 합쳐질 때도 뒤에 온 파일(더 가까운 프로젝트)이 자연스럽게 우선합니다.

그림 11-1 권한 평가 파이프라인

그림 11-1은 "이 도구를 지금 실행해도 되는가"를 판정하는 순서입니다. 요청은 action 하나(예: shell)와 resource 여러 개로 들어옵니다. 셸 명령을 &&로 이으면 명령마다 resource가 하나씩 생기고, patch로 파일 여러 개를 고치면 파일마다 하나씩 생깁니다. 판정은 네 관문을 차례로 지납니다.

  1. 설정 규칙으로 거부부터 확인합니다. 에이전트 규칙 뒤에 세션 규칙을 이어 붙이고, resource마다 마지막 매치 규칙(11.1)을 찾습니다. 하나라도 deny면 그 자리에서 끝납니다. 이 단계에서는 사용자가 예전에 누른 "항상 허용"을 아직 보지 않으므로, 설정에 적힌 금지는 과거의 승인으로 풀 수 없습니다.
  2. 저장된 "항상 허용"을 덧붙여 ask와 allow를 가립니다. 프로젝트에 저장된 승인을 allow 규칙으로 맨 뒤에 붙입니다. 규칙은 마지막에 매치된 것이 이기므로, 설정 규칙으로는 ask였던 resource도 저장된 승인에 매치되면 allow로 바뀝니다. 예를 들어 설정에 git * → ask가 있어도 예전에 git status -s를 "항상 허용"해서 git status *가 저장돼 있다면, git status -b는 묻지 않고 실행됩니다. 반대로 deny는 관문 1에서 이미 걸러졌으므로 이 승인으로 풀리지 않습니다. 저장된 승인을 반영하고도 물어볼 resource가 하나라도 남으면 ask, 모두 허용되면 allow입니다.
  3. 훅이 결과를 고칠 기회를 얻습니다. permission.evaluate 훅(15.10)이 ask나 allow를 받아 바꿀 수 있고, 관리형 정책(11.6)도 여기서 deny를 강제합니다.
  4. 답할 사람이 없으면 ask를 그대로 둘 수 없습니다. 예약 작업처럼 무인으로 도는 실행이라면 무인 규칙을 덧붙여 다시 평가합니다. 모든 resource가 allow가 되면 진행하고, 아니면 "승인이 필요한데 승인할 사람이 없다"는 메시지와 함께 deny로 끝냅니다.
예시: 셸 규칙 세 줄로 따라가 보기

shell 규칙이 이 순서로 있다고 합시다. ① * → allow, ② rm * → ask, ③ git push * → deny. 마지막 매치가 이기므로 대부분은 허용하되 삭제는 묻고 푸시는 막는 설정입니다.

  • git push --force: 관문 1에서 ③에 걸려 바로 deny입니다. 예전에 이 명령을 "항상 허용"했더라도 저장된 승인은 관문 2에서야 붙으므로 결과는 바뀌지 않습니다.
  • git status && rm -rf dist: resource가 둘입니다. git status는 ①로 allow, rm -rf dist는 ②로 ask입니다. 거부가 없으니 관문 2로 가고, 하나가 ask이므로 전체가 ask가 되어 사용자에게 묻습니다.
  • 같은 명령, "항상 허용"을 받은 뒤: 이전 질문에 "항상"으로 답해 rm *(11.3의 save 패턴)가 저장되어 있다면, 관문 2에서 이 allow 규칙이 맨 뒤에 붙어 ②를 이깁니다. 두 resource가 모두 allow가 되어 묻지 않고 실행합니다.
  • 같은 명령, 무인 실행에서: 저장된 승인이 없어 ask로 남았는데 지켜보는 사람이 없다면, 관문 4에서 무인 규칙이 rm -rf dist를 허용하지 않는 한 deny로 끝납니다.
관문 3의 훅은 어떻게 붙이나

permission.evaluate 훅은 플러그인으로 등록해야 적용됩니다. 프로젝트의 .opencode/plugins/<이름>/index.ts에 플러그인을 두면 자동으로 로드되고, 고치면 바로 다시 로드됩니다. 플러그인의 setup에서 ctx.permission.hook("evaluate", …)로 훅을 등록합니다. 아래는 규칙상 허용된 git push도 사람에게 묻게 바꾸는 예입니다.

.opencode/plugins/team-hooks/index.tsimport { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "team-hooks",
  setup: async (ctx) => {
    await ctx.permission.hook("evaluate", (e) => {
      if (e.action === "shell" && e.resources.some((r) => r.startsWith("git push")) && e.effect === "allow")
        e.effect = "ask"
    })
  },
})

훅에는 관문 1에서 거부되지 않은 요청만 들어오므로, 설정 규칙의 deny를 허용으로 바꿀 수는 없습니다. 플러그인이 로드되지 않았거나 setup에서 실패했다면 /plugins 화면의 Server 구역에서 오류를 볼 수 있습니다. 전체 절차는 15.12절에 있습니다.

참고: 관문 4의 무인 실행을 만드는 예약 작업

예약 작업은 실험 기능 플래그 schedules를 켜야 쓸 수 있습니다. 예약 도구는 이 플래그가 켜졌을 때만 등록되며, 플래그를 켜는 방법은 17.13절과 같습니다(예: OPENCODE_FLAGS=schedules).

플래그를 켠 뒤 세션에서 /schedule 매일 평일 9시에 테스트 돌리고 실패하면 알려줘처럼 말로 요청하면, 모델이 schedule_create 도구로 예약을 만듭니다. 실행 시점은 in(지연), at(시각), every(간격), cron 가운데 하나로 정합니다. 인자 없이 /schedule만 입력하면 이 세션의 예약 목록을 보여 주고, 일시정지·재개·삭제도 같은 명령에 말로 요청하면 됩니다. 예약이 깨어나 도는 동안에는 승인할 사람이 없으므로, 그 실행의 권한 판정이 관문 4를 거칩니다.

11.3 도구별 resource와 save 패턴

에이전트가 도구를 쓰려고 하면 OpenCode는 "이걸 해도 될까요?"라고 묻습니다. 이때 정해야 할 것은 두 가지입니다.

  1. 지금 무엇을 허락하는가(resources): 이번 한 번의 행동이 무엇을 대상으로 하는지입니다.
  2. "항상 허용"을 누르면 무엇을 기억하는가(save): 앞으로 다시 묻지 않도록 저장해 둘 규칙입니다.
경비원과 출입증에 빗대면 resources는 지금 들어가려는 방 번호(예: git status -s)입니다. 경비원은 이 방을 보고 들여보낼지 정합니다. save는 "항상 허용"을 눌렀을 때 받는 출입증(예: git status *)입니다. 이 출입증은 방 하나보다 조금 넓게 "이 층 전체"를 허락합니다. 다음에 다른 방(git status --short)에 가려 하면 경비원이 출입증과 맞춰 보고 묻지 않고 들여보내지만, 다른 층(git push)에 가려 하면 다시 묻습니다.

둘을 나누는 이유는 간단합니다. 지금 하는 행동은 구체적이어야 정확히 판단할 수 있고, 저장할 규칙은 적당히 넓어야 쓸모가 있습니다. 도구마다 이 둘을 다음처럼 정합니다.

도구resources (지금 묻는 대상)save ("항상 허용" 때 저장하는 규칙)

파일 도구는 두 번 묻습니다. 프로젝트 밖의 파일을 고치려 하면, 먼저 "프로젝트 밖으로 나가도 되는가"(external_directory)를 묻고, 그다음 "이 파일을 고쳐도 되는가"(edit 같은 해당 action)를 묻습니다. 밖으로 나가는 것과 고치는 것은 서로 다른 위험이므로, 하나를 허락했다고 다른 하나까지 허락한 것으로 치지 않습니다.

첫 질문인 external_directory는 파일 하나가 아니라 그 파일이 든 폴더를 단위로 묻습니다. 예를 들어 /home/me/other-repo/src/a.ts를 읽으려 하면 "/home/me/other-repo/src/*에 접근해도 될까요?"라고 묻습니다. "항상 허용"을 누르면 저장되는 <프로젝트 루트>는 지금 작업 중인 프로젝트가 아니라 그 바깥 폴더가 속한 프로젝트의 루트입니다. 위 예라면 /home/me/other-repo/*가 저장되어 같은 저장소의 다른 폴더는 다시 묻지 않고, 그 폴더가 어떤 프로젝트에도 속하지 않으면 <dir>/*를 그대로 저장합니다(packages/core/src/file-access.ts의 FileAccess.resolve).

셸 명령은 '적당한 길이'로 잘라 기억합니다. git status -s를 "항상 허용"했다고 합시다.

  • 명령 전체를 그대로 저장하면 git status만 쳐도 또 묻습니다. 너무 좁습니다.
  • git *로 저장하면 git push --force까지 허용됩니다. 너무 넓습니다.

그래서 OpenCode는 명령마다 "몇 단어까지가 한 명령인가"를 정한 표(arity 표)를 씁니다. git은 2단어(git status), docker compose는 3단어(docker compose up), rm은 1단어입니다. 그 길이까지만 남기고 뒤에 *를 붙이므로 git status -s는 git status *로 저장됩니다. git status의 다른 옵션은 다시 묻지 않고, git push는 여전히 따로 묻습니다.

arity라는 말 arity는 원래 "함수가 받는 인자의 개수"를 뜻하는 용어입니다. 여기서는 "명령 이름을 몇 단어까지로 볼지"를 정한 수를 가리킵니다. 표에는 git: 2, docker compose: 3, rm: 1처럼 적혀 있습니다.

11.4 에이전트별 기본 권한

packages/schema/src/agent.ts — Info.defaultpermissions: [
  { action: "*", resource: "*", effect: "allow" },
  { action: "read", resource: "*.env", effect: "ask" },
  { action: "read", resource: "*.env.*", effect: "ask" },
  { action: "read", resource: "*.env.example", effect: "allow" },
]

여기서 action은 권한을 검사하는 동작 이름입니다. read, shell, grep처럼 대개 도구 이름과 같지만 꼭 일대일은 아닙니다. write·patch 도구는 따로 검사하지 않고 모두 edit으로 검사하며, external_directory는 도구가 아니라 "프로젝트 밖 경로에 손대도 되는가"를 묻는 동작입니다. *는 모든 action에 매치됩니다(전체 목록은 17.4절).

기본값은 .env 파일을 제외한 전부 허용입니다. 마지막 매치 승리이므로 외부 경로도 첫 줄의 *에 매치되어 external_directory도 기본적으로 묻지 않습니다(V1은 물었습니다).

왜 기본으로 열어 두었을까요?긴 작업이나 서브에이전트가 백그라운드에서 돌아가는 구조에서는 묻는 순간 작업이 멈추고 흐름이 끊깁니다. 그래서 기본값은 편의 쪽으로 열어 두고, 막아야 하는 경우는 permissions 규칙이나 관리형 정책(11.6절)에 맡겼다고 봅니다.

V1처럼 외부 경로에 손댈 때마다 다시 묻게 하려면 opencode.json 최상위 permissions에 규칙을 하나 넣습니다. 이 규칙은 기본 규칙 뒤에 덧붙고 마지막 매치가 이기므로 첫 줄의 allow를 덮어씁니다. 묻지 않고 아예 막으려면 effect를 "deny"로 씁니다(17.4절).

예: opencode.json — 외부 경로 접근을 V1처럼 묻기{
  "permissions": [
    { "action": "external_directory", "resource": "*", "effect": "ask" }
  ]
}

설정의 최상위 permissions는 모든 에이전트에, agents.<id>.permissions는 그 에이전트에 덧붙습니다. ~와 $HOME은 경로 action에서만 확장합니다. 셸 resource를 건드리지 않는 이유는 "안전한 확장에는 셸을 이해하는 파싱이 필요"하기 때문입니다.

그림 11-2 권한 질문의 왕복

"거부"를 왜 결함(defect)으로 터널링할까요? OpenCode V2가 쓰는 Effect 라이브러리(3.5절)는 실패를 두 가지로 나눕니다. 하나는 도구가 중간에 잡아서 다르게 처리할 수 있는 보통 오류이고, 다른 하나는 도구가 잡지 못하고 그대로 위로 올라가는 결함(defect)입니다. 만약 사용자의 거부가 보통 오류라면, 도구가 그것을 잡아 "실패했습니다"라는 텍스트로 바꿔 모델에게 줄 수 있습니다. 그러면 모델은 그 실패를 보고 다른 방법으로 같은 일을 시도합니다. 사용자의 "아니오"가 모델에게는 "다시 해 보라"로 바뀌는 셈입니다. 이를 막으려고 권한 서비스는 거부를 일부러 결함으로 보냅니다. 결함은 도구가 잡지 못하므로, 거부는 도구를 그대로 지나쳐 바깥까지 올라갑니다. 도구 바깥에서 이를 받은 쪽이 다시 원래의 거부(DeclinedError)로 되돌리고 스텝을 멈춥니다. 따라서 이 거부는 모델에게 전달되지 않습니다. 해당 도구 호출은 "The user declined this tool call"이라는 실패로 기록되고, 모델은 다른 방법으로 다시 시도할 기회 없이 그 자리에서 멈춥니다. 터널을 지나듯 도구를 건드리지 않고 통과한다고 해서 이를 "결함으로 터널링한다"고 부릅니다. 사유를 적은 거부는 다릅니다. "이렇게 하라"는 교정이므로 스텝을 멈추지 않고 모델에게 그 사유를 전달합니다.

11.6 관리형 정책(policies)

정책(policies)은 "이 자원을 애초에 써도 되는가"를 정하는 allow/deny 규칙 목록입니다. 권한(11.1~11.4절)이 도구 호출마다 허용·질문·거부(allow/ask/deny)를 고른다면, 정책은 그보다 바깥에서 프로바이더·도구·통합·MCP 서버·스킬·플러그인·웹 검색을 쓸 수 있는지부터 걸러 냅니다. 그래서 정책에는 ask가 없습니다. 정책의 allow는 금지를 풀 뿐이고 권한을 대신 내주지는 않습니다. tool.use를 allow해도 실제로 실행할지는 여전히 권한 규칙과 저장된 승인이 정합니다.

정책은 규칙 하나하나를 정책 규칙(문장, statement)으로 적습니다. 규칙 하나는 {"effect":"deny","action":"provider.use","resource":"openai"}처럼 effect(allow/deny)·action·resource 세 칸으로 된 객체이고, 이 예는 "openai 프로바이더를 쓰지 못하게 한다"는 뜻입니다. 정책 규칙은 두 곳에서 옵니다. 하나는 사용자가 opencode.json의 policies에 직접 쓰는 규칙(저장소·사용자 전역)이고, 다른 하나는 조직 관리자가 OpenCode Console(조직용 관리 서비스)에서 정해 내려보내는 규칙입니다. 이 뒤의 것이 관리형(organization-managed) 정책입니다. Console에 연결된 클라이언트는 설정을 받을 때(GET /api/v2/config) 조직의 정책 규칙도 함께 받고, 약 1분마다 다시 받아 갱신합니다. 권위는 저장소 → 사용자 전역 → 조직 관리형 순으로 높아집니다. 따라서 조직이 막은 것은 저장소나 사용자 설정의 allow로 풀 수 없습니다. 아래 표는 정책이 다루는 action과 그 효과입니다.

왜 설정 덮어쓰기가 아니라 정책인가 specs/v2/provider-policy.md: 설정을 덮어쓰는 것으로는 사용자가 프로바이더를 추가하는 것을 막을 수 없습니다. "허용 목록"을 강제하려면 결과 카탈로그에 대한 필터가 필요하고, 그것이 정책입니다.

11.7 셸: 포그라운드·백그라운드·데몬

이 절은 에이전트가 요청한 셸 명령을 OpenCode의 shell 도구가 어떻게 실행하는지 설명합니다. 셸 명령은 에이전트의 도구 중 가장 강력하고 가장 오래 걸릴 수 있어서, 세 가지 문제를 풀어야 합니다. 첫째, 실행하기 전에 명령을 파싱해 권한을 확인해야 합니다. 둘째, 오래 걸리는 명령이 세션을 붙잡지 않도록 포그라운드와 백그라운드 가운데 하나로 돌려야 합니다. 셋째, 서버가 재시작해도 돌던 명령을 잃지 않아야 합니다(데몬 백엔드). 아래 요점 목록과 그림 11-3, 실행 백엔드 표가 차례로 이 셋을 다룹니다.

  • 얼마나 기다리나. 명령 하나는 기본으로 2분까지 기다립니다. 사용자가 중간에 멈추면 명령이 정리될 시간을 최대 0.5초(500ms) 주고, 그때까지 나온 출력을 결과로 삼아 마무리합니다.
  • "에이전트가 돌린 명령"이라는 표시. 명령을 실행할 때 AGENT=1, OPENCODE=1, AI_AGENT=opencode, OPENCODE_SESSION_ID, TERM=xterm-256color, OPENCODE_TERMINAL=1 같은 환경 변수를 붙여 줍니다. 그래서 스크립트는 지금 사람이 아니라 에이전트가 자신을 돌리고 있음을 알아채고, 예컨대 대화형 질문을 건너뛰는 식으로 동작을 바꿀 수 있습니다.
  • 실행 전에 무엇을 확인하나. 순서는 이렇습니다. ① 명령을 어느 폴더에서 돌릴지(cwd) 정합니다. ② 스캐너(shell/scan.ts, 약 2,500줄)가 bash·PowerShell 문법을 읽어 명령줄을 낱개 명령으로 쪼갭니다. 예를 들어 cd ../other && rm -rf dist는 cd와 rm 두 명령이 됩니다. ③ 작업 폴더와 cd로 들어가는 폴더가 프로젝트 밖이면 external_directory 권한을 확인합니다. 다만 V2 기본 권한은 맨 앞의 전체 허용 규칙(* / * / allow)이 이 검사에도 매치되므로 기본값으로는 묻지 않고 통과합니다(V1은 물었습니다). 다시 묻게 하려면 permissions에 external_directory를 ask로 두는 규칙을 덧붙입니다(11.4절). ④ 쪼갠 명령마다 shell 권한을 확인합니다. ⑤ 승인을 받은 뒤 작업 폴더가 존재하는지 한 번 더 확인합니다. 사용자가 승인 창 앞에서 머뭇거리는 사이에 폴더가 지워지거나 바뀔 수 있기 때문입니다.
  • 프로세스를 띄우는 순간은 끊지 않는다. 프로세스를 만드는 짧은 구간은 uninterruptibleMask로 감싸 중단 신호가 끼어들지 못하게 합니다. 그 사이에 끊기면 프로세스는 이미 떴는데 OpenCode는 그 존재를 모르는, 관리자 없는 "고아" 프로세스가 남을 수 있기 때문입니다.

그림 11-3 셸 명령의 경로

그림 11-3을 쉽게 풀면, 셸 명령은 "기다릴 것인가, 맡겨 두고 갈 것인가"에 따라 두 갈래로 나뉩니다. 갈림길은 모델이 shell 도구를 부를 때 background: true를 붙였는지입니다.

누가 정하나? 처음 판단은 모델이 합니다. 도구 설명이 "개발 서버나 오래 걸리는 빌드는 백그라운드로 돌리라"고 안내하고, 모델이 그에 따라 background 값을 넣습니다. 포그라운드 명령이 제한 시간을 넘기면 OpenCode가(shell_timeout_background 플래그를 켰을 때) 백그라운드로 옮기고, 실행 중에는 사용자가 ctrl+b로 직접 옮길 수 있습니다.

  • 백그라운드(왼쪽 갈래) — 맡겨 두고 갑니다. 명령을 띄우자마자 결과를 기다리지 않고 바로 돌아옵니다. 모델이 받는 것은 실행 결과가 아니라 "접수증"입니다. 명령을 가리키는 shell ID, 프로세스 번호(PID), 출력이 쌓이는 파일 위치입니다. 함께 "끝나면 알려 줄 테니 상태를 계속 확인(폴링)하지 말라"는 안내가 붙습니다. 명령이 끝나면 OpenCode가 shell id=... state=... 형태의 합성 메시지를 세션에 넣어 모델에게 알려 줍니다. 세탁기를 돌려 두고 다른 일을 하다가 완료 알림을 받는 것과 같습니다.
  • 포그라운드(오른쪽 갈래) — 끝날 때까지 기다립니다. 제한 시간(기본 2분) 안에 끝나면 출력의 뒷부분(tail)을 결과로 돌려줍니다. 앞부분이 아니라 뒷부분인 까닭은 아래에서 설명하듯 오류와 요약이 대개 로그 끝에 있기 때문입니다.
  • 제한 시간을 넘기면 — 플래그에 따라 둘 중 하나. 기능 플래그 shell_timeout_background가 꺼져 있으면 명령을 끝내 버리고 "더 큰 timeout으로 다시 실행하라"고 모델에게 알려 줍니다. 켜져 있으면 명령을 죽이지 않고 백그라운드로 옮깁니다. 이때는 명령이 여전히 돌고 있으므로 "같은 명령을 또 시작하지 말라"고 알려 주고, 끝나면 백그라운드 갈래와 똑같이 합성 메시지로 통지합니다. 오래 걸리던 빌드를 처음부터 다시 돌리는 낭비를 막는 길입니다. 이 플래그는 릴리스 빌드에서 기본으로 꺼져 있으며, 환경 변수 OPENCODE_FLAGS=shell_timeout_background나 opencode.json의 "experimental": { "shell_timeout_background": true }로 켭니다(17.13절).

실행 백엔드

모델이 shell 도구로 명령을 요청하면, 그 명령을 실제 OS 프로세스로 띄우고 들고 있을 주인을 정해야 합니다. 이것이 실행 백엔드이며, 포그라운드·백그라운드와는 별개의 축입니다. 백엔드는 둘입니다. daemon은 서버 바깥에서 따로 도는 PTY 데몬이 프로세스를 맡는 방식으로, 명령이 Location이 아니라 서버에 속하고 메타데이터(마감 시각 포함)가 데몬에 저장되어 계획된 서버 재시작 뒤에도 다음 서버가 다시 연결합니다. spawned는 서버가 Location의 Environment를 거쳐 명령을 자기 자식 프로세스로 직접 띄우는 방식입니다. 모델은 이 선택에 관여하지 않고, OpenCode가 명령을 띄울 때마다 아래 순서로 정합니다.

순서확인하는 것결과
①원격 워크스페이스가 아니고(Location에 workspaceID가 없음), 런타임이 PTY 데몬을 지원하는가(Bun·Node 빌드는 지원, Cloudflare workerd 빌드는 미지원)아니면 곧바로 spawned
②데몬에 실제로 연결되는가연결·기동 실패(UnavailableError)면 경고만 남기고 spawned로 넘어감. 요청은 갔는데 오류(RequestError)면 spawned로 넘어가지 않고 실패로 끝냄
③둘 다 통과daemon

왜 이 순서일까요? 첫째, 쓸 수 있으면 daemon을 먼저 고릅니다. 이 절 첫머리의 셋째 과제, 곧 서버가 재시작해도 돌던 명령을 잃지 않는 일을 해결하는 쪽이 daemon이기 때문입니다. 몇십 분짜리 백그라운드 빌드가 서버 재시작 한 번에 끊기지 않아야 합니다. 둘째, 원격 워크스페이스와 workerd를 맨 앞에서 걸러 냅니다. 데몬은 서버가 도는 기계의 로컬 프로세스라서 원격 워크스페이스의 명령은 그 워크스페이스의 Environment를 거쳐 띄워야 하고, workerd에서는 데몬을 띄울 수조차 없습니다. 셋째, 실패의 종류에 따라 대응이 갈립니다. 연결 실패라면 명령이 시작되지 않은 것이 확실하므로 서버가 직접 띄워도 안전하고, 명령을 아예 못 돌리는 것보다 낫습니다. 반면 요청 오류는 데몬이 명령을 이미 실행했는지 알 수 없는 상태입니다. 여기서 다시 띄우면 git push나 rm 같은 명령이 두 번 돌 수 있으므로, 소스 주석 그대로 "데몬이 이미 실행했을 수 있다. 여기서 다시 실행하지 말 것."을 지켜 실패로 끝냅니다.

이렇게 씁니다 — 오래 걸리는 명령 다루기: Esc · ctrl+b

에이전트가 오래 걸리는 셸 명령(긴 빌드, 테스트 전체 실행)을 돌리는 동안 세션은 그 도구가 끝나기를 기다립니다. 이때 두 가지를 고를 수 있습니다.

  • ctrl+b — 기다리지 말고 뒤로 보내기. 세션을 막고 있는 도구를 백그라운드로 옮깁니다. 위 그림 11-3의 "백그라운드로 이동" 경로를 사람이 직접 고르는 셈입니다. 명령은 계속 돌고, 끝나면 합성 메시지로 에이전트에게 통지되므로 에이전트는 기다리지 않고 다른 일을 이어 갑니다. 예를 들어 15분짜리 E2E 테스트가 돌기 시작했을 때 ctrl+b를 누르면, 테스트가 도는 동안 에이전트는 문서 정리를 하다가 테스트 결과 통지를 받고 다시 확인합니다.
  • Esc — 멈추기. 지금 실행을 중단합니다. 돌고 있던 셸 명령은 최대 500ms를 기다린 뒤 그때까지의 출력으로 마무리됩니다. 에이전트가 엉뚱한 명령을 돌리기 시작했다면 Esc로 끊고 방향을 다시 알려 주십시오(7.4절의 steer).

포그라운드 명령의 기본 타임아웃은 2분입니다. 개발 서버처럼 계속 떠 있어야 하는 프로세스는 에이전트에게 백그라운드로 돌리라고 시키거나, 직접 /terminal(4.7절)에서 띄워 두는 편이 깔끔합니다.

예시 — 파일 복사 도중 Esc를 누르면. 에이전트가 파일 100개가 든 폴더를 포그라운드 셸 명령으로 복사하고 있고, 파일 하나에 1초가 걸린다고 합시다. 69개를 마치고 70번째 파일을 복사하는 중에 Esc를 눌렀다면, 그 순간부터 다음 순서로 진행됩니다.

  1. 0초: 세션에 중단 표시가 붙고, 명령을 기다리던 셸 도구가 정지 신호를 받습니다. 도구는 곧바로 복사 프로세스에 SIGTERM을 보냅니다.
  2. 0~0.5초: 도구는 프로세스가 끝나기를 최대 500ms 기다립니다. cp처럼 SIGTERM을 받으면 바로 끝나는 명령은 여기서 멈춥니다. 1~69번 파일은 남고, 70번 파일은 일부만 복사된 채 남을 수 있으며, 71~100번 파일은 복사되지 않습니다.
  3. 0.5초: 프로세스가 아직 살아 있어도 도구는 더 기다리지 않습니다. 그때까지 나온 출력과 interrupted: true를 담아 도구 호출을 실패로 끝내고, 세션은 사용자 입력을 기다립니다.
  4. 3초: SIGTERM을 무시하고 계속 도는 프로세스가 있으면 SIGKILL로 강제 종료됩니다. 이 경우 그 사이에 70~72번 파일 정도가 더 복사될 수 있습니다.
  5. 이후: 이미 복사된 파일은 지워지지 않습니다. 남은 복사를 이어 갈지, 그만둘지 에이전트에게 다시 지시하면 됩니다.

11.8 파일 편집: edit, write, patch

층위는 FileAccess(경로 해석, 외부 경계) → FileWrite(대상·diff 미리보기와 함께 edit 권한·커밋·포맷) → FileMutation(잠금, BOM 보존 쓰기)입니다. 잠금은 정렬·중복 제거된 경로에 대한 프로세스 전역 KeyedMutex로 교착을 피합니다.

edit의 3단계 매칭

  1. LF 뷰에서 정확히 일치(모델은 read에서 LF를 봤으므로). 오프셋은 CRLF 원본으로 되돌려 매핑.
  2. 유니코드 정규화 일치(곡선 따옴표, 대시, NBSP류 공백).
  3. 줄 끝 공백을 무시한 줄 단위 일치.

교체문의 줄바꿈은 일치한 구간의 것을 LCS로 줄 단위 정렬해 따릅니다. 실패하면 "가장 가까운 줄" 힌트(최대 12줄)를 주되, 이미 read가 허용된 경우에만 보여 줍니다(편집 실패가 읽기 권한 우회가 되지 않도록). "newString is already in the file"로 이미 적용된 편집도 알려 줍니다.

patch 형식

tool/patch-grammar.txt (Lark, 발췌)start: begin_patch hunk+ end_patch
hunk: add_hunk | delete_hunk | update_hunk
update_hunk: "*** Update File: " filename LF change_move? change?
change: (change_context | change_line)+ eof_line?
  • 매칭은 exact → rstrip → trim → 유니코드 정규화 순으로 시도.
  • 두 단계: 모든 hunk를 메모리에서 준비·검증(같은 파일 hunk는 연쇄) → 모든 대상에 대해 한 번의 edit 권한을 합친 diff로 질문 → 순차 쓰기.
  • 중간 실패 시 "Completed before failure: …"로 부분 적용을 정직하게 보고. 다중 파일 원자성은 아직 TODO입니다.

포매터

확장자로 매칭하며 $FILE을 치환해 실행하고 첫 번째로 0을 반환한 포매터가 이깁니다. 설정에서 formatter: true로 켜야 동작합니다(미설정 시 꺼짐). diff는 포맷된 결과 기준입니다.

V2에 아직 없는 것 file-mutation.ts의 TODO: 감시자 이벤트 발행, 도구 호출 단위 스냅숏/되돌리기, LSP 진단, 다중 파일 트랜잭션. V2 코어에는 LSP 런타임이 없습니다(설정 키 lsp는 받아들이지만 소비자가 없음). 마이그레이션 문서는 린트·타입체크·컴파일 명령으로 대체하라고 권합니다.

11.9 스냅숏과 되돌리기

packages/core/src/snapshot.tsconst gitDirectory = AbsolutePath.make(
  path.join(global.data, "snapshot", location.project.id, Hash.fast(worktree)),
)

스냅숏은 프로젝트 Git과 분리된 그림자(shadow) Git 저장소에 트리로 저장됩니다. 사용자의 커밋 이력을 더럽히지 않으면서 Git의 내용 주소 저장을 그대로 씁니다.

  • Git 저장소이고 snapshots 설정이 false가 아닐 때만 활성.
  • capture()는 원본 저장소의 ignore를 존중하고, 추적 안 되는 파일은 2 MiB까지만. 실패해도 경고만 남기는 최선 노력 방식. 10분마다 최대 한 번 pack.
  • 스텝 시작(포크)과 끝에 캡처하고 변경 파일을 assistant 메시지의 snapshot.start/files에 기록.
워크트리와 pack
  • 워크트리는 원본 Git 저장소의 작업 트리(파일이 체크아웃된 루트)입니다. 그림자 저장소는 이 작업 트리를 그대로 공유하고, Git 디렉터리만 global.data/snapshot/<프로젝트ID>/<작업 트리 경로 해시>에 따로 둡니다. 경로를 해시하므로 같은 프로젝트라도 Git worktree마다 그림자 저장소가 따로 생깁니다.
  • pack은 캡처로 쌓인 낱개 객체(loose object)를 묶음 파일로 합치고 작은 묶음들도 합치는 정리 작업입니다. capture()가 끝날 때마다 시도하지만 마지막 시도 후 10분이 지나지 않았으면 건너뛰고, 돌더라도 낱개 객체 2048개·묶음 16개 미만이면 아무것도 하지 않습니다. 객체를 지우지 않으므로 되돌리기용 트리는 그대로 남습니다.

그림 11-4 2단계 되돌리기

정리 — stage에서 '숨긴다'는 뜻 stage는 메시지를 지우지 않습니다. RevertEvent.Staged로 세션에 revert = { messageID, snapshot, files } 표시만 남기고, 화면은 이 표시를 보고 경계 이후 메시지를 감춥니다. 그래서 clear(/redo)는 표시를 지우고 파일만 되돌리면 원래 상태로 돌아옵니다. stage 중에는 모델을 호출하지 않으며(실행 중이면 BusyError, wake 억제), 새 프롬프트나 /compact가 오면 다른 처리보다 먼저 commit이 숨긴 메시지를 실제로 지웁니다. 따라서 되돌린 메시지는 모델 컨텍스트에 다시 들어가지 않습니다.

stage는 경계 이후 assistant들이 건드린 파일마다 가장 이른 snapshot.start 트리를 찾아 그 파일들만 복원합니다("선택된 트리에 없는 경로는 삭제, 맵 밖의 경로는 건드리지 않음"). 되돌리기 직전 상태도 캡처해 두어 clear로 되돌리기를 취소할 수 있습니다.

왜 2단계일까요? 되돌리기는 파일과 대화를 동시에 과거로 돌립니다. 바로 이력을 지우면 "앗, 너무 많이 되돌렸다"를 수습할 수 없습니다. 먼저 파일만 돌려 사용자가 확인하게 하고(stage), 다음 프롬프트를 보낼 때 비로소 이력을 확정(commit)합니다. 확정 전까지는 언제든 취소(clear)할 수 있습니다.
이렇게 씁니다 — 마음 놓고 시키고 되돌리기: /undo · /redo · /timeline · /fork · /diff

2단계 되돌리기 덕분에 "일단 시켜 보고, 마음에 안 들면 되돌린다"는 방식이 안전합니다. 단, 스냅숏은 Git 저장소에서만 동작합니다. Git이 아닌 폴더에서 /undo를 하면 메시지만 숨겨지고 파일은 그대로입니다.

명령기본 키하는 일
/undoctrl+x u마지막 프롬프트 하나만큼 되돌림(파일 복원 + 메시지 숨김 = stage). 여러 번 누르면 한 프롬프트씩 더 거슬러 감
/redoctrl+x r되돌리기를 통째로 취소(clear). 첫 undo 직전 상태로 복귀
/timelinectrl+x g내 프롬프트 목록. 고른 지점으로 이동·되돌리기·복사·포크
/fork—전체 또는 특정 프롬프트 직전까지를 복사한 새 세션
/diff—변경 비교 뷰어(브랜치 전체, 커밋만, 커밋 안 한 것, 마지막 턴)

예 1 — 결과가 마음에 들지 않는다. "버튼 색을 바꿔 줘"라고 했더니 CSS 파일 세 개를 뜯어고쳤습니다. /undo를 누르면 에이전트가 일하는 중이라도 먼저 멈춘 뒤, 그 프롬프트 이후에 바뀐 파일들을 스텝 시작 전 상태로 돌립니다. 화면에는 "N messages reverted"와 바뀐 파일 목록이 뜨고, 방금 보낸 프롬프트 글자가 입력 칸에 다시 채워집니다. 이제 "button.css만 고쳐"처럼 다듬어 다시 보내면 됩니다. 이때 비로소 숨겨 둔 메시지가 확정 삭제됩니다(commit).

예 2 — 너무 많이 되돌렸다. 다시 보내기 전이라면 /redo로 전부 원래대로 돌아옵니다(화면의 "reverted" 배너를 눌러도 됩니다). 한 단계씩 앞으로 가는 것이 아니라 첫 undo 직전으로 한 번에 돌아갑니다.

예 3 — 지난 시점부터 다른 길로 가 보고 싶다. /fork를 열어 세 번째 프롬프트를 고르면, 그 프롬프트 직전까지의 대화를 복사한 새 세션이 생기고 고른 프롬프트는 새 세션의 입력 칸에 들어갑니다. 원래 세션은 그대로이므로 두 접근을 비교할 수 있습니다. 새 세션의 제목은 "원제목 (fork #1)"이 되고, 에이전트·모델·권한·폴더도 그대로 이어집니다.

예 4 — 이번에 뭘 바꿨는지 확인하고 싶다. /diff를 열고 d로 소스를 "Last turn"으로 바꾸면, 마지막 프롬프트 이후 에이전트가 바꾼 내용만 스냅숏 기준으로 보여 줍니다. ]/[로 변경 덩어리, n/p로 파일을 넘기고, m으로 검토한 파일을 표시합니다. 커밋 전에 한 번 훑어보는 습관을 들이면 좋습니다.

함정
  • 되돌린 뒤 새 프롬프트를 보내거나 /compact를 하면 숨긴 메시지가 영구 삭제되어 /redo가 불가능해집니다.
  • 되돌린 파일을 손으로 고친 뒤 /redo를 하면 그 수정이 스냅숏으로 덮어써집니다.
  • 포크는 파일을 복사하지 않습니다. 두 세션이 같은 폴더를 씁니다. 옛 시점에서 포크해도 디스크의 파일은 지금 상태 그대로이고, 모델에게도 "파일과 저장소는 원본과 공유된다"는 안내가 들어갑니다. 파일까지 따로 실험하려면 워크트리(5.7절)에서 하십시오.
  • /timeline에서 고른 "Revert"는 /undo와 달리 에이전트를 먼저 멈추지 않습니다. 실행 중이면 거부되므로 Esc로 멈춘 뒤 쓰십시오.
  • 추적되지 않는 2 MiB 넘는 파일은 스냅숏에 들어가지 않아 되돌려지지 않습니다.
