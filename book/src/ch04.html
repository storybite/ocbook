4장 클라이언트와 서버의 분리

opencode를 실행하면 실제로는 두 개의 프로그램이 돕니다. 백그라운드 서버와, 그 서버에 붙는 TUI입니다. 이 장에서는 서버를 찾고 띄우는 방법, 인증, 이벤트 전송을 차례로 살펴봅니다.

4.1 런처에서 바이너리까지

packages/cli/bin/opencode.cjs는 Node로 된 작은 셈(shim)입니다. 플랫폼에 맞는 @opencode/cli-<platform>-<arch> 패키지(x64는 AVX2 지원 여부까지 확인)를 골라 네이티브 바이너리를 실행하고, SIGINT·SIGTERM·SIGHUP 신호를 그대로 전달합니다. 진짜 진입점은 packages/cli/src/index.ts입니다.

  • 지연 import되는 핸들러 표를 만듭니다: 기본($, TUI), run, serve, service {start,restart,status,stop,get,set,unset}, acp, api, auth, mcp, plugin, session, pair, mini 등.
  • NO_PROXY에 127.0.0.1,localhost,::1을 추가합니다. 로컬 서비스 요청이 회사 프록시로 새지 않게 하기 위함입니다.
  • CLI 환경 변수는 주로 cli/src/env.ts에 모여 있지만 전부는 아닙니다. 진입점이 NO_PROXY/no_proxy와 내부 전달용 OPENCODE_SSH_ASKPASS_PORT를 직접 읽고, 서버 부팅(server-process.ts)과 TUI도 각자 읽습니다. 전체 목록은 17.18절에 있습니다.

그림 4-1 서버 연결 결정 흐름

그림 4-1의 맨 아래 다섯 갈래는 클라이언트 종류(웹·데스크톱·TUI)가 아니라, TUI 하나가 옵션과 등록된 서버 상태에 따라 서버를 얻는 다섯 가지 결과입니다. 실제 사용 장면으로 풀면 다음과 같습니다.

  1. 명시 서버 접속(--server URL): 회사 개발 서버에 OpenCode 서버를 띄워 두고, 내 노트북에서는 opencode --server http://dev-box:<포트>처럼 그 서버에 붙는 경우입니다. 내 PC에서는 서버를 띄우지 않고 화면 역할만 합니다. 서버 버전이 내 TUI와 달라도 경고만 띄우고 그대로 접속합니다.
  2. 전용 자식 서버(--standalone): 실험용으로 다른 터미널과 섞이지 않는 독립된 환경이 필요할 때 씁니다. 이 TUI만 쓰는 서버가 하나 따로 뜨고, TUI를 닫으면(stdin이 끊기면) 그 서버도 함께 꺼집니다.
  3. 재사용: 터미널 A에서 opencode를 켜 둔 상태에서 터미널 B에서 다시 opencode를 실행하는 경우입니다. B는 service.json에서 이미 떠 있는 서버를 찾아 그대로 붙습니다. 그래서 A와 B는 같은 서버와 같은 세션 기록을 함께 봅니다.
  4. 교체(재시작): 어제 띄운 v2.2 서버가 아직 백그라운드에 남아 있는데, 오늘 v2.3으로 업데이트하고 opencode를 실행한 경우입니다. 새 v2.3 서버가 등록 파일을 자기 정보로 바꿔 씁니다. 옛 서버는 5초마다 이 파일을 확인하다가 더는 자기를 가리키지 않는 것을 보고 스스로 종료합니다.
  5. 경쟁자 기동: 컴퓨터를 켜고 처음 opencode를 실행해 아직 서버가 없는 경우입니다. 이때 서버를 새로 띄웁니다. 터미널 두 개에서 거의 동시에 실행해도 포트가 고정되어 있어서 하나만 포트를 잡는 데 성공하고, 나머지 하나는 물러납니다. 결국 서버는 하나만 남습니다.

이 가운데 가장 흔한 경우는 3번 재사용입니다. 옵션 없이 opencode를 실행하는 기본 모드는 사용자 전체에서 하나만 도는 관리형 백그라운드 서비스를 씁니다. 그래서 처음 실행할 때(5번)와 업데이트 직후(4번)를 빼면 거의 모든 실행이 이미 떠 있는 서버에 붙습니다. 1번과 2번은 옵션을 직접 줄 때만 쓰는 특수한 경우입니다.

참고 — 로컬에서 TUI만 쓰는 사람에게도 이득이 있을까요?

있습니다. 첫째, opencode를 다시 실행하면 서버를 새로 띄우지 않고 이미 떠 있는 서버에 바로 붙습니다(3번 재사용). 둘째, 창을 여러 개 열어도 서버는 하나이므로 모든 창이 같은 세션 상태를 SSE로 함께 봅니다. 예를 들어 편집기 옆 작은 터미널에서는 진행 상황을 지켜보고, 큰 창에서는 같은 세션의 diff를 살펴볼 수 있습니다. 다른 창에서 queue로 넣은 지시도 모든 화면에 똑같이 보입니다. 셋째, 에이전트 루프는 TUI가 아니라 서버 안에서 돌기 때문에 창이 하나뿐이어도 이득이 있습니다. TUI를 실수로 닫았다가 다시 열어도 진행 중인 세션에 이어서 붙을 수 있습니다. TUI를 끝내는 것은 서버에서 화면만 떼어 내는 일이고, 작업을 멈추려면 따로 인터럽트(session.interrupt)를 보내야 합니다. TUI를 닫을 때 서버까지 함께 끄고 싶다면 --standalone으로 실행합니다.

4.3 관리형 백그라운드 서비스

기본 모드에서 서버는 사용자 전체에서 하나만 도는 백그라운드 서비스입니다. TUI 여러 개와 데스크톱 앱이 모두 같은 서비스를 공유합니다.

탐색 계약: service.json

서비스는 상태 디렉터리의 등록 파일로 자신을 알립니다. packages/client/src/effect/service.ts의 주석은 이 파일이 "완전한 탐색 계약"이라고 설명합니다.

packages/client/src/effect/service.ts// The service daemon advertises itself through a registration file in the
// user's state directory: url, pid, version, and the private password, with
// 0600 permissions. That file is the complete discovery contract — reading it
// is all a client needs to connect.
  • 위치: $XDG_STATE_HOME/opencode/service.json(기본 ~/.local/state/opencode/service.json). latest·dev·beta·next 채널은 이 이름을 공유하고, local 등 그 밖의 채널은 service-<channel>.json.
  • 같은 이름의 서비스 설정 파일(~/.config/opencode/service.json, 포트·비밀번호·env 등)과는 별개입니다. 클라이언트는 설정이 아니라 이 등록 파일만 읽습니다.
  • 내용: {id, version, url, pid, password}, 권한 0600.

고정 포트와 경쟁자(contender)

기본 포트는 0xC0DE(49374), local 채널은 0xC0DF(49375)입니다. Windows에서는 Hyper-V/WinNAT 예약 범위와 WSL이 잡는 4096포트 블록을 피하려고 0x7000 | (port & 0xfff), 즉 28894(local은 28895)로 바꿉니다. Service.ensure는 서버가 없으면 작은 경쟁자 프로세스를 띄웁니다. 포트가 고정이므로 동시에 뜬 경쟁자 둘 중 하나는 바인드에 실패하고 물러납니다.

왜 포트를 고정할까요? 포트 0(임의 포트)을 쓰면 충돌은 없지만, 두 서비스가 동시에 떠서 같은 SQLite 데이터베이스를 두고 다툴 수 있습니다. 고정 포트는 운영체제의 바인드 실패를 "하나만 살아남는" 락처럼 씁니다. 별도 분산 락 없이 단일 인스턴스를 보장하는 간단한 방법입니다.

주차 자리가 딱 한 칸뿐인 주차장을 떠올리면 쉽습니다. 서버가 늘 같은 포트(49374)만 쓰도록 정해 두면, 두 서버가 동시에 떠도 먼저 그 자리를 차지한 쪽만 살아남습니다. 나중에 온 쪽은 운영체제가 "이미 사용 중"이라며 바인드를 거부하므로 그대로 물러납니다. 덕분에 잠금 파일 같은 장치를 따로 두지 않아도 서버는 늘 하나만 돌고, 두 서버가 같은 데이터베이스를 함께 건드려 다투는 일이 생기지 않습니다.

자기 퇴출(self-eviction)

서버는 등록 파일을 원자적으로 씁니다(임시 파일 → rename, Windows EPERM은 재시도). 그리고 5초마다 파일을 다시 읽어, 자신을 가리키지 않으면 스스로 종료합니다("managed service registration replaced; shutting down"). 새 버전이 서비스를 이어받으면 옛 서버가 알아서 물러나는 구조입니다.

이렇게 씁니다 — 공유 서버 다루기: /reload · /restart · /update

4.3절에서 본 것처럼 TUI는 껍데기이고, 실제 일은 사용자 전체에서 하나만 도는 백그라운드 서비스가 합니다. 그래서 "무언가를 새로 읽게 하고 싶다"는 상황에서 무엇을 다시 띄워야 하는지를 구분하는 것이 중요합니다. 세 명령은 다시 시작하는 범위가 다릅니다.

명령다시 시작되는 것그대로 남는 것언제 쓰나
/reload불러온 모든 Location의 서비스(설정·플러그인·MCP 등)를 다시 조립서버 프로세스, TUI, 실행 중인 세션opencode.json, AGENTS.md 밖의 설정, MCP 서버 목록, 플러그인을 고쳤을 때
/restart공유 백그라운드 서버 프로세스 자체TUI(자동으로 다시 붙음), 영구 터미널(인계 시도)서버가 이상하게 굳었을 때, 서버 쪽 환경 변수를 바꿨을 때
/update새 버전을 설치. "Restart" 버튼은 TUI를 종료만 함—새 버전으로 올릴 때. 종료 후 opencode를 직접 다시 실행

예 1 — MCP 서버를 하나 추가했다. opencode.json의 mcp에 서버를 적고 저장한 뒤 TUI에서 /reload를 입력합니다. "Configuration reloaded" 알림이 뜨면 끝입니다. 서버를 껐다 켤 필요가 없습니다. 일하던 에이전트도 멈추지 않고, 다음 스텝 경계부터 새 서비스로 이어서 일합니다(8장의 "스텝 경계"가 여기서도 기준입니다).

예 2 — 응답이 아예 오지 않는다. 이럴 때는 /restart입니다. TUI는 살아 있는 채로 "Restarting service…"를 띄우고, 서버가 새로 뜨면 스스로 다시 연결합니다. 세션은 이벤트 로그로 디스크에 있으므로(6장) 서버를 다시 띄워도 대화가 사라지지 않습니다.

주의/reload는 대기 중이던 권한 질문과 폼을 취소합니다. 에이전트가 "이 명령을 실행해도 될까요?"라고 묻고 있을 때 리로드하면 그 질문은 사라지므로, 답을 먼저 하고 리로드하십시오. /restart는 관리형 서비스로 붙었을 때만 보입니다. --server <url>로 원격 서버에 붙었다면 이 명령 자체가 없습니다(그 서버는 그쪽에서 관리합니다).

그림 4-2 "먼저 바인드, 나중에 부팅" 순서

왜 먼저 바인드할까요? 바인드는 단일 인스턴스 락 역할을 합니다(4.3절). 부팅에는 데이터베이스 마이그레이션과 플러그인 로딩 때문에 시간이 걸리는데, 그동안 포트를 비워 두면 다른 경쟁자가 끼어들 수 있습니다. 먼저 자리를 잡고 503으로 "곧 됩니다"라고 알리는 편이 안전합니다.

4.5 HTTP API와 이벤트 전송

  • API: packages/protocol/src/api.ts의 Effect HttpApi가 /api/...에 마운트되고 OpenAPI는 /openapi.json에 있습니다. 새 API는 /api/experimental/<group>/...에서 시작해 안정되면 승격됩니다.
  • 실시간 이벤트: GET /api/event는 SSE입니다. 계약상 "휘발성"이어서, 느린 소비자는 스트림이 끊기고 연결이 끊긴 동안의 이벤트는 놓칩니다. types 필터를 받습니다.
  • 영속 재생: GET /api/experimental/session/:sessionID/log?after=&follow=는 특정 시퀀스 이후의 영속 이벤트를 재생하고 Synced 표지를 보낸 뒤 실시간으로 이어집니다.
  • WebSocket: PTY, 클라이언트 호스팅 MCP, 음성에만 씁니다. 브라우저는 WebSocket에 헤더를 못 붙이므로 단기 일회용 티켓으로 인증합니다.

그림 4-3 서버 범위 이벤트 피드: 공유 인코딩, 연결별 독립 큐

specs/v2/event-stream-architecture.md는 이 구조를 의사결정 기록으로 남겼습니다. 예전에는 연결마다 모든 이벤트를 각자 필터링·인코딩·JSON.stringify했기 때문에, 클라이언트 50개일 때 553.9ms 걸리던 일이 공유 인코딩 후 12.4ms(−97.8%)로 줄었습니다.

왜 PubSub를 쓰지 않았을까요? Effect의 PubSub 전략은 모두 "전체"에 영향을 줍니다. bounded는 가장 느린 구독자 때문에 발행자가 막히고, dropping은 모두에게서 이벤트를 버리며, sliding은 조용히 건너뛰고, unbounded는 메모리 상한이 없습니다. 원하는 성질은 "느린 연결 하나만 끊고 나머지는 순서대로 계속"이었고, 그래서 연결별 독립 큐를 택했습니다. 하나의 불변 문자열을 큐마다 참조만 하므로 50 × 4096개여도 약 1.6MiB입니다.
영속 재생 실사용 예: 자리를 비웠다가 이어 보기 노트북 TUI에서 "로그인 페이지를 다크 모드로 바꾸고 테스트까지 돌려 줘"라고 맡기면, 일은 백그라운드 서버가 하고 TUI는 GET /api/event(SSE)로 진행 상황을 받아 보여 줍니다. 도중에 노트북 뚜껑을 닫으면 SSE 연결이 끊겨 그동안의 이벤트는 노트북에 전달되지 않습니다. 그래도 서버는 계속 일하고, 파일 편집이나 테스트 재시도 같은 이벤트는 SQLite에 차례로 기록됩니다. 다시 연결한 클라이언트는 마지막으로 받은 시퀀스(예: 120)부터 log?after=120&follow=true로 재생을 요청해 놓친 이벤트를 순서대로 받고, Synced 표지가 온 뒤부터는 실시간 진행을 그대로 이어서 봅니다. 서버가 과거 기록을 읽기 전에 구독부터 걸어 두므로 재생과 실시간 사이에 빠지는 이벤트가 없고, 겹쳐 온 이벤트는 시퀀스 번호로 걸러집니다(6.4절).

4.6 인증과 페어링

  • Basic 인증: 사용자명 opencode, 비밀번호는 OPENCODE_PASSWORD(구 이름 OPENCODE_SERVER_PASSWORD). ?auth_token=(base64 user:pass)도 받습니다.
  • 페어링: opencode pair → POST /api/pair가 5분짜리 일회용 코드를 발급하고, 연결 URL이 이를 30일 HMAC 세션 쿠키로 교환합니다. 쿠키는 서버 비밀번호에서 파생된 키로 서명되므로 비밀번호를 바꾸면 모든 세션이 폐기됩니다.
  • 쿠키 이름에는 포트가 들어갑니다. 브라우저는 같은 호스트의 포트 간에 쿠키를 공유하기 때문입니다.
  • 임베디드 SDK는 password: Option.none()으로 인증 없이 라우터를 씁니다.

페어링은 비밀번호를 새 기기에 넘기지 않고도 그 기기를 서버에 접속하게 해 주는 방법입니다. 과정은 두 단계입니다.

  1. 코드 받기: 비밀번호를 이미 아는 CLI가 opencode pair로 서버에서 5분 동안만 쓸 수 있는 일회용 코드를 받습니다.
  2. 세션으로 바꾸기: 이 코드가 든 연결 URL을 링크나 QR로 새 기기에 넘기면, 새 기기는 코드를 30일짜리 세션(브라우저는 쿠키, 앱은 토큰)으로 교환합니다.

새 기기가 손에 쥐는 것은 일회용 코드와 세션뿐이므로 비밀번호는 한 번도 보지 않습니다. 그림 4-4는 이 흐름을 요청 단위로 보여 줍니다.

이렇게 씁니다 — 다른 기기에서 이어 보기: /pair (/web)

서버가 하나이고 모든 화면이 같은 이벤트 로그를 구독하므로(4.5절), 휴대폰이나 다른 PC의 브라우저도 "또 하나의 화면"으로 붙을 수 있습니다. 페어링이 그 입구입니다.

  1. TUI에서 /pair를 입력합니다. 대화상자에 "This device" 링크, 서버 주소별 링크 목록, 그리고 첫 링크의 QR 코드가 나옵니다.
  2. 휴대폰 카메라로 QR을 찍으면 /auth/connect/<코드> 링크가 열리고, 그 기기가 인증됩니다.
  3. 이제 휴대폰에서도 지금 돌고 있는 세션의 진행을 그대로 보고, 권한 질문에 답할 수 있습니다.

예 — 긴 리팩터링을 맡기고 자리를 비운다. 출발 전에 /pair로 휴대폰을 붙여 두면, 에이전트가 권한을 물어 멈춰 섰을 때 밖에서 바로 허용할 수 있습니다. 4.5절의 "자리를 비웠다가 이어 보기"를 실제로 쓰는 방법입니다.

주의링크는 한 번만 쓸 수 있고 몇 분 뒤 만료됩니다("Links work once and expire in N minutes"). 서버가 루프백(127.0.0.1)에서만 듣고 있으면 다른 기기는 닿지 못합니다. 이때 대화상자가 안내하는 대로 opencode service set hostname 0.0.0.0으로 바꿔야 하는데, 이는 같은 네트워크의 누구나 서버 포트에 접근을 시도할 수 있게 된다는 뜻입니다. 믿을 수 있는 네트워크에서만 여십시오.

4.7 데스크톱·웹·PTY 데몬

이 절의 요지는 한 문장입니다. 화면이 무엇이든 실제 일은 하나의 백그라운드 서버가 맡고, 그 서버가 바뀌거나 옮겨 가도 사용자 작업은 끊기지 않습니다. 웹·데스크톱·터미널은 이 원칙이 드러나는 세 장면입니다.

  • 웹: 서버가 번들된 @opencode/app을 직접 서빙합니다. API 인증보다 먼저 웹 셸을 내려보내, 로그인되지 않은 브라우저가 브라우저 기본 팝업이 아닌 앱 자체의 로그인 화면을 보게 합니다.
  • 데스크톱: Electron 메인 프로세스가 CLI 바이너리로 serve --service를 Service.ensure합니다. 즉 TUI와 같은 서비스를 씁니다. 서비스가 옮겨 가면 모든 창의 요청과 이벤트 스트림이 새 주소로 이동합니다.
  • PTY 핸드오프: Rust 데몬은 소유 연결을 잃으면 터미널을 멈추지만, 소유자가 먼저 prepare_handoff를 보내면 120초짜리 티켓을 받아 후임 서버가 이어받습니다(OPENCODE_PTY_HANDOFF). 서버를 업그레이드해도 셸이 살아남는 이유입니다.

PTY 핸드오프는 웹앱 전용 기능이 아닙니다. 화면이 TUI든 데스크톱이든 웹이든, 백그라운드 서버 프로세스를 새 것으로 바꿀 때(업그레이드 등) 일어납니다. 터미널을 쥐고 있는 쪽이 화면이 아니라 서버 쪽 Rust 데몬(opencode-pty)이기 때문입니다. 데몬에는 소유 연결이 하나뿐이고, 그 연결이 끊기면 데몬과 터미널이 함께 멈춥니다. 그래서 교체는 다음 순서로 진행됩니다.

  1. 기존 서버를 멈추기 전에 소유 연결로 prepare_handoff를 보내 120초 동안 유효한 티켓을 받고, 이를 파일로 공개합니다.
  2. 새 서버는 OPENCODE_PTY_HANDOFF 환경 변수로 티켓을 넘겨받아 같은 데몬의 소유권을 가져옵니다. 티켓은 원자적으로 소비되므로 후임은 하나뿐이고, 밀려난 옛 연결은 더 이상 데몬을 멈추지 못합니다.
  3. 티켓을 받지 못하면 교체를 막지 않습니다. 터미널을 정리한 뒤 핸드오프 없이 서비스를 교체합니다. 터미널은 최선 노력(best-effort)의 대상이기 때문입니다.

데몬 쪽 규칙(소유 연결, 120초 티켓, 단일 후임)은 packages/process-daemon/README.md에 정리되어 있습니다.

여기서 '터미널'이 무엇을 가리키는지 구분해 두어야 합니다. TUI는 사용자가 Windows Terminal의 PowerShell 같은 내 셸에서 opencode를 실행해 띄운 화면일 뿐이고, 핸드오프로 살아남는 것은 그 셸이 아닙니다. 살아남는 것은 서버가 PTY 데몬을 통해 따로 띄운 서버 쪽 셸 프로세스입니다. 이 셸은 두 경로로 쓰입니다.

  • 터미널 패널: TUI에서는 <leader>t(기본값은 Ctrl+X 다음 T)로, 웹·데스크톱에서는 터미널 독으로 엽니다. 어느 화면이든 같은 서버의 persistentPty API를 쓰고, 패널의 입출력은 WebSocket으로 오갑니다(4.5절). 패널은 세션에 묶여 있으므로 npm run dev를 띄워 두면 TUI를 닫아도 서버 쪽에서 계속 돕니다.
  • 에이전트의 shell 도구: 에이전트가 실행하는 npm test, pip install 같은 명령도 내 셸이 아니라 서버 쪽에서 돕니다. 로컬 Location이고 데몬을 쓸 수 있으면 PTY 데몬에서 실행되어 서버가 재시작된 뒤에도 이어집니다(11.7절).

명령이 실행되는 곳은 언제나 서버가 도는 컴퓨터입니다. 기본 모드에서는 서버가 내 PC의 백그라운드 서비스이므로 결국 내 PC에서 실행되지만, --server로 원격 서버에 붙었다면 그 원격 컴퓨터에서 실행됩니다(4.2절). 그림 4-5는 이 관계를 정리한 것입니다. 실선은 평소 흐름이고, 점선은 서버를 업그레이드할 때의 핸드오프입니다.

그림 4-5 TUI·내 셸·서버·PTY 데몬의 관계

이렇게 씁니다 — 세션 옆에 터미널 열기: /terminal

터미널은 세션 ID로 묶여 있어 세션을 지우면 함께 지워집니다. 서버가 영구 PTY를 지원하지 않으면 이 명령은 보이지 않습니다. 또 터미널은 만들 때의 디렉터리를 계속 쓰므로, 나중에 /cd로 세션을 옮겨도 이미 열린 터미널은 따라오지 않습니다.
