"범위가 Location"이란? 쉽게 말하면 Location은 "어느 폴더에서 일하느냐"입니다. 서버는 폴더마다 그 폴더 전용 작업 도구 세트(설정, 도구, 권한, 모델, SessionRunner)를 따로 준비해 둡니다. 그래서 /repo/a에서 만든 세션은 /repo/a의 세트로만 일하고, 같은 폴더의 세션끼리는 그 세트를 함께 씁니다. 반면 접수(SessionInbox)와 실행 관리(SessionExecution)는 폴더와 상관없이 서버 전체에 하나뿐입니다.
왜 셋으로 나눴을까요? V1도 메시지는 데이터베이스에 저장했습니다. 다만 저장된 입력을 누가 언제 처리할지는 메모리 안에서 도는 SessionPrompt.loop의 while(true)에 달려 있었습니다. 그래서 일하는 도중 새 입력이 오거나 프로세스가 죽으면, 입력은 남아도 그것을 처리할 실행이 뒤따른다는 보장이 약했습니다. V2는 입력을 "아직 전달되지 않은 일"로 실행보다 먼저 기록하고, "지금 실행 중"이라는 사실도 클레임으로 디스크에 남깁니다. 핵심은 저장 자체가 아니라 입력이 어떤 상태인지, 누가 실행을 맡았는지, 죽으면 어디서 다시 시작할지가 명시된다는 점입니다. 덕분에 실행 제어는 "지금 누가 돌리고 있나"만, 러너는 "한 스텝을 어떻게 돌리나"만 신경 쓰면 됩니다. specs/v2/session.md의 첫 절 제목이 바로 "Prompt Admission Precedes Execution(접수가 실행에 앞선다)"입니다.

7.2 Session 파사드와 ID 바인딩 연산

session.ts의 Session.Service는 전역 노드입니다. 목록·생성·포크·삭제 같은 컬렉션 연산은 직접 하고, 세션 하나에 대한 연산(prompt, shell, compact, interrupt, revert 등)은 session/session.ts의 forSession(id)에 위임합니다.

prompt의 정확한 순서

prompt는 Effect.uninterruptibleMask 안에서 돕니다. 1~5는 영속 접수, 6은 권고적 스케줄링입니다.

  1. admission.reconcile: 이 메시지 ID가 이미 접수(또는 승격)됐으면 그대로 반환 — 재시도 멱등성.
  2. SessionPrompt.prepare: 플러그인 훅 session.prompt, 첨부 파일 구체화(동시성 8), 스킬 해석.
  3. 되돌리기 확정: 파일만 과거로 돌려 둔(스테이징된) revert가 있으면, 접수 전에 그 시점 이후의 대화 기록까지 지워 확정(커밋)합니다. 그래서 새 메시지는 되돌린 시점 바로 뒤에 이어집니다(11.9절).
  4. admission.admit → InboxEnqueued 발행.
  5. 기본 전달 방식은 "steer".
  6. resume !== false이면 execution.wake(sessionID).

왜 uninterruptible일까요? 클라이언트가 요청 도중 연결을 끊어도 "접수됐는데 반쯤만 기록된" 상태가 생기면 안 됩니다. 접수 구간을 중단 불가로 묶고, 실행 시작(wake)은 별개의 권고로 둡니다. 그래서 클라이언트는 같은 메시지 ID로 안심하고 재시도할 수 있습니다.
이렇게 씁니다 — 세션 고르기·새로 시작하기: /sessions · /new · /clear · /rename

그림 7-4 promote의 결정 규칙

제어 항목(compaction, move)은 "전달 경계"가 됩니다. 정렬 규칙도 섬세합니다.

session/inbox.ts — pendingSteers// A move changes the context's Location: never pull compaction across it.
// Within that boundary, compact before promoting even earlier steers so
// their text stays verbatim after the checkpoint, not inside its summary.

압축 요청은 앞선 steer보다 먼저 처리됩니다. 그래야 그 steer 텍스트가 요약 속에 뭉개지지 않고 체크포인트 뒤에 원문 그대로 남습니다. 단 디렉터리 이동(move)을 가로질러 당기지는 않습니다.

멱등성과 직렬화

  • "첫 접수가 이긴다": 같은 ID·세션·타입이면 기존 항목 반환, 다른 세션/타입 재사용은 LifecycleConflict.
  • 전달 후에는 투영된 메시지와 대조해(promotedFromMessage) inbox 행이 사라진 뒤에도 재시도가 동작합니다.
  • 세션별 KeyedMutex(SessionInbox.serialized) 아래서 모든 변경과 러너의 경계 결정이 직렬화됩니다.
  • 압축 접수는 합쳐집니다(coalesce). 이미 대기 중이면 두 번째를 만들지 않습니다.
  • steer로 바꾸는 변경은 성공 후 실행을 깨우고, queue로 바꾸기와 취소는 깨우지 않습니다.
이렇게 씁니다 — 일하는 에이전트에게 말 걸기: Enter · ctrl+x Enter · Esc · /btw

위에서 본 steer와 queue는 TUI에서 이렇게 고릅니다. 에이전트가 일하는 중에도 프롬프트 칸은 막히지 않습니다.

지금 일이 끝난 뒤에 할 일 맡겨 두기ctrl+x Enterqueue로 접수 → 유휴 경계에서 하나씩
맡겨 둔 일 보기·고치기·지우기ctrl+x q대기 목록. 항목에서 ctrl+u 되돌리기, ctrl+d 삭제

예 1 — 방향 수정(steer). 에이전트가 테스트를 돌리려고 npm test를 준비하는 게 보입니다. 이 프로젝트는 pnpm을 씁니다. 프롬프트에 "npm 말고 pnpm으로 돌려"라고 치고 Enter를 누르면, 에이전트는 지금 스텝을 마친 직후 이 말을 읽고 다음 스텝부터 pnpm을 씁니다. 하던 일을 버리고 처음부터 다시 시작하지 않습니다.

예 2 — 다음 일 맡겨 두기(queue). 에이전트가 API를 고치는 중인데, 끝나면 문서도 갱신하게 하고 싶습니다. "끝나면 README의 API 절도 고쳐 줘"를 치고 ctrl+x Enter를 누릅니다. 지금 일에는 끼어들지 않고, 이 일이 끝나 유휴 상태가 되면 그때 시작합니다. 여러 개를 쌓아 두면 하나씩 차례로 처리합니다.

예 3 — 곁가지 질문(/btw). 작업 중에 "이 프로젝트에서 Effect.gen은 왜 쓰는 거야?"가 궁금해졌습니다. 그냥 물으면 그 질문과 답이 대화 이력에 들어가 에이전트의 맥락을 흐립니다. /btw Effect.gen은 왜 쓰는 거야?라고 보내면, 지금 세션의 맥락(시스템 프롬프트와 이력)을 그대로 보고 한 번만 답한 뒤 모달 창으로 보여 줍니다. 이력에는 아무것도 남지 않고, 도구도 쓰지 않습니다. 비용은 세션 사용량에 더해집니다. 답 창에서 c를 누르면 복사됩니다.

참고슬래시 명령은 queue로 맡길 수 없습니다("This prompt cannot be queued"). 압축(/compact)이나 폴더 이동(/cd)은 그 자체가 inbox의 제어 항목으로 들어가 경계를 만들기 때문입니다(위 그림 7-4).

왜 "종료 훅"이 아니라 "데이터베이스의 속성"일까요? SIGKILL이나 정전에서는 종료 훅이 돌지 않습니다. "실행 중"이라는 의도를 시작 이벤트와 같은 트랜잭션에 미리 써 두고, 정상 종료 때만 지우면, 남아 있는 클레임 자체가 "비정상 종료됐다"는 증거가 됩니다. 복구를 신뢰할 수 없는 훅이 아니라 디스크 상태로부터 도출합니다.

부팅 시 복구: SessionRestart

  1. 부모가 삭제된 고아 자식 클레임, 취소된 서브에이전트 자식의 클레임 해제.
  2. 셸·이미지 작업 결과 복구. 영속 데몬에서 아직 도는 셸은 다시 연결(ShellTool.reattach), 아니면 알림을 합성 메시지로 투입.
  3. 죽은 서버가 running으로 남긴 포그라운드 셸 호출은 "백그라운드로 이동"으로 정착.
  4. 서브에이전트: 끝난 자식은 outbox 재생, 실행 중이던 자식은 재개 준비(시도 횟수 계산).
  5. 직접 구동된 중단 세션: 시도 횟수 +1, "서버가 재시작되었습니다. 이미 끝낸 일을 반복하지 말고 이어서 하세요"라는 합성 메시지 투입 후 재개.
  6. 마지막에 자식 작업 시작 — 부모의 예산이 먼저 차감되도록.
  • 턴당 재개 한도 DEFAULT_MAX_ATTEMPTS = 10. 넘으면 "반복 중단되어 자동 재개하지 않습니다"로 실패 처리.
  • 보장 수준은 at-least-once입니다. "로컬 조정은 동시 drain을 막을 뿐, 크래시 후 외부 부작용의 반복까지 막지는 않습니다."
  • 매 drain 시작마다 settleStaleToolCalls가 진행 중으로 남은 도구 호출을 aborted로 실패 처리합니다. 애매한 부작용을 직접 재실행하지 않고 모델에게 맡깁니다.
이렇게 씁니다 — TUI를 닫아도 일은 계속된다

클레임과 이벤트가 먼저 디스크에 쓰이고, 실행은 TUI가 아니라 백그라운드 서버에서 돌기 때문에 다음 사용법이 안전합니다.

  • 긴 작업을 맡기고 TUI를 닫아도 됩니다. 에이전트는 서버에서 계속 일합니다. 다시 opencode를 띄워 /sessions(ctrl+x l)로 그 세션을 열면, 그동안 쌓인 진행이 그대로 보입니다.
  • 서버가 죽어도 대부분 이어집니다. 서버가 다시 뜨면 남아 있는 클레임을 보고 끊긴 실행을 재개합니다. 사용자가 할 일은 세션을 다시 여는 것뿐입니다.
  • 노트북 덮개를 닫는 것도 같은 원리입니다. 다만 서버도 같은 노트북에서 돈다면 잠자는 동안은 당연히 멈춥니다. 다시 깨어나면 경계에서 이어 갑니다.

V1도 에이전트 루프는 TUI 화면 코드가 아니라 서버 쪽에서 돌았습니다. 다만 그 서버가 TUI 프로세스 안에 Bun Worker로 내장되어 TUI마다 하나씩 떴기 때문에, TUI를 닫으면 내장 서버와 그 안의 루프도 함께 끝났습니다(2.3절 표의 8행). 실행 상태도 메모리(ensureRunning)에만 있어서 다시 열어도 끊긴 실행을 이어 갈 근거가 없었습니다(같은 표의 4행). "닫아도 된다"는 감각이 V2 사용법의 가장 큰 변화입니다.

7.7 affinity와 background: 이어진 세션의 캐시와 남은 일

세션은 혼자 있지 않습니다. 서브에이전트는 부모 세션 아래 자식 세션으로 생기고(12장), /fork는 원본에서 갈라진 세션을 만듭니다. 이렇게 이어진 세션들 사이에서 OpenCode가 챙기는 것이 두 가지 있습니다. 하나는 프롬프트 캐시를 같이 쓰게 묶는 일(affinity), 다른 하나는 아직 끝나지 않은 일을 모아 보는 일(background)입니다.

세션 ID는 누가 만드나

세션 ID는 ses_ + 26자입니다. 앞 12자리는 현재 시각을 비트 반전한 값이라 최근 세션일수록 사전순으로 앞에 오고(정렬만 해도 최신순), 뒤 14자는 랜덤입니다. 이벤트·메시지 ID(evt_, msg_)는 반대로 오름차순입니다.

core/src/session.ts — Session.createconst sessionID = input.id ?? SessionSchema.ID.create()   // 받은 ID가 있으면 그것을, 없으면 서버가 생성
const recorded = yield* store.get(sessionID)
if (recorded) return recorded                              // 같은 ID면 기존 세션 반환

자식과 포크도 자기 ID는 따로 받고, 캐시 라우팅 키만 원본의 것을 빌려 씁니다. 이 키는 모델 요청마다 헤더(x-session-affinity, X-Session-Id, x-opencode-session)에 실리고, 지원하는 프로바이더에는 promptCacheKey로도 갑니다(자기 ID는 x-opencode-session-id로 따로 실림).

세션 ID는 맥락(context)에 들어가지 않습니다

요청을 편지에 비유하면, 모델이 읽는 맥락은 본문(시스템 프롬프트, 대화 이력, 도구 결과)이고 세션 ID는 겉봉투(HTTP 헤더, 요청 옵션)에 적힌 주소입니다. 토큰을 늘리지도 답을 바꾸지도 않습니다. 하는 일은 프로바이더나 게이트웨이에 "같은 묶음이니 같은 캐시 쪽으로 보내 달라"고 알리는 것뿐이고, 이 힌트를 쓰지 않는 프로바이더는 무시합니다.

그래서 캐시 적중의 조건은 본문 앞부분(prefix)이 같은 것이고, affinity는 그런 요청을 같은 곳으로 보내는 장치입니다. 포크는 이력을 그대로 이어받아 앞부분이 같으므로 이 둘이 맞물려 첫 요청부터 캐시가 적중합니다(9.1절). 참고로 지금 소스는 포크의 포크가 맨 처음 세션이 아니라 바로 위 원본의 키를 씁니다(소스에 "중첩 포크도 루트 키를 쓰게" 하자는 TODO가 있음).

background: 아직 돌고 있는 일의 목록

SessionBackground.outstanding은 한 세션과 그 후손 세션에서 아직 끝나지 않은 일을 모읍니다. ctrl+b로 보낸 백그라운드 셸(11.7절), 이미지 작업, 실행 중인 서브에이전트, 그리고 정리(drain) 중인 자식 실행입니다. 자식이 부모에게 "끝났다"고 보고했어도 그 자식의 백그라운드 셸이 돌고 있으면 목록에 남습니다. 셸이 끝나면 그 알림이 자식을 다시 깨우므로 자식의 일은 아직 끝난 것이 아니기 때문입니다.

이 목록은 서브에이전트의 보고("아직 실행 중인 백그라운드 작업")와 experimental.idle 훅에 쓰입니다. 예를 들어 npm run dev를 ctrl+b로 백그라운드에 보낸 뒤 서브에이전트에게 테스트를 맡기면, 서브에이전트는 자기 일을 마치고도 "dev 서버가 아직 돌고 있다"고 함께 알려 줍니다. 부모 에이전트도 사용자도 다 끝난 줄 알고 넘어가지 않게 하는 장치입니다.

둘 다 새 세션을 만들지만 모델이 보는 맥락이 정반대입니다. 기록은 어느 쪽이든 지워지지 않습니다(7.2절).

예 1 — 비싸게 쌓은 조사를 두 작업으로 나누기. 30분 동안 결제 모듈 구조를 파악시킨 뒤, 원본에서는 테스트를 보강하고 /fork한 세션에서는 API 문서를 씁니다. 둘 다 조사 결과를 알고 있어 다시 읽힐 필요가 없고 캐시도 공유됩니다.

예 2 — 같은 지점에서 프롬프트를 바꿔 다시. 분석은 좋았는데 세 번째 프롬프트("리팩터링해 줘")부터 마음에 들지 않으면, /fork에서 그 프롬프트를 고릅니다. 직전까지 복사된 세션의 입력 칸에 그 프롬프트가 들어오니 "가독성 우선, 공개 API는 유지"처럼 고쳐 보냅니다(11장 되돌리기).

예 3 — 두 설계안을 실제로 비교. 포크한 뒤 /cd로 포크 세션을 다른 워크트리로 옮기고(5.7절), 원본은 안 A, 포크는 안 B로 구현시켜 /diff로 비교합니다.

함정 — 포크는 대화만 복사하고 파일은 복사하지 않습니다포크는 원본과 같은 폴더에서 일합니다. 두 세션이 같은 파일을 고치면 서로 덮어쓰고, 원본이 이미 고친 파일이 포크 지점으로 돌아가지도 않습니다. 같은 파일을 건드릴 갈래라면 워크트리로 나누고(예 3), 파일을 되돌리려면 /undo를 쓰십시오. 짧은 곁질문은 포크보다 /btw가, 큰 작업 전 보험은 스냅샷과 git 커밋이 맞습니다.
