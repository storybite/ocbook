10장 도구 체계와 Code Mode

모델은 글자만 만들어 낼 수 있습니다. 파일을 읽고, 고치고, 명령을 돌리는 일은 모두 도구가 합니다. 이 장은 도구 하나가 어떻게 생겼는지에서 시작해, 도구가 수백 개로 늘어났을 때 쓰는 방법인 Code Mode에서 끝납니다.

이 장의 구성 모델이 받은 도구 결과는 모두 다음 요청의 입력, 곧 컨텍스트에 쌓이고, 컨텍스트는 크기가 정해져 있습니다. 이 장의 장치들은 대부분 "모델의 컨텍스트를 어떻게 아낄까"에 대한 답이기도 합니다.

10.1 도구는 하나의 구조적 값

실제 장면: "package.json 보여 줘"

사용자가 TUI에 이렇게 입력했다고 합시다.

package.json에 어떤 스크립트가 있는지 알려 줘

모델은 글로 대답하기 전에 먼저 도구 호출을 하나 만듭니다. 모양은 대략 이렇습니다.

모델이 만드는 도구 호출 (단순화){ "name": "read", "input": { "path": "package.json" } }

OpenCode는 read 도구를 실행해 파일 내용을 돌려주고, 모델은 그 내용을 읽은 뒤 "dev, build, test 세 개가 있습니다"라고 답합니다. 사용자는 한 번 물었지만 안에서는 모델이 두 번 불렸습니다. 첫 번째 호출에서 모델은 도구 호출을 만들고, OpenCode가 도구를 실행한 뒤, 두 번째 호출에서 모델이 결과를 읽고 답합니다. 모델 호출 한 번을 스텝이라고 부르므로(8.1절) 이 장면은 스텝 두 개입니다.

도구 하나를 이루는 것

V2에서 내장 도구, MCP 서버의 도구, 플러그인이 만든 도구는 모두 같은 모양의 값입니다. 출처가 달라도 같은 길로 실행되므로, 권한 검사나 훅도 똑같이 적용됩니다.

packages/schema/src/tool.tsexport type Info<Input, Output> = {
  readonly name: string          // 모델이 부르는 이름: "read"
  readonly input: Input          // 입력 스키마: { path: string, offset?: number, ... }
  readonly freeform?: Freeform   // 입력을 JSON 대신 원문으로 받는 방식(10.5절)
  readonly description: string   // 모델이 읽는 사용 설명서
  readonly execute: (input, context: Context) => Effect.Effect<Result<Output>, Error>  // 실제 일
  readonly output?: Output       // 출력 스키마(Code Mode용)
  readonly options?: Options     // 네임스페이스·권한·Code Mode 여부 등
}

타입 선언이 낯설다면 주석만 읽어도 됩니다. name은 모델이 부르는 이름, input은 모델이 채울 입력 칸, description은 모델이 읽는 사용 설명, execute는 OpenCode가 실제로 하는 일입니다.

결과는 세 갈래로 나뉜다

도구가 일을 마치면 결과를 받는 쪽에 따라 세 갈래로 나눠 돌려줍니다. 이 분리가 도구 체계 전체의 핵심이고, 기계용 값 채널인 output은 10.6절 Code Mode에서 진가가 드러납니다.

채널누가 보나쉽게 말하면내용
outputCode Mode 프로그램기계가 계산에 쓰는 값스키마로 검증된 구조화 값. 저장하지 않음
content모델, 영속 저장모델이 읽는 보고서문자열 또는 텍스트/파일 파트
metadataUI화면에 그릴 재료diff, 잘림 여부 같은 간결한 JSON

예를 들어 edit 도구로 파일 한 줄을 고치면, 모델은 content로 "고쳤다"는 짧은 보고를 받고, TUI는 metadata에 담긴 diff로 빨강·초록 줄을 그립니다. 모델은 다음 작업을 정하는 데 "고쳤다"는 사실만 알면 되지만, 사용자는 무엇이 바뀌었는지 눈으로 봐야 합니다. 결과 하나로 둘을 다 만족시킬 수 없어서 모델용과 화면용을 따로 담은 것입니다.

왜 output과 content를 나눴을까요? 모델에게는 사람이 읽기 좋은 텍스트가, 프로그램에게는 구조화된 값이 필요합니다. 하나로 합치면 모델용 텍스트를 프로그램이 파싱하거나, 프로그램용 JSON을 모델이 읽어야 합니다. 둘을 나누면 Code Mode 스크립트는 output으로 정확히 계산하고, 최종 요약만 content로 모델에게 갑니다(10.6절).

그 밖의 구성 요소

여기부터는 플러그인으로 도구를 직접 만들 때 필요한 내용입니다. 사용만 한다면 아래 실패 종류 표만 읽고 넘어가도 됩니다.

  • 스키마: Effect Schema, Standard Schema(Zod·ArkType 등), 원시 JSON Schema(MCP)를 모두 받습니다. 플러그인 작성자는 익숙한 라이브러리로 입력 칸을 정의하면 됩니다.
  • Context: 실행 중인 도구가 받는 주변 정보입니다. {sessionID, agent, messageID, id, progress(update), cancel?}. progress로 "30% 진행" 같은 중간 상황을 화면에 보낼 수 있습니다.
  • 취소: 사용자가 Esc로 멈추면 cancel을 기다리는 도구는 "여기까지 했다"는 부분 결과로 실패할 수 있고, 기다리지 않는 도구는 그냥 중단됩니다.
  • Options: {namespace?, permission?, codemode?, pinned?}. 어느 묶음에 속하는지, Code Mode 뒤에 숨길지 등을 정합니다.

실패도 종류를 구분합니다. 이 구분이 실제 사용에서 무엇을 뜻하는지 예로 보면 이렇습니다.

중단과 결함은 절대 모델에게 보이는 실패로 바꾸지 않습니다. 사용자가 멈췄는데 모델이 "오류가 났으니 다시 해 보겠습니다"라며 계속 달리면 안 되기 때문입니다.

10.2 레지스트리와 스냅숏

등록된 모든 도구를 모아 두는 곳이 레지스트리입니다. 그런데 모델에게 매번 레지스트리 전체를 보여 주지는 않습니다. 요청을 보낼 때마다 "이번에 보여 줄 도구 목록"을 따로 만드는데, 이것이 스냅숏입니다. 에이전트 규칙과 Code Mode 설정에 따라 이번 요청에 맞는 도구만 담습니다.

이 절에는 비슷한 이름이 셋 나옵니다. 먼저 구분해 두면 편합니다.

이름무엇인가

스냅숏이번 요청에 모델에게 줄 도구 구성(직접 도구 정의 + execute)
인벤토리 / 카탈로그인벤토리는 Code Mode 뒤에서 execute로 부를 수 있는 도구 집합, 카탈로그는 그 집합을 모델에게 보여 주는 요약 목록(10.6절)
비유: 식당 메뉴판

식당 메뉴판에 빗대어 보면, 주방 장부에 적힌 요리 전체가 레지스트리입니다. 이번 손님(에이전트)에게 금지된 요리를 빼고 남은 요리는 단품과 세트로 나뉩니다. 세트(execute)로만 주문할 수 있는 요리 전체가 인벤토리이고, 그 요리들을 짧게 줄여 메뉴판에 적은 안내문이 카탈로그입니다. 단품 목록과 세트 주문 한 줄을 함께 담아 이번 손님에게 건네는 메뉴판이 스냅숏입니다. 아래 예는 GitHub·math MCP 서버가 연결되어 있고 이번 에이전트에게 webfetch가 금지된 경우입니다(서버·도구 이름은 설명용).

카탈로그에 적히지 않은 github 요리 18가지도 인벤토리에는 있으므로 모델이 execute 안에서 search로 찾아 부를 수 있습니다. github·math·opencode는 인벤토리의 도구를 출처별로 나눈 칸(네임스페이스)입니다.

레지스트리는 Location 범위입니다. Location은 OpenCode가 지금 작업 중인 디렉터리(프로젝트)를 가리키는 단위라서, 같은 OpenCode라도 프로젝트마다 도구 구성이 다를 수 있습니다. 예를 들어 A 프로젝트의 .opencode/plugins/에 둔 도구는 B 프로젝트 세션에는 나타나지 않습니다. 도구 등록은 State 변환, 즉 "현재 도구 목록에 이 도구를 더한다"는 변경을 레지스트리에 적용하는 방식으로 이루어집니다(5.8절). 이름은 /^[A-Za-z0-9_-]+$/로 정규화되고, execute라는 이름은 Code Mode용으로 예약되어 있습니다. 잘못된 등록은 로그만 남기고 건너뛰므로, 플러그인 하나가 이상해도 나머지 도구는 정상적으로 뜹니다.

표의 세 번째 행을 보면, 도구는 정의가 그대로 요청에 실리는 것(직접 도구)과 요약 목록에만 실리고 execute 안에서 부르는 것(Code Mode)으로 갈립니다. 왜 이렇게 나누는지는 10.6절에서 봅니다.

①의 execute 정의는 Code Mode가 켜졌는지(execute가 통째로 거부되지 않았는지)만 보고 넣습니다. 인벤토리로 간 도구가 있는지는 따지지 않으므로, 모든 도구가 codemode: false라서 인벤토리가 비어 있어도 목록 끝에는 execute 정의가 실립니다(v2 packages/core/src/tool.ts의 스냅숏 생성 부분).

카탈로그는 LLM이 쓰는 글이 아니라 OpenCode 코드가 규칙대로 만드는 값입니다. summarize가 인벤토리를 받아 Summary 구조체 { total, namespaces }를 만들고, 네임스페이스마다 name, description(선택), 전체 도구 경로 tools, 실제로 보여 줄 줄 entries를 담습니다. 네임스페이스 줄(- github (24 tools, 6 shown) // 설명)은 모두 넣고, 도구 줄(- 시그니처 // 설명 첫 줄)은 2,000토큰 예산 안에서 네임스페이스마다 경로순으로 하나씩 돌아가며 고릅니다. 이 토큰 수는 모델이나 토크나이저로 센 값이 아니라, 글자 수를 4로 나눠 반올림한 어림값입니다(CHARACTERS_PER_TOKEN = 4). 그래서 모델을 부르지 않고도 바로 계산할 수 있고, 같은 입력이면 늘 같은 결과가 나옵니다. 모델에게 보낼 때는 render가 이 구조체를 줄 단위로 펼쳐 줄바꿈으로 이은 문자열 하나로 바꿉니다(v2 packages/core/src/codemode/catalog.ts, instructions.ts). 모델 호출이 끼지 않으므로 도구 구성이 같으면 카탈로그도 글자 하나까지 같습니다. 도구 하나에 담기는 정보도 직접 도구 정의(이름·설명 전문·입력 JSON Schema 전체)보다 훨씬 적습니다(10.6절).

  • 표의 첫 번째 행처럼 deny 규칙으로 도구를 목록에서 빼는 것(그림 10-1의 "카탈로그에서 숨김")은 권한이 아닙니다. 필터링은 "목록에 보이느냐"(카탈로그 가시성)일 뿐 "실행해도 되느냐"(실행 권한)가 아닙니다(tool/AGENTS.md). 실제 권한은 도구를 실행할 때 다시 검사합니다. 목록 단계를 어떻게든 통과해도 실행 단계에서 다시 막힙니다.
심화: 도구 목록을 한 글자도 바꾸지 않는 이유 프로바이더는 요청의 앞부분이 지난번 요청과 글자 하나까지 같으면, 그 부분을 캐시에서 꺼내 써서 비용과 시간을 줄여 줍니다(9장). 도구 목록은 요청의 앞부분에 들어갑니다. 그래서 스텝마다 목록이 조금이라도 달라지면 캐시가 깨집니다. 이를 막으려고 OpenCode는 카탈로그·인벤토리·execute 정의를 한 번 만들면 저장해 두고, 레지스트리가 바뀌지 않았고 도구 구성도 같으면 그대로 다시 씁니다. 도구 스키마(JSON Schema)도 매번 똑같은 모양이 되도록 미리 정리합니다. 겹겹이 쌓인 allOf를 한 겹으로 펼치고, 같은 스키마 안의 $ref 참조를 실제 내용으로 바꿔 넣고, Effect가 Schema.Int에 자동으로 붙이는 안전 정수 범위 표시를 지웁니다. 마지막 것은 소스 주석의 표현대로 "도구 스키마가 바뀌어 캐시가 깨지지 않도록"입니다.

모델에 맞춰 도구 모양 바꾸기

스냅숏을 보내기 직전, 내장 플러그인들이 요청 훅(15.7절)으로 목록을 조금씩 손봅니다. 사용자가 무엇을 하지 않아도 모델과 환경에 맞게 바뀝니다. 다만 표의 마지막 플러그인은 끼어드는 때가 다릅니다. 앞의 셋은 모델에게 보내는 것(도구 목록)을 고치고, 마지막 하나는 모델이 보내온 것(도구 호출 입력)을 실행 직전에 고칩니다. 그래서 표에 "언제" 열을 따로 두었습니다.

플러그인언제무엇을 하나사용자가 겪는 일
patch.ts요청 조립 직후(context·compaction·generate 훅)GPT 계열(이름에 gpt- 포함, oss·gpt-4 제외)이면 edit/write를 지우고 patch만 남김. 그 밖의 모델은 patch를 지움모델을 GPT로 바꾸면 파일 수정이 "패치 적용" 형태로 표시됨. 모델이 훈련된 편집 방식에 맞춘 것
websearch.ts요청 조립 직후(같은 세 훅)웹 검색이 꺼져 있거나 프로바이더가 없으면 websearch 제거모델이 없는 검색을 시도하다 실패하는 일이 없음
shell.ts요청 조립 직후(같은 세 훅)설명에 OS와 셸 이름을 넣음Windows PowerShell에서는 모델이 ls·grep 대신 PowerShell 문법을 쓸 가능성이 높아짐
tool-input-repair.ts도구 실행 직전·직후(tool.execute.before·after 훅)문자열로 감싼 객체, "20"→20, null 자리표시자를 스키마가 의도를 확정할 때만 고침. bash라는 도구가 없으면 shell로 돌려 실행하고, 결과에 "shell을 직접 부르라"는 문장을 덧붙임모델이 limit: "20"처럼 사소하게 틀려도 재시도 없이 그냥 실행됨. bash를 부른 모델도 다음부터는 shell을 부름

앞의 세 플러그인은 모두 같은 방식으로 만들어져 있습니다.

  1. 세 플러그인(patch.ts·websearch.ts·shell.ts)에는 도구 목록(event.tools)을 고치는 hook 함수가 하나씩 있습니다. 세 플러그인은 이 함수 안에서 목록을 어떻게 고치는지만 다릅니다. 예를 들어 patch.ts의 hook은 GPT 계열 모델이면 edit/write를 지우고, 아니면 patch를 지웁니다.
  2. 이 hook 함수를 ctx.session.hook으로 세 곳에 똑같이 등록합니다. 세 곳 모두 요청이 모델로 나가기 직전에 불리는 지점입니다. "context"는 평소 대화 요청, "compaction"은 긴 대화를 요약하는 요청, "generate"는 플러그인이 대화와 따로 모델에게 묻는 요청(ctx.session.generate)입니다(15.7절).
  3. 그래서 어떤 요청이 나가든 도구 목록이 똑같이 고쳐집니다. GPT 모델이라면 평소 대화 요청에도, 요약 요청에도 edit/write 없이 patch만 실립니다.

아래 코드는 patch.ts만 대표로 보인 것입니다.

v2 packages/core/src/tool/plugin/patch.ts — 도구 목록 훅const hook = (event: SessionHooks["context"]) =>
  Effect.sync(() => {
    const usePatch =
      event.model.id.includes("gpt-") && !event.model.id.includes("oss") && !event.model.id.includes("gpt-4")
    if (usePatch) {
      delete event.tools.edit
      delete event.tools.write
      return
    }
    delete event.tools.patch
  })
yield* ctx.session.hook("context", hook)
yield* ctx.session.hook("compaction", hook)
yield* ctx.session.hook("generate", hook)
목록을 고쳐도 캐시가 깨지지 않는 이유

앞의 세 플러그인은 요청 앞부분인 도구 목록을 바꾸지만, 결과가 모델 이름, 웹 검색 설정과 프로바이더, OS·셸에만 달려 있습니다. 이 값들은 스텝마다 바뀌지 않으므로 매 스텝 같은 목록이 나오고, 앞의 심화 상자에서 본 캐시도 그대로 유지됩니다. 모델을 바꾸면 patch.ts의 결과가 달라지지만, 프로바이더 캐시는 모델별이라 어차피 처음부터 다시 읽습니다(9.1절).

tool-input-repair.ts는 요청을 아예 건드리지 않습니다. 모델이 응답으로 도구 호출을 보낸 뒤, 그 호출을 실행하기 직전에 입력만 고칩니다. bash 별칭도 목록에 bash 도구를 더하는 방식이 아니라, 없는 bash가 호출되었을 때 shell로 돌려 실행하는 방식입니다. Code Mode의 execute 자체는 건너뛰지만, 그 안에서 부르는 도구의 입력은 똑같이 고칩니다. 훅의 짝 구조는 15.10절에서 다룹니다.

출력 잘라내기 — 왜, 어떻게

도구가 돌려준 결과는 다음 스텝에서 모델 입력에 그대로 들어갑니다. 긴 웹 문서나 MCP 도구가 돌려준 큰 응답을 다 넣으면 맥락 창이 금방 차고, 비용이 늘고, 모델이 정작 중요한 부분을 놓칩니다. 원칙은 한 줄로 모델에게는 앞부분과 표지만 주고, 원본은 파일로 빼 둔다입니다. 스텝 러너는 결과를 이벤트로 남기기 직전(그림 10-2의 마지막 단계)에 이 일을 합니다.

packages/core/src/tool-output.tsexport const MAX_LINES = 2_000
export const MAX_BYTES = 50 * 1024 // 50 KiB
export const RETENTION = Duration.days(7)
export const DIRECTORY = "tool-output"
  • 텍스트 파트만 측정하고 앞부분을 남깁니다. 줄/바이트 한도 중 먼저 닿는 곳에서 자소(grapheme) 안전하게 자릅니다. 한글 한 글자가 반으로 잘려 깨지는 일은 없습니다.
  • 표지: [showing lines 1-N of TOTAL (last line cut); full output saved to <file>]. 전체 출력은 ~/.local/share/opencode/tool-output/tool_<id>에 저장되고 7일 후 정리됩니다.
  • 도구가 스스로 결과를 제한하고 metadata.truncated를 설정했으면 건너뜁니다. read, grep, glob, shell이 그렇습니다. 예를 들어 grep은 처음부터 결과를 100개(limit)로 제한합니다. 셸은 오히려 뒷부분을 남깁니다(11장). 테스트 로그나 빌드 오류는 마지막 줄에 핵심이 있기 때문입니다.

그래서 이 공통 잘라내기는 주로 webfetch나 MCP 도구처럼 스스로 길이를 제한하지 않는 도구에서 일어납니다.

실제 장면. "이 라이브러리의 API 레퍼런스 페이지 읽고 retry 옵션 설명해 줘"라며 긴 문서 URL을 주면, 모델은 webfetch를 부릅니다. 마크다운으로 바꾼 페이지가 9,431줄이라면, 2,000줄에 닿기 전에 50 KiB 한도에 먼저 닿아 앞부분 수백 줄만 남습니다. 모델은 그 앞부분과 함께 끝에 다음 표지를 받습니다(표지 형식은 tool-output.ts의 marker, 숫자는 예시).

…(앞부분, 약 50 KiB)…
[showing lines 1-812 of 9431 (last line cut); full output saved to ~/.local/share/opencode/tool-output/tool_…]

모델은 이 표지로 결과가 잘렸다는 것과 전체가 어느 파일에 있는지를 압니다. 찾던 retry 설명이 앞부분에 없으면, 저장된 파일을 grep으로 "retry"만 찾아 그 주변을 read(범위 지정)로 다시 읽습니다. 맥락 창은 지키면서 정보는 잃지 않는 셈입니다.

잘라내기는 컨텍스트를 아끼는 첫 번째 방법이지만 한계가 있습니다. 필요한 내용이 뒷부분에 있으면 모델은 다시 찾아 읽어야 하고, 그만큼 스텝이 늘어납니다. 결과에서 필요한 것만 골라 넘기게 할 수 있다면 더 좋을 것입니다. 그 방법 중 하나가 10.6절의 Code Mode입니다.

이 파일은 프로젝트 밖(데이터 폴더)에 있어서 외부 폴더 접근 권한(external_directory) 검사를 받습니다. 기본 권한은 .env를 빼고 전부 허용이라 보통은 묻지 않고 읽지만, 설정에서 external_directory를 ask나 deny로 바꿨다면 다시 읽을 때 승인 요청이 뜨거나 막힙니다(11.3·11.4절).

한도는 설정으로 바꿀 수 있습니다. 결과를 더 많이 보게 하고 싶다면(그만큼 컨텍스트를 더 씁니다):

opencode.jsonc{
  "tool_output": { "max_lines": 4000, "max_bytes": 102400 }
}

10.4 내장 도구 전체 목록

표부터 보면 외울 목록처럼 보이므로, 실제 요청 하나가 어떤 도구들로 풀리는지 먼저 보겠습니다. "로그인 실패 시 에러 메시지를 한국어로 바꿔 줘"라고 하면 보통 이렇게 진행됩니다.

  1. grep으로 "Invalid credentials" 같은 문구가 있는 파일을 찾습니다.
  2. read로 그 파일의 해당 부분을 읽습니다.
  3. edit로 문구를 바꿉니다(GPT 계열 모델이면 patch).
  4. shell로 관련 테스트를 돌려 확인합니다.

일상적인 코딩은 이 네 가지(찾기·읽기·고치기·실행)로 대부분 끝납니다. 아래 표는 전체를 하는 일별로 묶은 참조표입니다. 처음에는 굵은 글씨의 분류 줄만 훑어도 충분합니다.

  • "모드"의 direct는 모델이 이름으로 바로 부르는 도구, CM은 Code Mode의 execute 안에서만 부르는 도구입니다.
  • pinned는 Code Mode 카탈로그가 예산 때문에 잘려도 항상 목록에 보이는 도구입니다. 플래그가 붙은 도구는 해당 기능 플래그를 켜야 나타납니다.
  • "권한 action"은 11장의 권한 규칙에 쓰는 이름입니다.

10.5 Freeform 입력: 긴 코드를 원문 그대로

이 절을 읽는 이유 이 절은 도구가 무엇을 하느냐가 아니라, 모델이 도구에 입력을 어떻게 포장해 넘기느냐를 다룹니다. 사용자가 켜고 끌 설정은 없고, 모델이 지원하면 저절로 쓰입니다. 그런데도 따로 다루는 이유는 네 가지입니다.
  1. 다음 절 Code Mode의 준비입니다. Code Mode는 모델이 코드를 써서 넘기는 방식인데, 그 코드가 매번 망가지지 않고 전달되는 이유가 여기에 있습니다.
  2. patch의 형식이 깨지지 않는 이유입니다.
  3. 프로바이더 API의 기능과 이어집니다. Freeform은 OpenAI API의 Custom tools를 OpenCode 도구에 연결하는 장치입니다. 모델에 따라 동작이 달라지는 이유가 여기서 나옵니다.
  4. 화면에서 보이는 현상을 설명합니다. GPT 모델에서 파일 수정이 "패치" 형태로 보이거나, execute 호출 내용이 JSON이 아니라 코드로 보이는 이유입니다.

문제: 긴 코드를 JSON 칸에 넣기

도구 입력은 원래 JSON입니다. read처럼 칸이 짧다면 아무 문제가 없습니다.

{ "path": "package.json" }

그런데 입력 자체가 긴 코드나 패치인 도구가 둘 있습니다. Code Mode의 execute와, GPT 계열 모델이 파일을 고칠 때 쓰는 patch입니다. 이 코드를 JSON 문자열 안에 넣으면 이렇게 됩니다.

JSON으로 보낼 때{ "code": "const r = await tools.github.list_issues({ repo: \"acme/api\" })\nreturn r.length" }

따옴표는 \"로, 줄바꿈은 \n으로 전부 바꿔 써야 합니다. 두 줄이라 읽을 만하지만, 수십 줄짜리 프로그램이나 여러 파일을 고치는 패치라면 모델이 이 변환에서 틀리기 쉽습니다. 하나만 틀려도 JSON이 깨져 입력 오류가 나고, 모델은 다시 호출해야 합니다(10.3절의 입력 오류).

해결: 그 한 칸만 원문으로

Freeform은 그 한 칸을 JSON으로 감싸지 않고 원문 그대로 보내게 하는 방식입니다.

freeform으로 보낼 때const r = await tools.github.list_issues({ repo: "acme/api" })
return r.length

원문을 받으면 OpenCode가 그것을 {code: "..."} 객체로 다시 감싸 도구에 넘깁니다. 도구 쪽은 아무것도 달라지지 않고, 바뀌는 것은 모델과 주고받는 포장뿐입니다. 이 방식은 프로바이더 API의 기능을 빌려 쓴 것입니다. 아래에서 그 배경부터 보겠습니다.

배경: 프로바이더 API의 두 가지 도구 방식

Freeform은 OpenCode가 혼자 만든 개념이 아닙니다. OpenAI API는 도구를 두 종류로 나눕니다(OpenAI 문서의 Function calling → Custom tools).

  "input": "const r = await tools.github.list_issues({ repo: \"acme/api\" })\nreturn r.length" }

위쪽은 코드를 JSON 객체에 넣고, 그 객체를 다시 문자열로 넣기 때문에 이스케이프가 두 겹입니다. 모델은 그중 안쪽 한 겹, 즉 {"code": "..."} 안의 이스케이프를 직접 맞춰 써야 합니다. 아래쪽은 모델이 코드를 그냥 씁니다. 바깥 JSON 포장은 API가 처리합니다.

두 방식 모두 도구를 실제로 실행하는 쪽은 모델이 아니라 애플리케이션입니다. Custom tool이라고 모델이 코드를 직접 돌리는 것이 아닙니다. 모델은 글을 만들 뿐이고, 그 글을 받아 실행하는 것은 OpenCode입니다. 그래서 권한 검사·훅·Code Mode 샌드박스가 그대로 적용됩니다.

OpenCode의 Freeform: Custom tool로 내보내는 표시

OpenCode 도구에 붙는 freeform 옵션은 "이 도구는 지원되는 모델에게 Custom tool로 내보내라"는 표시입니다. 소스의 정의로는 "도구의 유일한 필수 문자열 필드에 대한 선택적 전송 인코딩"입니다. 그래서 입력 스키마에 필수 문자열 칸이 딱 하나 있는 도구에만 쓸 수 있습니다(execute의 code, patch의 patchText).

OpenCode 형식OpenAI로 나갈 때쓰는 도구
{type:"text"}format 없음(아무 텍스트)execute(JavaScript 코드)
{type:"regex", pattern}grammar, syntax regex—
{type:"lark", grammar}grammar, syntax larkpatch(패치 형식)

변환은 프로토콜 계층(ai/src/protocols/openai-freeform.ts)이 맡습니다. OpenAI Responses와 Chat Completions가 이 모듈을 공유합니다. 소스 주석의 표현대로 "원문 텍스트는 전송 구간에서만 오가고, 그 밖의 모든 곳에서 호출은 평범한 { field: raw } 입력을 유지"합니다.

  • 받을 때: 모델이 보낸 원문을 {"code": "..."} 같은 JSON 입력으로 다시 감쌉니다. 스트리밍 중에도 원문 조각을 JSON 인자 조각으로 바꿔 내보내므로, 세션·UI·도구 실행 쪽은 이 호출이 Custom tool로 왔는지 알 필요가 없습니다.
  • 다시 보낼 때: 다음 스텝에서 대화 이력을 다시 보낼 때는 지난 호출을 원래 왔던 모양(custom_tool_call)으로 되돌려 보냅니다.

언제 원문으로 보내나: 모델 능력

Custom tool은 모든 모델이 지원하지 않습니다. OpenCode는 요청을 만들 때 도구의 freeform 형식이 모델 능력(capabilities.freeform) 목록에 있을 때만 그대로 두고, 없으면 지웁니다(session/model-request.ts). 지워진 도구는 평범한 JSON 도구(Function tool)로 나갑니다.

  • 모델 능력은 models.dev 카탈로그의 tools.freeform 값(text·lark·regex 중 해당하는 것)에서 옵니다.
  • 그래서 같은 execute 호출도 GPT 계열에서는 코드 원문으로, Claude 같은 다른 모델에서는 {"code": "..."} JSON으로 오갑니다. 기능은 같고 포장만 다릅니다.
  • 사내 게이트웨이처럼 카탈로그에 없는 모델이라면 모델 설정의 capabilities.freeform으로 직접 알려 줄 수 있습니다. 실제로 Custom tool을 받는 엔드포인트일 때만 켜십시오.
opencode.jsonc{
  "providers": {
    "corp-gateway": {
      "models": {
        "big": { "modelID": "corp-big-2", "capabilities": { "freeform": ["text", "lark"] } }
      }
    }
  }
}

16.9절의 게이트웨이 예제에 능력 한 줄을 더한 설명용 설정입니다.

문법을 주면 형식이 보장됩니다. patch처럼 Lark 문법을 주면 프로바이더가 모델이 글자를 만들어 내는 단계에서부터 문법에 맞는 것만 나오게 강제할 수 있습니다. 패치의 형식이 깨지는 일은 이렇게 막습니다.

형식이 맞는다고 내용이 옳은 것은 아닙니다 문법은 "패치처럼 생긴 글"을 보장할 뿐입니다. 엉뚱한 줄을 고치는 패치도 형식은 맞을 수 있습니다. 수정 내용은 여전히 diff로 확인하십시오.

정리하면, Freeform 덕분에 모델은 다음 절의 Code Mode 프로그램을 이스케이프 걱정 없이 원문 그대로 길게 쓸 수 있습니다. 이제 그 프로그램이 무엇을 하는지 볼 차례입니다.

10.6 Code Mode: 도구 호출을 자바스크립트로 엮는다

Code Mode를 한마디로 줄이면 이렇습니다. 모델이 도구를 하나씩 호출하는 대신, 여러 도구의 호출 순서를 JavaScript 코드로 써서 한꺼번에 실행하게 하는 방식입니다. 쉬운 예부터 보겠습니다.

예: 서울과 부산의 기온 비교

날씨 MCP 서버가 연결되어 있고, 사용자가 이렇게 요청했다고 합시다(도구 이름과 값은 설명용).

서울과 부산의 현재 기온을 비교해 줘.

기존 방식에서는 모델이 도구를 부르고, 결과를 받아 읽고, 다음 행동을 정합니다.

  1. 모델: get_weather("서울") 호출 → 15℃를 받아 읽음
  2. 모델: get_weather("부산") 호출 → 19℃를 받아 읽음
  3. 모델: 두 값을 비교해 "부산이 4℃ 높습니다"라고 답함

(두 호출을 한 번에 병렬로 요청할 수도 있지만, 결과가 모두 모델에게 돌아오고 계산을 모델이 한다는 점은 같습니다.)

Code Mode에서는 모델이 다음 JavaScript 코드를 써서 execute라는 도구 하나에 넘깁니다.

모델이 쓰는 코드 (설명용)const [seoul, busan] = await Promise.all([
  tools.weather.get({ city: "서울" }),
  tools.weather.get({ city: "부산" }),
])
return { difference: busan.temp - seoul.temp }

OpenCode는 이 코드를 실행하면서 두 도구를 실제로 부르고, 차이를 계산하고, 마지막 return 값인 { difference: 4 }만 모델에게 돌려줍니다.

핵심은 두 가지입니다.

  • 도구 호출을 코드로 묶는다. 도구를 부를 때마다 모델이 끼어들지 않고, 코드가 정한 순서대로 실행됩니다.
  • 중간 결과를 모델에게 보내지 않는다. 코드 안에서 필요한 값만 뽑거나 계산해 최종 결과만 전달합니다.

왜 이런 방식을 도입했을까

MCP 서버를 여러 개 붙이면 도구가 수십~수백 개로 늘어납니다. 기존 방식에서는 그 도구들의 이름, 설명, 입력 스키마를 요청마다 전부 모델에게 보내야 합니다. Code Mode에서는 많은 도구를 execute 하나 뒤에 묶고, 도구 목록은 짧게 요약해서만 알려 줍니다.
