8장 세션 엔진 II — 에이전트 루프

이제 엔진의 심장부인 runner/llm.ts와 runner/step.ts를 봅니다. ChatGPT 답변이 "가장 중요한 파일"로 꼽은 두 파일입니다. 판단은 모델에 맡기고 행동은 프로그램이 실행하는 구조가 여기서 완성됩니다.

8.1 용어: 스텝, 턴, 시도

용어뜻
스텝(step)논리적 LLM 호출 1회. "각 스텝은 다시 읽은 이력에서 이어지는 명시적 llm.stream 호출 하나"(AGENTS.md)
시도(attempt)한 스텝 안의 물리적 요청. 재시도·오버플로 복구로 여러 번일 수 있음
턴(turn)유휴 표지(idle 메시지) 사이의 모든 스텝. "turn"이라는 단어는 이 의미로 예약
drain실행 파이버가 inbox를 비우며 스텝을 돌리는 한 번의 바쁜 기간
"메모리 속 도구 루프"를 금지한 이유 AGENTS.md는 "메모리 속 도구 루프를 추가하지 말라"고 못 박습니다. V1은 Vercel AI SDK의 streamText가 도구 디스패치를 맡았습니다(V1 소스 주석: "AI SDK owns provider execution and tool dispatch"). 그러면 도구 호출과 재호출 사이의 상태가 SDK 메모리 안에만 있어서, 중간에 죽으면 복구할 수 없고 재시도·압축을 끼워 넣을 틈도 없습니다. V2는 스텝마다 DB에서 이력을 다시 읽어 요청을 새로 만듭니다. 느려 보이지만 모든 스텝이 관찰·재생·재개 가능해집니다.

그림 8-1 SessionRunnerLLM.drain의 흐름

session/runner/llm.ts — 메인 루프while (true) {
  const next = yield* advanceToStep()
  if (next._tag !== "Ready") return next
  continuing = yield* runStep(next.context, step, input.interruption)
  stepped = true; step++; force = false; entering = false
}
  • continuing: 직전 스텝에서 모델이 로컬 도구를 호출했으면 true. 이때 다음 경계의 scope는 "steer"라서, 사용자가 중간에 보낸 steer는 다음 모델 호출 전에 끼어들고 queue는 기다립니다.
  • 스텝 카운터 리셋: 새 사용자 입력이 승격되면 step = 1. 사용자가 말을 걸 때마다 스텝 한도가 다시 채워집니다.
  • 제목 생성: 루트 세션이고 제목이 기본값이면 FiberMap에 비차단으로 포크합니다.
  • 지침 델타 커밋이 입력 전달보다 먼저: AGENTS.md 변경이 사용자 메시지보다 앞에 놓여, 모델이 바뀐 규칙을 보고 나서 요청을 읽게 됩니다.

8.3 runStep: 논리 스텝 하나의 정책

스텝마다 새 재시도 예산(SessionRunnerRetry.make)을 만들고, 오버플로 복구와 연속(continuation) 복구를 각각 한 번씩 허용합니다.

  1. 첫 시도가 아니면 컨텍스트를 다시 읽습니다. "재시도는 더 많은 입력을 전달하지 않고 컨텍스트만 새로 고칩니다."
  2. 토큰 추정 → compaction.compact({reason:"auto"}). 압축이 완료되면 새 assistant ID로 체크포인트부터 요청을 다시 만듭니다.
  3. (선택) 백그라운드 요약 선계산.
  4. 스텝 한도: agent.steps에 도달하면 "CRITICAL - MAXIMUM STEPS REACHED … Respond with text ONLY." 메시지를 덧붙이고 toolChoice:"none". 단 도구 정의는 유지합니다 — 프로바이더의 캐시된 접두를 보존하기 위해서입니다.
  5. baseTranscript로 요청 조립(9장) → steps.attempt.
결과(Outcome)처리

Retry{decision}RetryScheduled{attempt, at} 발행 후 대기. 출력 전이면 같은 assistant ID 재사용

그림 8-2 한 번의 시도(attempt)

session/runner/step.ts — 도구 호출 즉시 포크fiber: yield* Effect.uninterruptibleMask((restore) =>
  restore(executeTool(event, cancel)).pipe(
    Effect.flatMap(toolOutput.truncate),
    Effect.flatMap((outcome) => publisher.toolExecution(event.id, event.name, outcome)),
    Effect.catchTag("Tool.Error", (error) =>
      publisher.failTool(event.id, toSessionError(error), error.metadata).pipe(Effect.asVoid)),
  ),
).pipe(Effect.forkScoped),
세 가지 설계 포인트 ① 스냅숏과 요청의 병렬화(스냅숏과 요청을 동시에): 작업 전 파일 상태를 찍는 일(스냅숏)과 모델에게 요청을 보내는 일을 함께 시작합니다. 스냅숏은 도구가 파일을 건드리기 전에만 있으면 되므로, 그만큼 모델의 첫 응답이 빨라집니다. 소스 주석의 표현으로는 "시작 스냅숏은 로컬 도구가 돌기 전에만 있으면 된다"이며, Git 트리 캡처를 첫 토큰까지의 시간(TTFT)에서 빼냅니다.
V1 대비: V1은 AI SDK가 도구를 먼저 돌려 버릴 수 있어서 스트림을 시작하기 전에 snapshot.track()이 끝나기를 기다렸고, 그만큼 첫 응답이 늦었습니다.
② 부작용 전 영속화(실행 전에 먼저 기록): 도구를 돌리기 전에 "이 도구를 실행한다"(Tool.Called)를 디스크에 먼저 적어 둡니다. 서버가 도중에 죽어도 "이 도구는 시작됐을 수도 있다"는 사실을 알 수 있으므로 정직하게 복구할 수 있습니다.
V1 대비: V1은 도구 실행을 AI SDK·LLM 계층이 맡고, 세션은 tool-call 이벤트를 받은 뒤에야 파트를 running으로 고쳤으므로 기록이 실행보다 앞선다는 보장이 없었습니다.
③ 열성(eager) 실행(나오는 즉시 실행): 모델이 말을 다 끝낼 때까지 기다리지 않고, 도구 호출이 나오는 대로 바로 돌립니다. 모델이 다음 도구 호출을 스트리밍하는 동안 앞선 도구가 이미 돌기 때문에, 파일 여러 개를 읽는 일이 하나씩이 아니라 동시에 진행됩니다.
V1 대비: 즉시 실행 자체는 V1에도 있었습니다(LLM 계층의 ToolRuntime.dispatch). 달라진 것은 실행 주체로, V2는 세션 스텝이 도구마다 파이버를 직접 띄우고 결과를 잘라 낸 뒤 이벤트로 저장합니다.

정착(settlement) 규칙

정착 규칙은 시도가 어떻게 끝났는지(사용자 정지, 서버 핸드오프, 오버플로, 권한 거부, 정상 종료 등)에 따라, 결과가 아직 없는 도구 호출과 스텝을 어떤 최종 상태로 확정할지 정한 규칙입니다.

  • 사용자 정지: 도구에 협조적 cancel을 보내고 COOPERATIVE_STOP = 5초 기다린 뒤 강제 중단.
  • 서버 핸드오프 준비됨: 크래시처럼 빠져나가 호출을 미정착으로 남겨, 다음 서버가 이어받게 합니다.
  • 출력 전 컨텍스트 오버플로: 1회 압축 후 Compacted.
  • 권한 거부·질문 취소: 해당 호출 실패 "The user declined this tool call", 나머지 미정착 도구 실패, 스텝 중단.
  • 알 수 없는 종료 사유: InvalidProviderOutputError(incomplete-stream).
  • finish === "length" → OutputLimit, 그 외 → Completed{needsContinuation}.

명세와 코드의 차이 specs/v2/session.md는 "최초 요청 + 최대 4회 재시도"라고 적었지만 v2.3.0 코드(model-retry.ts 27행)는 Schedule.recurs(10)입니다. 이 책은 코드를 기준으로 합니다. 문서는 의도를, 코드는 현재를 말한다는 점을 기억해 두십시오.

재시도 가능한 오류 분류: rate-limit, provider-internal, 전송되지 않았거나 전달이 불확실한 transport, 불완전 스트림. 출력이 시작된 뒤의 재시도는 새 assistant 메시지로 하며 부분 출력은 남깁니다.

루프는 언제 계속되고 언제 멈추나

④의 반복은 "모델이 할 말을 다 했나"가 아니라 이번 스텝에서 로컬 도구를 불렀나로 정해집니다. 도구 결과를 모델에게 돌려줘야 하므로 다음 스텝이 필요한 것이지요. 프로바이더가 자기 쪽에서 실행한 도구(예: 프로바이더 내장 웹 검색)는 결과가 이미 응답에 들어 있으므로 다음 스텝을 만들지 않습니다. 그 밖의 갈림길은 다음과 같습니다(각 항목 앞에 루프가 계속되는지 멈추는지 표시했습니다).

  • [계속 · 세 번 연속 잘리면 멈춤] 출력 토큰 한도에 걸려 답이 잘렸다 — "이어서 쓰라"는 합성 메시지를 넣고 계속합니다. 단, 잘린 응답이 세 번 연속이면(이어 쓰기 두 번 실패) 오류로 끝냅니다.
  • [계속] 맥락이 넘쳤다(overflow) — 압축으로 한 번 복구를 시도한 뒤 같은 스텝을 다시 합니다.
  • [계속] 일시적 오류 — 8.5절의 재시도 정책을 따릅니다. 재시도는 이력을 다시 읽지만 새 입력을 승격하지는 않습니다.
  • [멈춤] 에이전트의 steps 한도에 닿았다 — 마지막 스텝은 "이제 도구 없이 정리하라"는 프롬프트를 덧붙이고 toolChoice: none으로 보냅니다. 도구 정의 자체는 빼지 않는데, 빼면 프롬프트 앞부분이 달라져 캐시가 깨지기 때문입니다(9장).
  • [계속] queue로 넣은 입력이 있다 — 지금 턴이 끝나는 유휴 경계에서 승격되어 같은 실행 안에서 다음 턴으로 이어집니다. 그래서 스피너가 멈추지 않고 바로 다음 일을 시작합니다.
  • [계속] idle 훅에서 플러그인이 입력을 넣었다 — 끝내지 않고 계속합니다(목표를 다 이룰 때까지 일을 이어 가게 하는 플러그인이 이 지점을 씁니다).

도중에 프로세스가 죽으면

클레임은 4번에서 Started와 함께 쓰이고 15번에서 풀립니다. 그러니 4번 이후 어디서든 프로세스가 죽으면(크래시, 강제 종료) 클레임이 남고, 다음 부팅의 SessionRestart가 이를 찾아냅니다. 남은 도구 호출은 "Tool execution interrupted"(도구 실행이 중단됨)로 실패 처리되고, "The server restarted while you were working. Continue from where you left off without repeating completed work."(작업 중에 서버가 재시작되었습니다. 이미 끝낸 작업은 반복하지 말고 중단된 곳부터 이어서 하십시오.)라는 메시지가 들어가 턴이 재개됩니다(턴당 최대 10회). 소스 주석의 표현대로, 복구는 종료 훅이 아니라 데이터베이스의 성질입니다. 종료 훅은 크래시 때 돌지 않을 수 있지만 디스크의 클레임은 남기 때문입니다. 서버를 정상적으로 내릴 때(shutdown)도 일부러 클레임을 남겨 두므로, 다음에 서버가 뜨면 일하던 턴이 같은 방식으로 이어집니다.
