2장 1.x에서 2.x로 — 무엇이, 왜 바뀌었나

ChatGPT 답변은 "2.x는 1.x에 기능을 더한 것이 아니라 엔진·세션·서버 API·플러그인을 재설계한 버전"이라고 했습니다. 이 장은 V1 소스(1.19.5)와 V2 소스(2.3.0)를 나란히 놓고 그 말이 정확히 무엇을 뜻하는지 확인합니다.

2.1 하룻밤의 재작성이 아니었다

겉으로 드러난 차이부터 말하면, V1이 터미널마다 서버를 따로 띄워 작업했다면 V2는 여러 화면이 하나의 백그라운드 서버를 공유하고, 작업을 이벤트로 기록해 중단 후 재개하도록 바뀌었습니다. 그러나 이것은 결과입니다. 더 핵심적인 변화는 V1의 메모리 중심 실행 루프를, 입력과 진행 상태를 먼저 기록하고 하네스가 실행을 직접 통제하는 구조로 바꾼 것입니다. 공유 백그라운드 서버와 중단 후 복구는 이 설계가 드러나는 대표적인 결과입니다(2.3절 표의 6·8행).

이 변화는 한 번에 일어나지 않았습니다. V1 저장소의 태그를 따라가면 V2가 1.x 안에서 점진적으로 자라났다는 사실이 보입니다.

그림 2-1 이행 연표 (V1 저장소 태그 기준)

그래서 1.19.5는 혼성(hybrid)입니다. 레거시 V1 런타임(packages/opencode/src/session/prompt.ts)과 V2 코어(packages/core/src/session/*)가 같은 프로세스에서 돌았습니다. V1 AGENTS.md는 이미 이렇게 적고 있습니다.

v1/repo/AGENTS.md — V2 Session Core- Keep durable prompt admission separate from model execution.
- Preserve one explicit `llm.stream(request)` call per provider turn and reload projected history
  before durable continuation. Do not bridge through legacy `SessionPrompt.loop(...)` or delegate
  orchestration to an in-memory tool loop.

이 지침이 앞에서 말한 핵심 변화를 그대로 요약합니다. V1은 큰 루프 안에서 메시지를 읽고 AI SDK에 모델 호출과 도구 실행을 맡겼습니다. 저장 기능은 있었지만, 실행 중 새 입력이 오거나 프로세스가 죽었을 때 처리하는 구조가 한 루프에 얽혀 있었습니다.

V2는 이를 세 책임으로 나눕니다(7.1 세 책임의 분리).

  • Inbox는 사용자 요청을 실행 전에 디스크에 남깁니다. 지침의 "durable prompt admission"이 이것입니다.
  • Execution은 세션마다 실행 흐름 하나를 관리하며 시작·중단·복구를 맡습니다.
  • Runner는 모델 호출과 도구 실행을 진행합니다.

또한 모델 호출 한 번이 끝나면 도구 결과를 이벤트로 저장하고, 다음 스텝은 저장된 이력을 다시 읽어 시작합니다. 지침에서 "모델 호출(provider turn) 한 번에 llm.stream(request)도 한 번만 부르고, 다음 스텝으로 넘어가기 전에 저장된 이력을 다시 읽는다"고 한 부분이 바로 이 규칙입니다. 따라서 중간 입력을 언제 반영할지, 어디서 다시 실행할지를 하네스가 명시적으로 결정할 수 있습니다. 공유 백그라운드 서버(4.3 관리형 백그라운드 서비스)는 이런 실행 구조를 여러 화면에서 이용하게 만드는 변화입니다. 두 루프의 구조 차이는 2.2절의 그림 2-2에서 다시 비교합니다.

점진적 이행의 원리 재작성 프로젝트가 실패하는 흔한 이유는 "새 버전이 완성될 때까지 아무도 쓰지 않는" 데 있습니다. OpenCode는 저장소(SQLite), 런타임(Effect), 서버(HttpApi)를 차례로 바꾸며 매 릴리스를 배포했고, 새 세션 코어를 옛 것 옆에서 실사용으로 검증한 뒤 분기했습니다. V2에 남은 호환 계층(core/src/v1/config, database/v1-migration.bun.ts)은 이 이행의 흔적입니다.

그림 2-3 V2 에이전트 루프의 호출 흐름과 루프 범위

바깥의 drain은 “다음 할 일이 있나?”를 확인하고, 있으면 한 단계씩 실행하는 반복입니다. 그 안의 runStep은 한 단계를 처리하며, 대화 압축이나 재시도가 필요하면 기록을 다시 읽고 그 단계를 다시 시도합니다. 맨 안의 attempt는 모델을 한 번 호출한 뒤, 흘러오는 답변 조각을 기록하고 도구 사용 요청을 실행하는 과정입니다. 모델을 다시 호출할 때는 매번 저장된 대화 기록을 다시 읽어 이어갑니다.

6행의 "고아 도구 휴리스틱"이란

휴리스틱은 확실한 근거 대신 상황을 보고 그럴듯하게 추정하는 경험칙입니다. "아마 이럴 것이다"라고 보고 처리하는 방식이지요.

고아 도구는 짝을 잃은 도구 호출입니다. 에이전트가 도구(셸, 파일 수정 등)를 부르면 대화 기록에 "도구 호출"이 남고, 끝나면 "도구 결과"가 짝으로 붙습니다. 그런데 도구가 도는 중에 노트북이 꺼지면 호출만 있고 결과가 없는 기록이 남습니다.

V1: 휴리스틱V2: 클레임(기록)
남아 있는 근거"결과 없는 도구 호출"이라는 상태뿐실행(턴)을 시작할 때 세션에 써 두는 클레임("이 세션의 턴이 진행 중"). 도구마다가 아니라 실행마다 하나
다음 실행 때 판단"결과가 없으니 아마 중간에 죽었겠지" 하고 추정해서 정리클레임이 남아 있으면 그 턴이 확실히 중단된 것으로 보고, 결과 없이 남은 도구 호출을 실패 처리
이어서 하기정리로 끝남. 자동으로 이어 가지 않음"서버가 재시작되었습니다… 이미 끝낸 일은 반복하지 말고 이어서 하라"는 메시지를 넣고 턴을 자동 재개(턴당 최대 10회, 7.6절, 8장)

V1은 실행 상태를 메모리(ensureRunning)에만 들고 있어서 프로세스가 죽으면 "무엇이 진행 중이었는지"도 함께 사라졌습니다. 남은 흔적을 보고 짐작할 수밖에 없었고, 그것이 휴리스틱입니다. V2는 실행을 시작할 때 기록부터 남기므로(쓰기 선행) 짐작할 필요가 없습니다.

사용자 입장에서는 이렇게 다릅니다. V1에서는 리팩터링 도중 노트북이 꺼지면, 다시 열었을 때 그 작업이 실패로 정리된 채 멈춰 있었습니다. V2에서는 다음에 서비스가 뜰 때 에이전트가 스스로 "중단됐었다"는 사실을 알고 이어서 작업합니다.

표의 차이는 실제 사용에서 어떻게 느껴질까요? V2의 장점은 대부분 작업을 디스크에 먼저 기록하고, 여러 화면이 하나의 서버를 함께 쓰는 구조에서 나옵니다. 에이전트와 대화하며 코드를 짜는 바이브코딩 상황에 빗대어 보면 다음과 같습니다(장면은 이해를 돕기 위한 예시입니다).

7·8 공유 서버·SSE터미널 두 개와 데스크톱 앱에서 같은 세션을 엶터미널마다 서버가 따로 뜸백그라운드 서비스 하나가 SSE로 모든 화면에 같은 상태를 보여 줌(4.3절)
14 서브에이전트"인증 코드 위치 찾아줘"를 맡겨 놓고 그사이 UI 수정 얘기를 함task 도구가 끝날 때까지 부모 대화가 멈춤하위 작업은 백그라운드로 돌고, 유휴가 되면 결과가 부모 대화에 보고됨(12.5절)
16·17 압축·지침몇 시간 이어지는 긴 세션매 스텝 지침을 다시 구성해 프롬프트 캐시가 깨지기 쉬움앞부분은 그대로 두고 바뀐 지침만 델타로 덧붙여 캐시가 유지되고, 비용·지연이 줄어듦(9.5절)
11 Code Mode"파일 20개 훑어서 TODO 모아줘"Code Mode는 MCP 도구에만 쓸 수 있음execute 스크립트 하나로 여러 도구 호출을 묶고, 중간 결과를 모델에 모두 보여 주지 않아 토큰을 아낌(10.6절)
12 권한"git 명령은 허용하되 git push만 묻게" 설정도구별 맵과 tools 불리언을 따로 맞춰야 함순서 있는 permissions 배열 하나에서 마지막에 매치된 규칙이 이겨, 예외를 한눈에 볼 수 있음(11.1절)
18 스냅숏에이전트가 망친 수정을 되돌림그림자 Git으로 되돌림같은 방식에 패킹·동시 캡처가 더해져 더 튼튼해짐(11.9절)

4번 동시성에서 사용자가 얻는 것은 끼어들 수 있다는 점이 아니라, 보낸 메시지를 다루는 방법이 늘었다는 점입니다. V1도 작업 중에 보낸 메시지가 다음 모델 호출에 반영되었지만, 따로 대기시키거나 전달 방식을 고를 수는 없었습니다. V2에서는 다음이 가능합니다.

  1. 다음 작업을 예약할 수 있습니다. queue로 보내면 지금 하는 일을 흔들지 않고, 작업이 끝난 유휴 경계에서 반영됩니다(7.4절).
  2. 보낸 뒤에도 바꾸거나 취소할 수 있습니다. 대기 중인 메시지는 대화 이력 밖의 session_inbox에 있으므로, 반영되기 전이면 steer와 queue를 서로 바꾸거나 취소할 수 있습니다(7.3절).
  3. 메시지를 잃지 않습니다. 대기 입력이 DB에 저장되므로 서버가 죽어도 남고, 같은 세션을 연 모든 화면에서 똑같이 보입니다(6장).
  4. 압축이 끼어도 지시가 뭉개지지 않습니다. 압축을 앞선 steer보다 먼저 처리하므로, 사용자가 보낸 지시가 요약에 섞이지 않고 원문으로 남습니다(7.4절).

19개 차원 표에는 따로 행이 없지만, 실제로 쓸 때 가장 크게 체감되는 차이 중 하나가 프롬프트 캐시입니다. 에이전트는 스텝마다 거의 같은 대화를 통째로 다시 보내고, 프로바이더는 요청 앞부분이 바이트 단위로 같으면 그 부분을 캐시에서 원래 입력 가격의 10~25% 정도로 읽습니다. 그래서 앞부분을 얼마나 안 바꾸느냐가 비용과 응답 속도를 몇 배씩 좌우합니다(9.1절). V1(1.19.5)과 V2의 소스를 나란히 보면 차이는 세 군데입니다.

장면V1 (1.19.5)V2
긴 세션 도중 AGENTS.md를 고침매 스텝 시스템 프롬프트를 새로 조립(환경, 지침 파일, MCP 지침, 스킬). 지침이 바뀌면 맨 앞부터 달라져 그 뒤 대화 전체가 캐시에서 빠짐시스템 프롬프트는 에포크 동안 고정. 바뀐 지침은 대화 중간에 "변경 알림"으로 덧붙여 앞부분 캐시가 유지됨(9.5절)

이 차이는 우연이 아니라 설계 동기입니다. 2.4절 표의 ④ "캐시 친화 컨텍스트"가 바로 이것이고, V2는 그 밖에도 끝쪽에 붙이는 plan 모드 알림, 접두를 재사용하는 압축, steps 한도에서도 도구 정의를 빼지 않는 처리처럼 캐시를 지키는 장치를 곳곳에 둡니다(9장, 8.7절). 사용자 쪽에서 캐시를 깨지 않는 습관은 9.1절의 사용법 상자에 정리했습니다.
